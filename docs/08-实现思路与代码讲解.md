## 1. 整体骨架：一个请求是怎么走完的

涉及：[main.py](../backend/app/main.py)、[deps.py](../backend/app/deps.py)、[errors.py](../backend/app/errors.py)、[database.py](../backend/app/database.py)、`api/*.py`

### 要解决什么

每个接口都要做同样几件事：认出是谁在请求、确认要操作的数据是他的、出错时按统一格式返回。不能每个接口各写一遍。

### 思路

分三层，和 Spring Boot 的 Controller / Service / 领域层一一对应：

```
api/        接请求、校验参数、返回 JSON（很薄）
services/   编排流程、读写数据库、开后台任务
parser/ diagnose/ matching/ graphs/ rewrite/    领域层：只做计算，输入输出都是普通数据，不碰数据库
```

"公共的前置工作"（认证、归属检查）用 FastAPI 的**依赖注入**抽出来；"出错怎么返回"用**全局异常处理**统一做。

### 代码逐段讲

**① 依赖注入：拿到"当前用户"**（[deps.py:17](../backend/app/deps.py#L17)）

```python
def get_current_user(
    credentials: HTTPAuthorizationCredentials | None = Depends(_bearer),   # 从请求头取 Bearer 令牌
    db: Session = Depends(get_db),                                          # 数据库会话
) -> User:
    user_id = decode_access_token(credentials.credentials) if credentials else None
    user = db.get(User, user_id) if user_id is not None else None
    if user is None:
        raise ApiError(UNAUTHORIZED, "未登录或登录已过期")
    return user
```

接口里只要写一个参数 `user: User = Depends(get_current_user)`，FastAPI 就会在调用接口**之前**先调用 `get_current_user`，把返回值传进来；没登录就在进接口之前抛异常，接口本身一行认证代码都不用写。

> **〔语法〕`Depends` 可以一层套一层。** `get_current_user` 自己也依赖 `_bearer` 和 `get_db`。项目里叠了三层：
> `get_current_user`（登录了）→ `get_owned_resume`（简历是你的）→ `get_parsed_resume`（而且已经解析完）。
> 查"简历原文分块"的接口直接写 `resume: Resume = Depends(get_parsed_resume)`，三个检查一次到位。

**② 越权访问一律 404**（[deps.py:37](../backend/app/deps.py#L37)）

```python
def load_owned_resume(db: Session, user: User, resume_id: int) -> Resume:
    resume = db.get(Resume, resume_id)
    if resume is None or resume.user_id != user.id or resume.is_deleted:
        raise ApiError(NOT_FOUND, "简历不存在")
    return resume
```

为什么别人的简历返回 404 而不是 403？403 等于告诉对方"这个 id 存在，只是你没权限"，别人就能挨个试 id 来探测。404 让"不存在"和"不是你的"看起来一模一样。

**③ 数据库会话：带 `yield` 的依赖**（[database.py:34](../backend/app/database.py#L34)）

```python
def get_db() -> Generator[Session, None, None]:
    db = SessionLocal()
    try:
        yield db          # ← 接口拿到的就是这个 db
    finally:
        db.close()        # ← 接口返回后（哪怕抛了异常）一定执行
```

> **〔语法〕带 `yield` 的依赖**：`yield` 之前的代码在接口执行前跑，`yield` 出去的值交给接口用，接口结束后再回来执行 `finally`。相当于 Java 的 try-with-resources。

**④ 统一的错误格式**（[errors.py:29](../backend/app/errors.py#L29)）

```python
class ApiError(Exception):
    def __init__(self, code: int, message: str):
        super().__init__(message)
        self.code = code
        self.message = message

    @property
    def http_status(self) -> int:
        return self.code // 100          # 40401 → 404，50003 → 500

def register_error_handlers(app: FastAPI) -> None:
    @app.exception_handler(ApiError)
    async def _api_error(_: Request, exc: ApiError) -> JSONResponse:
        return JSONResponse(_body(exc.code, exc.message), status_code=exc.http_status)
    ……
```

业务代码只管 `raise ApiError(NOT_FOUND, "…")`，响应格式 `{code, message, data}` 由这里统一拼。错误码设计成"前三位就是 HTTP 状态码"，所以 `code // 100` 一行就换算出来。另外还注册了两个兜底：参数校验失败 → 40001，任何没料到的异常 → 50001（并把完整堆栈写进日志）。

**⑤ 后台任务：上传立刻返回，解析在后台跑**（[api/resume.py:22](../backend/app/api/resume.py#L22)）

```python
if not deduplicated or resume.parse_status == "failed":
    background.add_task(parse_resume, resume.id, session_factory, llm)
return ok(UploadOut(id=resume.id, task_id=f"parse:{resume.id}", parse_status=resume.parse_status, deduplicated=deduplicated))
```

`BackgroundTasks` 的意思是：响应先发出去，然后在**同一个进程**里接着执行 `parse_resume`。解析要调模型，十几秒，不能让用户干等。
注意后台任务要**自己开数据库会话**（`session_factory()`）——请求用的那个会话在响应返回时已经关掉了。

### 为什么全部用同步写法（`def` 而不是 `async def`）

- FastAPI 会把普通 `def` 接口放进线程池执行，不会卡住别的请求；
- 用到的库（PyMuPDF、SQLAlchemy、LangGraph 的 `invoke`）都是同步 API；换成 async 要把数据库驱动等整套换成异步版本；
- 单人毕设、单进程部署，async 带来的复杂度不值得。

### 踩过的坑

- **必须单进程运行（`--workers 1`）**：后台任务在接收请求的那个进程里跑；启动时的"清理中断任务"（把库里 `running` 的记录标成失败）依赖一个前提——启动那一刻库里的 `running` 一定是上次进程留下的死任务。开多个进程，就会把别的进程正在跑的任务误标成失败。见 [main.py](../backend/app/main.py) 的 `cleanup_interrupted_tasks`。
- **表结构不由代码自动建**：没用 `create_all()`，而是由 `scripts/dump_schema.py` 从 `models.py` 生成 `schema.sql`，手动执行；测试 `test_schema_sync.py` 检查两者一致。好处是建表语句能直接放进论文附录，也不会在生产库上被代码悄悄改表。

### 答辩可能被问

- **越权怎么防？** 所有按 id 取数据的地方都经过 `load_owned_resume` 这类函数比较 `user_id`，别人的一律 404。
- **为什么不用 async？** 见上面三条。

## 2. 登录：密码、令牌、自动退出

涉及：[security.py](../backend/app/security.py)、[api/auth.py](../backend/app/api/auth.py)、[schemas.py](../backend/app/schemas.py) 的 `_Credentials`；前端 [api/client.ts](../frontend/src/api/client.ts)、[store/auth.ts](../frontend/src/store/auth.ts)、[App.tsx](../frontend/src/App.tsx)

### 思路

- 密码用 **bcrypt** 哈希后存：自带随机盐，同一个密码每次哈希结果都不同；而且故意算得慢（约 0.1 秒一次），暴力破解成本高。
- 登录成功发 **JWT**：一段带签名的令牌，服务端不用存会话，拿到令牌验一下签名就知道是谁。
- 前端把令牌存 `localStorage`，每次请求带上；任何接口返回 401 就自动退出。

### 代码逐段讲

**① 防止别人"探测用户名"**（[api/auth.py:47](../backend/app/api/auth.py#L47)、[security.py:26](../backend/app/security.py#L26)）

```python
DUMMY_HASH = hash_password("dummy-password-for-timing")      # 模块加载时算好一个假哈希

def login(body: LoginIn, db: Session = Depends(get_db)):
    user = db.scalar(select(User).where(User.username == body.username))
    password_ok = verify_password(body.password, user.password_hash if user else DUMMY_HASH)
    if user is None or not password_ok:
        raise ApiError(UNAUTHORIZED, "用户名或密码错误")
    return _token_response(user)
```

两层防护：
1. 提示语不区分"用户不存在"还是"密码错"；
2. **用户不存在时也验一次假哈希。** bcrypt 很慢，如果用户不存在就立刻返回，攻击者看响应是 1 毫秒还是 100 毫秒就知道用户名存不存在——这叫**时序攻击**。验一次假哈希，两种情况耗时一样。

**② 注册判重：靠数据库的唯一约束，不是"先查再插"**（[api/auth.py:34](../backend/app/api/auth.py#L34)）

```python
user = User(username=body.username, email=body.email, password_hash=hash_password(body.password))
db.add(user)
try:
    db.commit()
except IntegrityError:          # 违反 UNIQUE 约束
    db.rollback()
    raise ApiError(CONFLICT, "用户名或邮箱已被注册") from None
```

"先查有没有这个用户名、没有再插入"有并发漏洞：两个请求同时查，都查到"没有"，都插进去了。让数据库的 UNIQUE 约束来判，插入失败就是重名，天然没有竞争。

**③ bcrypt 只看前 72 字节**（[schemas.py](../backend/app/schemas.py) 的 `_Credentials`）

```python
BCRYPT_MAX_BYTES = 72

@field_validator("password")
@classmethod
def _fits_bcrypt(cls, v: str) -> str:
    if len(v.encode("utf-8")) > BCRYPT_MAX_BYTES:
        raise ValueError("密码过长")
    return v
```

bcrypt 会忽略 72 字节以后的内容，两个前 72 字节相同的长密码都能登录，所以直接拒收。中文一个字占 3 字节，所以要按 `encode("utf-8")` 之后的字节数算，而不是字数。前端 [AuthDialog.tsx](../frontend/src/components/AuthDialog.tsx) 用 `new TextEncoder().encode(password).length` 做了同样的检查。

**④ JWT 的内容与签名**（[security.py:33](../backend/app/security.py#L33)）

```python
def create_access_token(user_id: int) -> str:
    now = datetime.now(timezone.utc)
    payload = {"sub": str(user_id), "iat": now, "exp": now + timedelta(seconds=token_lifetime_seconds())}
    return jwt.encode(payload, settings.JWT_SECRET, algorithm=ALGORITHM)
```

令牌长这样：`头.内容.签名`。**内容只是 base64 编码，谁都能解开看**；签名是用服务端密钥算出来的，内容被改一个字签名就对不上。所以里面只放 `user_id`，不放任何敏感信息。`exp` 是过期时间，`jwt.decode` 会自动检查。

**⑤ 前端：所有请求走一个出口，401 自动退出**（[client.ts:50](../frontend/src/api/client.ts#L50)）

```ts
export async function request<T>(path: string, options: { method?: string; body?: unknown } = {}): Promise<T> {
  ……
  if (!res.ok || payload.code !== 0) {
    if (res.status === 401 && token) onUnauthorized?.()     // ← 令牌失效
    throw new ApiError(payload.code, payload.message || '请求失败')

```

`onUnauthorized` 是登录 store 注册进来的回调（`setUnauthorizedHandler(signedOut)`）：清掉令牌、状态变成未登录，路由守卫 `RequireAuth` 就会把人带回首页并弹出登录框。

为什么用"注册回调"，而不是在 `client.ts` 里直接 `import` 登录 store？因为 store 要调用 `client.ts` 发请求，`client.ts` 再反过来 import store 就成了**循环依赖**。

**⑥ 刷新页面时恢复登录**（[store/auth.ts:17](../frontend/src/store/auth.ts#L17)）

```ts
status: tokenStore.get() ? 'checking' : 'guest',

async bootstrap() {
  if (!tokenStore.get()) return set({ status: 'guest' })
  try {
    set({ user: await authApi.me(), status: 'authed' })
  } catch {
    signedOut()     // 过期、被篡改或后端不可用：都按未登录处理
  }
},
```

状态有三种：`checking / authed / guest`。有令牌时先是 `checking`，页面显示"加载中"，等 `/auth/me` 回来再决定。如果只有"登录 / 未登录"两种，刷新的那一瞬间还没验完令牌，就会被当成未登录踢回首页。

> **〔语法〕zustand**：`create((set) => ({...}))` 返回一个 hook。组件里写 `useAuth((s) => s.user)` 表示"只订阅 user 这一个字段"，别的字段变了这个组件不会重新渲染。比 React Context 省事，也不用在最外层包 Provider。

### 踩过的坑

- **localStorage 在浏览器隐私模式下可能直接抛异常**，所以 `tokenStore` 的读写都包了 try/catch。
- **后端没启动时**，Vite 代理返回的是一个 HTML 错误页，`res.json()` 会抛异常。`request` 里单独接住这种情况，提示"服务暂时不可用，请确认后端已启动"。

### 答辩可能被问

- **JWT 被别人拿到怎么办？** 在过期之前（24 小时）确实能冒用，所以必须走 HTTPS；要能"立刻作废"就得在服务端存黑名单，本项目没做，属于已知取舍。
- **为什么不用 Session + Cookie？** JWT 无状态，服务端不用存会话；前后端分离、SSE 流式接口都统一用请求头带令牌，处理起来一致。

## 3. 解析简历：从 PDF 到"坐标系"

涉及：[resume_service.py](../backend/app/services/resume_service.py)（上传校验）、[parse_service.py](../backend/app/services/parse_service.py)（后台解析的编排），以及 `parser/` 下的 [extract.py](../backend/app/parser/extract.py) → [layout.py](../backend/app/parser/layout.py) → [section.py](../backend/app/parser/section.py) → [pii.py](../backend/app/parser/pii.py) → [structure.py](../backend/app/parser/structure.py)

### 要解决什么

把一份 PDF 变成三样东西：
1. **`full_text`**：按正确阅读顺序拼起来的全文。两栏简历如果直接从上往下读，左右两栏会一行一行交错在一起。
2. **块（block）**：全文切成的一段段，每段记下它在 `full_text` 里的起止位置 `[char_start, char_end)`。
3. **结构化结果**：教育、经历、项目、技能……每一条都记着它由哪几块组成、对应哪段区间。

之后诊断、匹配、高亮全靠这套"第几个字到第几个字"的**坐标系**，所以它一旦定下来就永远不改（系统不变量①②）。

### 整体流程（[parse_service.py:30](../backend/app/services/parse_service.py#L30)）

```python
extracted = extract_pdf(settings.DATA_DIR / resume.file_path)   # ① 抽出每一行文字 + 坐标 + 字号 + 是否加粗
layout = analyze_layout(extracted)                               # ② 排阅读顺序、切块、定坐标系
sections = detect_sections(layout)                               # ③ 认出"教育背景""项目经历"这些章节
basics = extract_basics(layout, sections)                        # ④ 本地抽姓名电话邮箱（不发给模型）
structured = extract_structure(layout, sections, basics, llm, …) # ⑤ 让模型把章节拆成一条条
```

每一步都是纯函数（输入数据、输出数据），`parse_service` 负责读文件、改状态、写库。任何一步抛异常都会被接住，落成 `parse_status='failed'` 并记下原因（扫描件、加密、模型失败……），后台任务绝不能把异常"抛丢"。

### 3.1 上传校验：便宜的检查先做

（[resume_service.py:57](../backend/app/services/resume_service.py#L57)，[api/resume.py:32](../backend/app/api/resume.py#L32)）

```python
data = file.file.read(resume_service.max_upload_bytes() + 1)   # 最多读 20MB + 1 字节
upload = resume_service.validate_upload(file.filename or "", data)
```

只多读 1 个字节就能判断"超没超 20MB"——读到了第 20MB+1 个字节就说明超了，不用把一个 500MB 的文件整个读进内存。

校验按固定顺序、便宜的先做：扩展名 + 文件头魔数（`%PDF-`）→ 大小 → 能不能打开 / 有没有加密 → 页数。任何一步不过就拒收，**不落盘也不落库**。文件保存时用 UUID 命名，用户传上来的文件名只用来显示，所以文件名里有 `../` 这种路径穿越也无所谓。

同一个用户重复上传同一个文件（按 SHA-256 判断）会直接复用原来的记录，只解析一次；如果上次解析失败了，就重新排队解析。

### 3.2 按"行"抽取，并保证前后端算出的字数一样

（[extract.py:79](../backend/app/parser/extract.py#L79)、[extract.py:87](../backend/app/parser/extract.py#L87)）

PyMuPDF 能直接给出"块"（block），但它的块太粗（常把一整节十几行并成一块），顺序也不可靠（页顶的姓名可能排在最后）。所以只取"行"，顺序和分块自己做。

```python
_NON_BMP = re.compile(r"[\U00010000-\U0010FFFF]")    # emoji、部分图标字体

def clean_text(s: str) -> str:
    """唯一允许的文本清洗点：偏移一旦算出，任何地方都不得再改动文本。"""
    s = _NON_BMP.sub(_REPLACEMENT, s)
    s = _CONTROL.sub("", s)
    s = s.replace("\t", " ").replace(" ", " ").replace("　", " ")
    return s.strip()
```

为什么要把 emoji 换掉？**Python 和 JavaScript 数"字符长度"的方式不一样**：`"😀"` 在 Python 里 `len` 是 1，在 JS 里 `.length` 是 2（JS 按 UTF-16 编码单元计数）。后端说"高亮第 10 到 20 个字"，前端遇到 emoji 就会整体错位。把这类字符统一换成 `�`（它在两边都算 1），坐标就一致了。

判断"这一行是不是加粗"和"字号多大"：一行可能由多段不同样式的文字组成，按**字数加权**取多数（[extract.py:87](../backend/app/parser/extract.py#L87)）：

```python
bold = sum(len(s["text"]) for s in spans if s["flags"] & _BOLD_FLAG or "bold" in s["font"].lower())
by_size: dict[float, int] = {}
for s in spans:
    size = round(s["size"], 1)
    by_size[size] = by_size.get(size, 0) + len(s["text"])
font_size = max(by_size.items(), key=lambda kv: kv[1])[0]    # 字数最多的那个字号
……
return Line(page_no, x0, y0, x1, y1, text, font_size, bold * 2 > total)   # 加粗字数过半才算加粗
```

这样行首一个特别大的项目符号"●"不会把整行的字号带偏。

扫描件怎么识别：全文能抽出来的字符少于 100 个，就认为是图片型 PDF，抛 `ScannedPdfError`。

### 3.3 分栏算法：怎么知道是两栏、怎么按对的顺序读（全项目最难的部分）

（[layout.py](../backend/app/parser/layout.py) 的 `_best_band`、`_order`）

**核心直觉**：两栏简历中间有一条**从上到下贯穿的空白带**。找到它，左边读完再读右边。难点在于：页顶的姓名、通栏的章节标题会"压"在这条空白带上，把它挡住。

**第一步：用滑动窗口找空白带**（[layout.py:147](../backend/app/parser/layout.py#L147)）

```python
def _best_band(lines: list[Line], page_width: float) -> _Band | None:
    width = settings.LAYOUT_MIN_GAP_RATIO * page_width        # 窗口宽 = 3% 页宽
    a = min(l.x0 for l in lines)
    while a + width <= right_end:                              # 窗口从左往右每次挪 2pt
        b = a + width
        left = [l for l in lines if l.x1 <= a + EDGE_EPS]      # 整行都在窗口左边的
        right = [l for l in lines if l.x0 >= b - EDGE_EPS]     # 整行都在窗口右边的
        if len(left) >= MIN_SIDE_LINES and len(right) >= MIN_SIDE_LINES:            # 两边都至少 3 行
            left_share, right_share = char_share(left), char_share(right)
            if min(left_share, right_share) >= MIN_SIDE_CHAR_RATIO:                  # 两边字数都 ≥ 12%
                blocked = {i for i, l in enumerate(lines) if l.x0 < b - EDGE_EPS and l.x1 > a + EDGE_EPS}
                key = (len(blocked), abs(left_share - right_share))   # 压住窗口的行越少越好，其次两边越均衡越好
                if best is None or key < best[0]:
                    best = (key, a, blocked)
        a += GRID_STEP
    ……
    return _Band(x0, x1, blocked, 1 - len(blocked) / n)       # clearness（文档里的 c）= 1 − 被压住的行数 / 总行数
```

逐句理解：
- 一个 3% 页宽的竖条从左扫到右，每个位置数一数"有多少行横跨了这个竖条"（`blocked`）；
- 横跨的行越少，这里越可能是栏间空白；
- **两边都必须真的像一栏**（每边 ≥3 行、字数 ≥12%）。没有这个条件，单栏简历里"项目名 ………… 2023.09–2024.01"这种右对齐的日期，会被当成一个很窄的"右栏"；
- 最后用 `c = 1 − 被压住的行数 / 总行数` 表示"这条空白带有多干净"：c = 1 是完全干净，c 越小越不像。

**第二步：递归切分**（[layout.py:251](../backend/app/parser/layout.py#L251)）

```python
def _order(lines, region, col=None, depth=0, allow_y_cut=True) -> list[_Placed]:
    band = _best_band(lines, region.page_width) if depth < MAX_DEPTH else None

    if band and band.clearness >= settings.LAYOUT_DOUBLE_MIN_C:          # c ≥ 0.8：确定是分栏
        spanning = band.blocked | _header_rows_above_right_column(lines, band, region.page_width)
        if spanning:
            return _split_by_spanning_rows(lines, spanning, region, col, depth)  # 有跨栏行：先横着切
        return _split_columns(lines, band, region, col, depth)                  # 没有：直接左右切

    if allow_y_cut:
        segments = _y_segments(lines)          # 在大的水平留白处横切成几段
        if len(segments) > 1:
            return [p for seg in segments for p in _order(seg, region, col, depth + 1, allow_y_cut=False)]

    # 切不动了：这就是一个"叶子"，按 y、x 排好
    clearness = band.clearness if band else 0.0
    if settings.LAYOUT_SINGLE_MAX_C < clearness < settings.LAYOUT_DOUBLE_MIN_C:   # 0.3 < c < 0.8：说不清
        stats.unknown_lines += len(lines)
    return _place_rows(lines, 0 if col is None else col, stats)
```

这是**递归 XY 切分**的一个变体：
- 能竖着切（分栏）就竖着切；
- 竖着切不了，就在大的水平空白处横着切，切完的每一块再试一次竖切；
- 都切不动了就是"叶子"，叶子里按从上到下、从左到右排。

**跨栏行怎么处理**（[layout.py:292](../backend/app/parser/layout.py#L292)）：那几行"压住"空白带的行（姓名、通栏标题）本身不属于任何一栏。从上往下扫，遇到跨栏行就单独成段，夹在两段跨栏行之间的普通行作为一个区域递归处理：

```
姓名（跨栏）               → 单独一段，column_index = -1
┌ 左栏 A ┐  ┌ 右栏 A ┐     → 递归：先左后右
项目经历（通栏标题，跨栏） → 单独一段
┌ 左栏 B ┐  ┌ 右栏 B ┐     → 递归：先左后右
```

**第三步：给整页定性**（[layout.py:435](../backend/app/parser/layout.py#L435)）：说不清的行占全页 ≥30% → `unknown`（置信度 0.5）；分栏的行占 ≥30% → 看空白带中心在不在页宽 40%–60% 之间，在就是 `double`，偏一边就是 `sidebar`（侧边栏）；否则 `single`。

### 3.4 行 → 块，以及"坐标系"是怎么定下来的

（[layout.py:379](../backend/app/parser/layout.py#L379)、[layout.py:416](../backend/app/parser/layout.py#L416)）

排好序的"行"还要拼成"块"：一句话折行成两行，要并回一块；一条新的项目符号要另起一块。判断"这一行是另起一块，还是上一行的折行"：

```python
def _starts_new_block(prev, cur, body_size, head=None) -> bool:
    if prev is None:
        return True
    a, b = prev.line, cur.line
    different_place = cur.leaf != prev.leaf or a.page_no != b.page_no          # 换了区域 / 换了页
    different_style = a.font_size != b.font_size or a.is_bold != b.is_bold      # 字号或粗细变了
    explicit_start = _BULLET.match(b.text) is not None or _is_heading_like(b, body_size)  # 项目符号 / 像标题
    prev_is_complete = _is_heading_like(a, body_size) or prev.tabular or not _line_was_full(prev)  # 上一行没写满
    paragraph_gap = b.y0 - a.y1 > PARAGRAPH_GAP * b.height                       # 行间留白明显变大
    next_labeled_item = (head is not None and _LABEL.match(head.line.text) is not None
                         and _LABEL.match(b.text) is not None)                   # "标签：内容"列表的下一项
    return (different_place or different_style or explicit_start or prev_is_complete or paragraph_gap
            or next_labeled_item)
```

最有意思的是 `_line_was_full`：**上一行只有"写满到栏的右边"，下一行才可能是它的折行**。一句话没写满就换行了，说明是作者主动换的行。

块排好之后，**全系统唯一定义坐标系的函数**：

```python
def assign_offsets(blocks: list[Block]) -> str:

        b.char_start, b.char_end = cursor, cursor + len(b.text)
```

从此以后恒成立：`full_text[b.char_start:b.char_end] == b.text`（开区间）。测试 `test_full_text_contract` 专门断言这一条。之后任何地方都**不准再改动文本**（不准 strip、不准全角转半角），否则所有区间都会错位。

### 3.6 个人信息掩码：为什么必须"长度不变"

（[pii.py:84](../backend/app/parser/pii.py#L84)）

```python
def mask_pii(text: str, name: str | None = None) -> str:
    masked = _ID_CARD.sub(_mask_digits, text)      # 先处理身份证：它里面有一段会被手机号正则命中
    masked = _PHONE.sub(_mask_digits, masked)      # 手机号每个数字 → X
    masked = _EMAIL.sub(_mask_email, masked)       # 邮箱除 @ 和 . 以外的字符 → *
    if name and len(name.strip()) >= 2:
        masked = masked.replace(name.strip(), "某" * len(name.strip()))   # 姓名 → 同样个数的"某"

```

发给模型的永远是掩码后的文本（不变量⑤）。**逐字符替换、长度不变**的好处是：模型在掩码文本上说"第 120 到 135 个字有问题"，这个区间直接拿到原文上用，不需要任何换算。如果把手机号换成"[电话]"这种长度不同的占位符，后面所有的位置都会错开。

> **〔语法〕`re.sub` 的第二个参数可以是函数**：每匹配到一处就调用一次，参数是匹配对象 `m`，返回值就是替换成的内容。`_mask_digits` 返回 `re.sub(r"[\dXx]", "X", m.group(0))`，也就是把这一段里的数字逐个换成 X。

### 3.7 结构化抽取：模型只回"块编号"，不回文字

（[structure.py:116](../backend/app/parser/structure.py#L116)、[structure.py:161](../backend/app/parser/structure.py#L161)、[structure.py:213](../backend/app/parser/structure.py#L213)）

**问题**：让模型"把项目经历拆成一条条，每条给出描述文字"，模型会悄悄改标点、合并换行、甚至改写句子，拿它的文字去原文里就找不到了。

**做法**：发给模型的每一块前面带编号 `[#12]`，要求模型**只输出"这条经历由第 12、13 块组成"**。文字和区间全部由代码按编号从原文里切出来：

```python

        ids = self.valid(ids)                       # 不在本章节里的编号直接丢掉（模型编的）
        if not ids:
            return None
        ids = list(range(ids[0], ids[-1] + 1))      # 补全中间漏掉的块
        return {"block_ids": ids,
                "char_start": self.blocks[ids[0]].char_start, "char_end": self.blocks[ids[-1]].char_end}

def _build_experience(out, sb, section):

```

这样模型**根本没有机会改写简历内容**，每条描述都和原文逐字一致。日期也不让模型抽，由 `normalize.find_date_range` 用正则在块里本地识别。

> **〔语法〕`if h_span := sb.span(...)`** 是"海象运算符"：先赋值再判断，等价于 `h_span = sb.span(...)` 然后 `if h_span:`。

**各章节并行调用**（[structure.py:257](../backend/app/parser/structure.py#L257)）：

某个章节抽取失败（模型两次都没给出合法 JSON）不算整体失败：其余章节照常可用，失败原因记在 `structure.extraction_errors` 里。

### 踩过的坑

- **右对齐的日期被当成右栏**：所以才有"两边都必须像一栏"的条件（每边 ≥3 行、字数 ≥12%）。
- **"标签：内容"列表**（如"缓存与分布式：熟练使用 Redis…"）：上一项恰好写满整行时，会被误判成折行。所以加了 `next_labeled_item` 条件。
- **表格还没处理**：带边框的表格会被当成分栏，按列读乱，而且页面被判成 sidebar、置信度 1.0。已记入计划，M8 前补。

### 答辩可能被问

- **两栏简历怎么保证阅读顺序？** 找贯穿的空白带（滑动窗口数被压住的行），用跨栏行把页面横切，每段先左后右，递归处理。
- **怎么保证模型不篡改简历？** 结构化时模型只回块编号，文字由代码从原文切片；之后模型给的任何引用都要经过 `locate_span` 核实（第 4 章）。
- **为什么要按"行"而不用 PyMuPDF 的块？** 它的块太粗，顺序也不可靠。

## 4. 防幻觉的核心：`locate_span`

涉及：[diagnose/evidence.py](../backend/app/diagnose/evidence.py)。它被诊断、JD 解析、匹配、结构化抽取（技能）四处共用。

### 要解决什么

模型说"这句话有问题：『负责系统的优化工作』"。这句话**真的在简历里吗**？如果是模型编的（幻觉），就不能展示给用户。

### 思路

拿模型引用的那句话去原文里找：
1. **先精确找**；
2. 找不到再**模糊找**（相似度 ≥ 90）——模型常把中文逗号写成英文逗号、把跨行的句子接成一行，这些只是格式差异，不算编造；
3. 先在提示的范围里找（比如送审的那条经历），找不到再扩大到全文；
4. **都找不到 = 编的，丢掉并计数**。论文里的"幻觉拦截率"就是这个计数除以模型给出的总条数。

### 代码逐段讲

**① 长度不变的归一化**（[evidence.py:27](../backend/app/diagnose/evidence.py#L27)）

```python
# 一对一的字符映射：全角 ASCII（！到～）→ 半角、中文标点 → 英文标点、各种空白 → 空格
_CHAR_MAP = {code: code - 0xFEE0 for code in range(0xFF01, 0xFF5F)}
_CHAR_MAP.update({ord(k): ord(v) for k, v in {"　": " ", "\n": " ", "。": ".", "、": ",", "“": '"', ……}.items()})
for _upper in range(ord("A"), ord("Z") + 1):          # 大写 → 小写（只处理 ASCII）
    _CHAR_MAP[_upper] = _upper + 32
    _CHAR_MAP[_upper + 0xFEE0] = _upper + 32          # 全角大写直接映射到半角小写

def normalize_for_match(s: str) -> str:
    out = s.translate(_CHAR_MAP)
    assert len(out) == len(s), "归一化必须保持长度不变"
    return out
```

关键在于**每个字符只换成另一个字符**，所以归一化后的文本和原文一样长、每个字的位置不变。在归一化文本上找到"第 100 到 120 个字"，这个区间可以直接用在原文上。和第 3 章的"掩码长度不变"是同一个思路。

> **〔语法〕`str.translate(table)`**：`table` 是 `{原字符的编码: 新字符的编码}` 的字典，一次遍历就完成全部替换，比链式 `.replace()` 快得多。全角字符 `！`（U+FF01）和半角 `!`（U+0021）的编码正好差 `0xFEE0`，所以一行字典推导式就能生成全部映射。

**② 查找**（[evidence.py:55](../backend/app/diagnose/evidence.py#L55)、[evidence.py:68](../backend/app/diagnose/evidence.py#L68)）

```python
def _search(quote: str, text: str, lo: int, hi: int) -> Span | None:
    window = text[lo:hi]
    at = window.find(quote)
    if at >= 0:
        return Span(lo + at, lo + at + len(quote), 1.0, "exact")            # 精确命中
    if len(quote) < MIN_FUZZY_LEN or len(quote) > len(window):
        return None                                                          # 太短的引用不做模糊匹配
    hit = fuzz.partial_ratio_alignment(quote, window)                        # 在 window 里找和 quote 最像的一段
    if hit is None or hit.score < settings.EVIDENCE_FUZZY_MIN:               # 相似度 < 90 → 不算
        return None
    return Span(lo + hit.dest_start, lo + hit.dest_end, round(hit.score / 100, 3), "fuzzy")

def locate_span(quote: str, text: str, hint: tuple[int, int] | None = None) -> Span | None:
    needle = normalize_for_match(quote.strip(_QUOTE_WRAPPERS))               # 去掉模型加的引号、省略号
    if len(needle) < MIN_QUOTE_LEN:
        return None
    haystack = normalize_for_match(text)
    if hint is not None:
        lo, hi = max(0, hint[0]), min(len(text), hint[1])
        found = _search(needle, haystack, lo, hi)                            # 先在提示范围里找
        if found:
            return found
    return _search(needle, haystack, 0, len(text))                           # 再全文找
```

`partial_ratio_alignment` 是 RapidFuzz 库的函数：在一段长文本里找"和短文本最像的那一段"，返回相似度（0–100）和那一段的起止位置。

**为什么太短的引用不做模糊匹配？** 2–5 个字的引用，在任何一段文字里都能找到"差不多像"的片段，模糊匹配没有意义，只做精确匹配。

**调用方怎么用**（诊断，[llm_review.py:57](../backend/app/diagnose/llm_review.py#L57)）：

```python
where = locate_span(item.evidence_quote, masked_text, hint=(unit.char_start, unit.char_end))
inside_unit = where is not None and unit.char_start <= where.start and where.end <= unit.char_end
if not inside_unit:        # 定位不到，或者定位到了别的经历里 —— 都不能作为这条经历的证据
    return Finding(**base, evidence_quote=item.evidence_quote, verify_result="failed", ……)
return Finding(**base, evidence_quote=full_text[where.start:where.end], char_start=where.start, ……)
```

注意最后一行：通过核实之后，**证据文字改用原文切片**，而不是模型给的那句。这样存下来、展示给用户的永远是简历原话。

### 答辩可能被问

- **为什么阈值是 90？** 是经验值：格式差异（标点全半角、换行变空格）只改动个别字符，相似度很高；整句改写或编造的相似度会明显更低。这个阈值还没有系统测过，要在 M8 用降质样本（故意改几个字、整句编造）画出拦截率随阈值的变化来定。
- **模糊匹配会不会放过编造？** 引用必须 ≥6 个字才做模糊匹配，并且要求 ≥90% 相似，编造的整句话很难做到；而且必须落在送审的那条经历里（`inside_unit`）。

## 5. 调模型的唯一出口：`LLMClient`

涉及：[llm/client.py](../backend/app/llm/client.py)、[cache/llm_cache.py](../backend/app/cache/llm_cache.py)、[cache/ratelimit.py](../backend/app/cache/ratelimit.py)、[llm/registry.py](../backend/app/llm/registry.py)、[llm/audit.py](../backend/app/llm/audit.py)

### 要解决什么

全项目有十几处要调模型。每一处都需要：同样的输入别重复付费（缓存）、别超过服务商的调用频率（限流）、记下花了多少钱（审计）。要是每处各写一遍，一定会有地方漏掉。

### 思路

所有调用只走一个函数（系统不变量④），固定五步：

```
① 渲染 prompt，算缓存 key  →  ② 缓存命中？命中就记一行审计、直接返回
→ ③ 限流占位  →  ④ 调模型，取 token 用量，按单价算成本  →  ⑤ 写缓存 + 写审计
```

### 代码逐段讲

**① 缓存 key 包含整段 prompt 的哈希**（[llm_cache.py:18](../backend/app/cache/llm_cache.py#L18)）

```python
def make_key(scene: str, model: str, prompt_version: str, rendered: str) -> str:
    digest = hashlib.sha256(rendered.encode("utf-8")).hexdigest()
    return f"llm:{scene}:{model}:{prompt_version}:{digest}"
```

`rendered` 是把消息列表、schema 名、temperature 序列化成的 JSON 字符串。同一段经历换了目标岗位，prompt 就变了，哈希也变了，不会命中旧答案。`prompt_version` 也在 key 里：**改了提示词就升版本号，旧缓存自动失效**。

**② 结构化输出：解析失败不抛异常**（[client.py:65](../backend/app/llm/client.py#L65)）

```python
def parse_json(text: str, schema: type[T]) -> tuple[T | None, str | None]:
    cleaned = _CODE_FENCE.sub("", text.strip())          # 去掉模型爱加的 ```json ``` 包裹
    if not cleaned:
        return None, "模型返回了空内容"
    try:
        return schema.model_validate(json.loads(cleaned)), None
    except json.JSONDecodeError as e:
        return None, f"不是合法的 JSON：{e.msg}（第 {e.lineno} 行）"
    except ValidationError as e:
        first = e.errors()[0]
        return None, f"字段不符合要求：{'.'.join(map(str, first['loc']))} {first['msg']}"
```

返回 `(对象, None)` 或 `(None, 错误原因)`。**错误原因是写给模型看的**：调用方会把它原样放进下一轮消息，让模型"带着原因重试"。例如 JD 解析（[jd_parser.py:43](../backend/app/matching/jd_parser.py#L43)）：

这比"失败就原样再问一次"有效得多：模型知道自己错在哪。诊断里"引用找不到"也走同一条重试路径（第 6 章）。

> **〔语法〕Pydantic**：`class _JdOut(BaseModel): requirements: list[_Requirement]` 声明了"期望的形状"，`model_validate(字典)` 会检查每个字段的类型、`Literal` 的取值范围、`Field(min_length=1)` 这类约束，不合格就抛 `ValidationError` 并说明是哪个字段。

**③ 限流：Redis 固定窗口计数**（[ratelimit.py:20](../backend/app/cache/ratelimit.py#L20)）

```python
def acquire(provider: str, limit_per_minute: int) -> None:
    deadline = time.monotonic() + MAX_WAIT_SECONDS
    while True:
        now = time.time()
        key = f"ratelimit:{provider}:{int(now // WINDOW_SECONDS)}"    # 每分钟一个桶，如 ratelimit:deepseek:29412345
        count = redis_client.incr(key)                                  # 原子加 1，返回加完之后的值
        if count == 1:
            redis_client.expire(key, WINDOW_SECONDS * 2)                # 第一次用这个桶时设过期
        if count <= limit_per_minute:
            return                                                      # 拿到名额
        if time.monotonic() > deadline:
            raise RateLimitTimeout(f"{provider} 限流等待超时")
        time.sleep(WINDOW_SECONDS - now % WINDOW_SECONDS + 0.05)        # 睡到下一分钟开始
```

诊断时十几条经历**同时**调模型，很容易超过服务商每分钟的上限，被拒后还要浪费重试。这里先占名额：Redis 的 `INCR` 是原子操作，多个线程同时加也不会算错。

**⑤ 流式版本 `stream()`**（[client.py:144](../backend/app/llm/client.py#L144)，给"具体建议"用）

```python
def stream(self, scene, messages, *, prompt_version, ref=None, model=None, temperature=0.0, use_cache=True) -> Iterator[str]:
    ……
    if cacheable and (hit := self._cache.get(key)) is not None:
        self._write_audit({…… "cache_hit": True ……})
        yield hit["text"]                  # 缓存命中：一次给出全文
        return
    self._acquire(……)
    text, usage, model_version = "", {}, None
    try:
        for chunk in self._chat_factory(model, temperature).stream(list(messages)):
            usage = chunk.usage_metadata or usage       # token 用量只在最后一个分块里
            piece = chunk.content if isinstance(chunk.content, str) else ""
            if piece:
                text += piece
                yield piece                             # ← 模型吐一段，就往外交一段
    except GeneratorExit:
        self._write_audit(failed("调用方提前结束了流式读取"))   # 用户关了页面：费用照样记
        raise
    except Exception as e:
        self._write_audit(failed(f"{type(e).__name__}: {e}"))
        raise LLMError(……) from e
    ……  # 正常结束：写缓存、记账（同 invoke）
```

> **〔语法〕生成器**：函数里出现 `yield`，调用它不会立刻执行，而是得到一个"生成器"。外面每 `for piece in client.stream(...)` 取一次，函数就往下跑到下一个 `yield`，交出一段后暂停。所以模型每吐几个字，调用方就能马上拿到，不用等全部生成完。
> **`GeneratorExit`**：调用方中途不要了（比如浏览器断开，生成器被关闭），Python 会在暂停的那个 `yield` 处抛出这个异常。它继承自 `BaseException`，`except Exception` 接不住，所以要单独写一个分支。

### 可替换的依赖：为什么构造函数有四个参数

```python
class LLMClient:
    def __init__(self, chat_factory=registry.get_chat_model, cache=llm_cache,
                 acquire=ratelimit.acquire, write_audit=audit.write_llm_call):
```

四样外部依赖都通过参数传入，有默认值。线上用默认值；测试时传入假的模型、假的缓存（一个字典）、假的限流和审计（一个列表），**不联网、不连 Redis、不连 MySQL** 也能测完整的五步逻辑。见第 11 章。

### 踩过的坑

- **DeepSeek 的 JSON 模式要求 prompt 里出现 "json" 这个词**，否则直接报错。所以 `invoke` 开头有检查，并且每个结构化 prompt 都给了 JSON 示例。
- **本机开着 HTTP 代理时**，访问国内模型服务走代理反而慢好几倍（实测 1 秒 vs 5 秒），所以 `registry` 里 `httpx.Client(trust_env=False)` 默认直连。
- **流式调用要打开 `stream_usage=True`**，否则流式时拿不到 token 用量，记账全是 0。

### 答辩可能被问

- **缓存会不会让评测结果失真？** 评测时设置批次号（`current_run_id`），有批次号就跳过缓存，每次都真实调用。
- **为什么不用 LangChain 的 `with_structured_output`？** 它也能做（配合 `include_raw=True` 可以拿到原始文本和解析错误），但我们还要在同一个地方做缓存、限流、记账，并且把错误原因整理成给模型看的中文提示去重试。自己用 JSON 模式 + Pydantic 校验包一层，这几件事都在 `client.py` 一个文件里，更好控制，也更好讲清楚。

## 6. 诊断：规则 + 模型 + LangGraph 并行

涉及：[diagnose/rules.py](../backend/app/diagnose/rules.py)、[diagnose/llm_review.py](../backend/app/diagnose/llm_review.py)、[diagnose/scorer.py](../backend/app/diagnose/scorer.py)、[graphs/diagnose_graph.py](../backend/app/graphs/diagnose_graph.py)、[graphs/state.py](../backend/app/graphs/state.py)、[services/diagnose_service.py](../backend/app/services/diagnose_service.py)

### 要解决什么

找出简历"写得不好"的地方，每一处都要能指到原文的具体位置，并且给出一个总分。

### 思路：确定的用规则，模糊的交给模型

| 用规则判（免费、稳定、零幻觉） | 交给模型判 |
|---|---|
| 这条描述里有没有数字 | 这句话是不是空话、有没有夸大 |
| 开头是不是"参与 / 协助"这类弱动词 | 职责边界清不清楚 |
| 技能栏写了、经历里没出现 | 前后逻辑通不通 |

规则先跑；规则的结论同时告诉模型"这些已经查过了，别重复报"。分数一律用公式算，**不让模型打分**——模型打分不稳定，也说不清为什么是这个分。

### 代码逐段讲

**① 规则用装饰器注册**（[rules.py:56](../backend/app/diagnose/rules.py#L56)）

```python
RULES: dict[str, Rule] = {}

def rule(code: str) -> Callable[[Rule], Rule]:
    def register(fn: Rule) -> Rule:
        RULES[code] = fn          # 把函数登记到字典里
        return fn                 # 原样返回，函数本身不变
    return register

@rule("NO_QUANTIFICATION")
def no_quantification(ctx: RuleContext) -> Iterable[Finding]:
    """说了"提升 / 降低"却没有任何数字。"""
    for u in ctx.experience_units:
        result = _RESULT_WORDS.search(u.text)
        if result and not _has_number(u.text):
            yield _finding(ctx, "NO_QUANTIFICATION", "quantification", "high", "成果缺少量化数据", ……,
                           u, _clause_around(u, result.start()))

def run_rules(ctx: RuleContext) -> list[Finding]:
    return [finding for fn in RULES.values() for finding in fn(ctx)]
```

> **〔语法〕带参数的装饰器**：`@rule("X")` 先执行 `rule("X")`，得到 `register` 函数；再用 `register` 去"装饰"下面的函数，也就是执行 `register(no_quantification)`。效果是：模块一被导入，7 条规则就自动登记进 `RULES`。**新增一条规则 = 新写一个函数、上面加一行 `@rule`，别处一行都不用改。**
> 每条规则都用 `yield` 产出问题，是个生成器，一条规则可以报 0 个或多个问题。

**"有没有数字"不能简单地找数字**（[rules.py:70](../backend/app/diagnose/rules.py#L70)）：

```python
_NUMBER = re.compile(r"(?<![A-Za-z\d.#+\-])\d+(?:\.\d+)?")     # 前面紧挨字母 / 数字 / . # + - 的不算
_LINE_PREFIX = re.compile(r"^(?:[•·▪■…]|\d{1,2}[.、)）](?!\d)|[（(]\d{1,2}[)）]|[①-⑩])?\s*")

def _has_number(text: str) -> bool:
    """有没有量化数字。行首的列表编号（"1." "（2）"）不算。"""
    return any(_NUMBER.search(line, _LINE_PREFIX.match(line).end()) for line in text.split("\n"))
```

- `(?<!…)` 是"反向否定预查"：数字前面不能紧挨着字母，所以 Vue3、JDK8、CET-6 里的数字不算量化；
- 行首的"1."是列表编号，也不算，所以从编号之后开始找（`search` 的第二个参数是起始位置）；
- 但"10.5%"里的点后面紧跟数字，它不是编号——`(?!\d)` 就是为了区分这两种情况。

**证据怎么来**：规则的证据区间都从原文切出来（`_clause_around` 找到包含关键词的那个分句），所以规则的 `verify_result` 恒为 `exact`，不需要再核实。

**② 模型审查：一条经历一次，带核实的重试循环**（[llm_review.py:76](../backend/app/diagnose/llm_review.py#L76)）

```python
for attempt in range(1, MAX_ATTEMPTS + 1):                       # 最多 3 次：首次 + 2 次重试
    result = llm.invoke("diagnose", messages, ……, schema=_ReviewOut, ……)
    if result.parsed is None:                                    # 格式不对
        review.schema_errors += 1
        feedback = prompts.DIAGNOSE_RETRY_SCHEMA.format(error=result.parse_error)
    else:
        failed_now = []
        for item in result.parsed.findings[:MAX_FINDINGS_PER_UNIT]:
            finding = _to_finding(item, unit, attempt, full_text, masked_text)    # 用 locate_span 核实引用
            if finding.verify_result == "failed":
                review.rejected.append(finding)
                failed_now.append(finding)
            elif not any(_same_problem(finding, kept) for kept in review.verified):  # 重试时可能重复报
                review.verified.append(finding)
        if not failed_now:
            break                                                # 全部核实通过，结束
        quotes = "\n".join(f"- {f.evidence_quote}" for f in failed_now)
        feedback = prompts.DIAGNOSE_RETRY_EVIDENCE.format(failed_quotes=quotes)   # "这几句在原文里找不到"
```

两种失败——格式不对、引用找不到——走**同一条重试路径**：把错在哪告诉模型，让它重来。被拦下的（`rejected`）不展示，但会存进数据库（`verify_result='failed'`），因为论文要统计拦截率：**首轮**（`attempt_no=1`）被拦下的条数 ÷ 首轮模型给出的总条数。

**③ LangGraph：每条经历一个并行分支**（[diagnose_graph.py](../backend/app/graphs/diagnose_graph.py)）

图的形状：

```
START → rule_scan → plan_review ─(Send × N)→ review_unit ─┐
                                 └─(没有要审的)────────────┴→ merge_findings → score → END
```

分发用 `Send`（[diagnose_graph.py:48](../backend/app/graphs/diagnose_graph.py#L48)）：

```python
def _dispatch(state: DiagnoseState) -> list[Send] | str:
    units = state["review_units"]
    if not units:
        return "merge_findings"                   # 条件边：返回节点名 = 走到那个节点
    ……
    return [Send("review_unit", ReviewUnitInput(unit=u, rule_summary=……, ……)) for u in units]   # 一条经历一个分支

graph.add_conditional_edges("plan_review", _dispatch, ["review_unit", "merge_findings"])
```

`Send(节点名, 载荷)` 的意思是"用这份载荷单独跑一次这个节点"。返回一个列表，LangGraph 就**同时**跑 N 个 `review_unit`。7 条经历并行审查，总耗时约等于最慢的那一条，而不是 7 条之和。

**N 个分支同时往 State 里写结果，怎么合并？** 靠 State 里声明的 reducer（[state.py:18](../backend/app/graphs/state.py#L18)）：

```python
class DiagnoseState(TypedDict, total=False):
    ……
    rule_findings: list[Finding]                        # 只有一个节点写，不需要 reducer
    llm_findings: Annotated[list[Finding], add]         # 多个分支同时写 → 用 add（列表相加）合并
    rejected_findings: Annotated[list[Finding], add]
    schema_errors: Annotated[int, add]                  # 整数也能 add：各分支的次数加起来
    cost: Annotated[float, add]
```

每个 `review_unit` 分支只返回自己的增量，比如 `{"llm_findings": [f1, f2], "cost": 0.002}`，LangGraph 用 `add`（也就是 `+`）把所有分支的结果合并起来。**没声明 reducer 的字段如果被多个并行分支同时写，LangGraph 会直接报错**——这是 LangGraph 并行最容易踩的坑。

> **〔语法〕`Annotated[类型, 附加信息]`**：给类型挂一个附加信息，Python 本身不管它；LangGraph 读出这个附加信息，当作合并函数用。`from operator import add` 就是 `+` 运算的函数版本。

**三种 mode 共用一张图**：`llm_only` 时 `rule_scan` 直接返回空；`rule_only` 时 `plan_review` 不选任何单元。图的形状不变，做消融实验切换的是参数，不是代码路径。

**成本预检**（[diagnose_graph.py:38](../backend/app/graphs/diagnose_graph.py#L38)）：分发之前按"每条经历预估花多少钱 × 重试余量 1.5"算一次最多能审几条，超出的截掉，诊断状态记为 `partial`。只在分发前算一次——分发出去的就让它跑完。

**④ 合并去重：规则优先**（[diagnose_graph.py:76](../backend/app/graphs/diagnose_graph.py#L76)）

规则和模型指向同一处（证据区间重叠超过较短者的一半）、而且属于同一维度时，只留规则那条：规则的结论是确定的。

**⑤ 评分公式**（[scorer.py:28](../backend/app/diagnose/scorer.py#L28)）

```python
PENALTY = {"high": 25, "medium": 12, "low": 5}
REFERENCE_UNITS = 4

scale = REFERENCE_UNITS / max(unit_count, REFERENCE_UNITS)       # 经历超过 4 条的按比例摊薄
for f in findings:
    if f.verify_result != "failed":
        deducted[f.category] += PENALTY[f.severity]
detail = {c: round(max(0.0, 100 - deducted[c] * scale), 1) if c in active else None for c in CATEGORIES}
overall = sum(WEIGHTS[c] * detail[c] for c in active) / total_weight   # 只对"本模式下有来源"的维度加权
```

两个细节：
- **按经历条数摊薄**：经历写得多，被检查的地方也多，直接累加扣分会让它天然吃亏（开发时遇到过一份 7 条经历的简历，"表达"维度被扣到 0 分）；
- **没人查的维度记 `None`，不记满分**：只开模型通道时，"量化"和"ATS"没有任何来源能查出问题，记 100 分就是把"没人查"当成"没问题"。

### 答辩可能被问

- **LangGraph 在这里起了什么作用？** 两处并行：每条经历并行审查（`Send`）；诊断和匹配两个子图并行（第 8 章）。并行分支的结果靠 reducer 合并。
- **规则和模型的结论冲突怎么办？** 同一处、同一维度的，只留规则的。
- **分数为什么不让模型打？** 不稳定、不可解释。公式每一分都能说清从哪扣的。

## 7. 匹配：规则先判，其余一次交给模型

**② 技能词典：一条正则扫全文**（[skill_dict.py:37](../backend/app/matching/skill_dict.py#L37)）

```python
    left = r"(?<![A-Za-z0-9])" if _is_ascii_word_char(word[0]) else ""    # 英文词左边不能紧挨字母数字
    right = r"(?![A-Za-z0-9])" if _is_ascii_word_char(word[-1]) else ""
    return left + re.escape(word) + right

def _compile(words: list[str], flags: int) -> re.Pattern | None:
    ordered = sorted(set(words), key=lambda w: (-len(w), w))              # 长的写法排前面
    return re.compile("|".join(_pattern(w) for w in ordered), flags)
```

三个细节，每个都对应一个真实会出错的例子：
- **长的排前面**：正则的 `|` 按顺序尝试，"微服务架构"要先于"微服务"、"C++"要先于"C"，否则只会匹配到短的；
- **英文词两侧加边界**：不然"Go"会命中"Google"，"Java"会命中"JavaScript"。没用 `\b` 是因为 `\b` 对中文不起作用；
- **两个字符以内的英文写法区分大小写**（C、Go、JS），其余不区分：否则普通英文单词"go"也会被当成 Go 语言。

### 为什么匹配不用 RAG

最初的设计是"每条要求先检索简历里最相关的几段，再让模型判"。设计阶段用一份真实简历 × 一份校招 JD 实测对比过（单份样本，只作设计依据，数据见 [06-workflows](06-workflows.md) 6.2）：

| 做法 | 模型调用 | 耗时 | 花费 |
|---|---|---|---|
| 全文一次判断 | 1 次 | 3.7 s | ¥0.018 |
| 逐条 RAG 判断 | 18 次 + 36 次向量 / 重排 | 5.1 s | ¥0.028 |

RAG 还多一种出错方式：检索没覆盖到的内容（学历、"技术栈"那一行）会被误判为缺失。RAG 解决的是"资料太多、塞不进 prompt"，而简历加 JD 只有两三千字。**知道什么时候不该用 RAG，本身就是一个能讲的点。**检索的代码（`retrieval/`）保留给模拟面试：用户贴的面经、公司介绍可能上万字，那里才真的需要。

- **同义词怎么处理（SpringBoot / Spring Boot）？** 同义词词典只负责"同一技能的不同写法"；上下位关系（Spring Boot 属于 Java 生态）交给模型判，因为手工建的技能树永远覆盖不全。
- **匹配度 60 分的线怎么来的？** 配置项 `SCREEN_THRESHOLD`，默认 60，是经验值，属于待评测的参数。

## 8. 投递流水线与进度推送

涉及：[api/apply.py](../backend/app/api/apply.py)、[services/apply_service.py](../backend/app/services/apply_service.py)、[graphs/apply_graph.py](../backend/app/graphs/apply_graph.py)、[cache/pubsub.py](../backend/app/cache/pubsub.py)、[api/task.py](../backend/app/api/task.py)、[nginx/default.conf](../nginx/default.conf)

### 要解决什么

用户点「投递」之后，要跑解析（如果还没解析完）、诊断、匹配、初筛，前后十几秒到几十秒。要做到：
1. 接口立刻返回，不让浏览器干等；
2. 页面上实时看到进度；
3. 进度推送出了问题（断线、漏消息），也一定能知道任务结束了。

### 整体时序

```
浏览器  POST /apply ──► 建两条 pending 记录（诊断、匹配），开后台任务，立刻返回 {id}
浏览器  GET /tasks/apply/{id}/stream（SSE，长连接）
后台    等简历解析完 → 跑图 A（诊断 ∥ 匹配 → 初筛）→ 每完成一个节点往 Redis 频道发一条 progress
SSE     订阅这个频道，收到 progress 就转发给浏览器；每秒查一次数据库，任务结束就发 done 并断开
浏览器  收到 done → GET /apply/{id} 拿结果
```

### 代码逐段讲

**① 图 A：两个子图并行**（[apply_graph.py:51](../backend/app/graphs/apply_graph.py#L51)）


**② 后台任务：边跑图边推进度**（[apply_service.py:93](../backend/app/services/apply_service.py#L93)）

**③ MySQL"可重复读"的坑**（[apply_service.py:79](../backend/app/services/apply_service.py#L79)）

用户可能刚上传完就点投递，这时简历还在解析，要等它：

```python
def _wait_until_parsed(db: Session, resume: Resume) -> None:
    deadline = time.monotonic() + PARSE_WAIT_SECONDS
    while resume.parse_status in ("pending", "parsing"):
        if time.monotonic() > deadline:
            raise TimeoutError("等待简历解析超时")
        time.sleep(0.5)
        db.commit()           # ← 先结束当前事务
        db.refresh(resume)    # ← 再重新读
```

如果只写 `db.refresh(resume)`，会**一直读到 `parsing`**，死等到超时（CLAUDE.md 的"踩过的坑"里记着这一条）。原因：MySQL 默认的隔离级别是"可重复读"（REPEATABLE READ），同一个事务里不管读多少次，看到的都是事务开始那一刻的快照；解析任务在另一个会话里提交的新状态，这个事务看不见。先 `commit()` 结束旧事务，下一次读才会开新事务、看到最新数据。

**④ Redis 发布 / 订阅**（[pubsub.py:24](../backend/app/cache/pubsub.py#L24)）

后台任务发布到频道 `task:apply:17`，SSE 接口订阅同一个频道。为什么需要 Redis 在中间？后台任务和 SSE 接口是两段各自独立运行的代码，Redis 的发布订阅是它们之间的"广播喇叭"。

**⑤ SSE 接口：以数据库为准**（[task.py:76](../backend/app/api/task.py#L76)）

```python
def _events(kind, task_ref, session_factory, subscribe) -> Iterator[str]:
    subscription = subscribe(f"{kind}:{task_ref}")
    started = last_sent = time.monotonic()
    try:
        while time.monotonic() - started < MAX_STREAM_SECONDS:            # 最长 10 分钟
            status = _status(session_factory, kind, task_ref)             # ① 每轮先查数据库
            if status not in _IN_PROGRESS:
                failed = status in ("failed", None)
                yield sse_event("error" if failed else "done", {"kind": kind, "id": task_ref, "status": status})
                return                                                    #    结束了就发 done / error 并断开
            message = subscription.get(timeout=POLL_SECONDS)              # ② 最多等 1 秒频道消息
            if message and message.get("event") == "progress":
                yield sse_event("progress", message["data"])              #    有进度就转发
                last_sent = time.monotonic()
            elif time.monotonic() - last_sent > HEARTBEAT_SECONDS:
                yield ": keep-alive\n\n"                                   # ③ 15 秒没动静发一行注释当心跳
                last_sent = time.monotonic()
        yield sse_event("error", {"kind": kind, "id": task_ref, "status": "timeout"})
    finally:
        subscription.close()

def sse_event(event: str, data: dict) -> str:
    return f"event: {event}\ndata: {json.dumps(data, ensure_ascii=False)}\n\n"   # SSE 的文本格式
```

**为什么"结束"要看数据库，而不信 Redis 的 done 消息？** 发布订阅是"发了就忘"：浏览器连上来之前发的消息、网络抖动时发的消息，都会丢。如果只等 Redis 的 done，一旦错过就永远等下去。每秒查一次数据库，不管什么时候连上来、中间漏了多少消息，**任务一结束就一定能收到 done**。Redis 只负责"中间过程"这种丢了也无所谓的信息。

**心跳**：很多代理（包括 Nginx）会把一段时间没有数据的连接掐掉。SSE 规定以 `:` 开头的行是注释，浏览器会忽略，正好用来当心跳。

**Nginx 要关掉缓冲**：Nginx 默认会把后端的响应攒一攒再发给浏览器，SSE 就变成"攒够了一次性到"，进度条不动。`default.conf` 里 `proxy_buffering off`，后端响应头也带 `X-Accel-Buffering: no`；`gzip_types` 里也故意不包含 `text/event-stream`，压缩同样会缓冲。

**⑥ "哪里不符合"在读取时组装**（[apply_service.py:124](../backend/app/services/apply_service.py#L124)）


### 答辩可能被问

- **为什么用 SSE 不用 WebSocket？** 进度只需要服务端往浏览器推，单向；SSE 就是普通的 HTTP 长连接，Nginx 配置简单，断线重连、心跳都好处理。
- **进度消息丢了怎么办？** 结束信号以数据库为准，丢的只是中间进度；前端还有兜底：30 秒没数据就改成每 3 秒轮询一次（第 10 章）。

## 9. 具体建议：提示词、流式接口、数字复检

涉及：[rewrite/advice.py](../backend/app/rewrite/advice.py)、[services/advice_service.py](../backend/app/services/advice_service.py)、[api/advice.py](../backend/app/api/advice.py)、[llm/prompts.py](../backend/app/llm/prompts.py) 的 `ADVICE_*`；调提示词的过程见 [具体建议-提示词草稿](design/具体建议-提示词草稿.md)

### 要解决什么

原来结果页上"怎么改"是规则的固定模板，同一种问题下面永远是同一句话（你当时说"说的有点太泛了"）。要改成针对**这一句**、**这条要求**的具体建议，篇幅不长不短。

### 思路

1. **点开时才生成**：只为用户真正看的条目付费；生成过的存库，下次直接用。
2. **流式显示**：一个字一个字出来，1 秒左右就能看到第一个字，不用盯着转圈。
3. **不能让模型编**：改写里原文没有的内容一律用【】留给用户填；生成完再用代码复检一遍数字。

### 提示词是怎么调出来的

不是一次写好的。拿一次真实投递（虚构简历）的数据，直接调 DeepSeek 看输出，发现问题就改：

| 版本 | 发现的问题 | 怎么改 |
|---|---|---|
| 第一版 | 偏长（146–257 字）；改写时加了原文没有的做法（"保证回调幂等"）；技能类问题改错了地方 | 每段限定字数；"原文没有的内容一律用【】留空"；技能问题要说明"在某段经历里写" |
| 第二版 | 把"参与了数据库设计"直接改成"负责……"，替用户升级了职责 | 加一条：参与 / 负责 / 主导这类词不替用户改，写成【负责 / 参与，按实际】 |
| 第三版 | 问题类 78–125 字，差距类 139–231 字，首字 0.5–1.1 秒 | 定稿 |

**调提示词的方法**：拿真实数据跑，逐条读输出，把每个问题翻译成一条具体规则写进提示词，而不是凭空写一堆"请具体一点"。

### 代码逐段讲

**② 数字复检**（[advice.py:92](../backend/app/rewrite/advice.py#L92)）

```python
def fix_numbers(text: str, section: str, original: str) -> tuple[str, int]:
    allowed = set(_NUMBER.findall(original))            # 原文（这段经历）里出现过的数字
    parts = _SECTION.split(text)                         # 按【段标题】切开：[开头, 段名, 内容, 段名, 内容, ...]
    replaced = 0

    def fix(m: re.Match) -> str:
        nonlocal replaced
        if m.group(0) in allowed:
            return m.group(0)                            # 原文里有的数字照留
        replaced += 1
        return PLACEHOLDER                               # 编出来的换成【数值】

    for i in range(1, len(parts), 2):
        if parts[i] == section:                          # 只查【改成】（或【怎么补】）这一段
            pieces = _BRACKETED.split(parts[i + 1])      # 再按【…】切开，占位里的内容不动
            parts[i + 1] = "".join(p if p.startswith("【") else _NUMBER.sub(fix, p) for p in pieces)
    ……
```

> **〔语法〕`re.split` 带括号的正则**：模式里有捕获组 `(…)` 时，切出来的列表会把分隔符本身也保留下来。所以 `_SECTION.split("【问题】A【改成】B")` 得到 `['', '问题', 'A', '改成', 'B']`，奇数位置是段名、偶数位置是内容，最后还能原样拼回去。
> **`nonlocal`**：内层函数要修改外层函数的变量（这里是计数器 `replaced`），必须先声明 `nonlocal`，否则 Python 会把它当成内层函数自己的新变量。

**为什么是"事后复检"而不是"发现违规就让模型重写"？** 流式输出已经显示在屏幕上的字撤不回来。所以边生成边显示原文，生成完复检一次，以**复检后的全文**为准存库，并在结束事件里下发给前端**整段替换**。

**③ 服务层：要么直接给存好的，要么给一个"待生成任务"**（[advice_service.py:50](../backend/app/services/advice_service.py#L50)）

```python
def run(task: AdviceTask, llm: LLMClient, session_factory: SessionFactory) -> Iterator[Event]:

            text += piece

        return                                             # 失败什么都不存，前端可以重试

    result = {"text": final, "violation_count": violations, ……}
    with session_factory() as db:                          # 开新会话存库（请求的会话在流式开始后就不能用了）
        task.save(db, result)
        db.commit()
    yield "done", result
```

**④ 接口：生成器直接变成流式响应**（[api/advice.py:53](../backend/app/api/advice.py#L53)）

### 答辩可能被问

- **建议是模型写的，怎么保证不胡说？** 三层：提示词明确禁止编造（原文没有的用【】留空、不升级职责、"如果你做过……"的条件写法）；代码复检改写里的数字；而且建议只是建议，【】需要用户自己按实际填。

为什么不是"当前是第几步就只渲染那一步"？因为那样切走的那一步组件会被**卸载**，里面的状态（贴了一半的 JD、上传中的进度、已解析出的要求）全都丢了，从第 ② 步点"换个岗位"回来就得重新贴。三步都渲染着、只用 `hidden` 藏起来，状态一直都在。

顺带的好处：进场动画是 CSS 写的（`.fade` 类），元素从 `display: none` 变成可见时，浏览器会**重新播放**动画，所以每次切换都有进场效果，不用写 JS。

> **〔语法〕React 开发模式下 effect 会跑两次**：`main.tsx` 里包了 `<StrictMode>`，开发时每个 `useEffect` 会"执行 → 清理 → 再执行"一遍，用来暴露忘写清理函数的 bug。所以异步请求的 effect 都带一个 `cancelled` 标记，清理时置为 true，旧请求回来发现被取消了就什么都不做。上线构建不会跑两次。

### 10.3 跟踪投递进度：fetch 读 SSE、断了改轮询、只进不退

**① 为什么不用浏览器自带的 `EventSource`？** 它不能设置请求头，没法带登录令牌；也不能发 POST（具体建议接口是 POST）。所以用 `fetch` 拿到响应体的**字节流**，自己按 SSE 格式切（[client.ts:105](../frontend/src/api/client.ts#L105)）：

```ts
export async function* sseEvents(stream: ReadableStream<Uint8Array>, onChunk?: () => void): AsyncGenerator<SseEvent> {
  const reader = stream.getReader()
  const decoder = new TextDecoder()
  let buffer = ''
  for (;;) {
    const { value, done } = await reader.read()        // 等下一块字节到来
    if (done) return
    onChunk?.()                                        // 有数据来了（哪怕只是心跳），用来重置"多久没动静"的计时
    buffer += decoder.decode(value, { stream: true })  // stream: true —— 一个汉字的字节可能被拆在两块里
    let cut: number
    while ((cut = buffer.indexOf('\n\n')) >= 0) {      // SSE 用空行分隔事件
      const event = parseEvent(buffer.slice(0, cut))
      buffer = buffer.slice(cut + 2)
      if (event) yield event                           // 心跳注释行解析出来是 null，跳过
    }
  }
}
```

> **〔语法〕异步生成器 `async function*`**：和 Python 的生成器一样用 `yield` 一个个交出结果，只不过中间可以 `await`。使用方写 `for await (const event of sseEvents(stream)) { … }`，每收到一个事件循环体跑一次。
> **`decode(value, { stream: true })`**：UTF-8 里一个汉字占 3 个字节，网络分块时可能正好从中间切开；`stream: true` 让解码器把不完整的字节留着，等下一块来了再拼，不会出现乱码。

**② 断线、超时就改成轮询**（[apply.ts:86](../frontend/src/api/apply.ts#L86)、[apply.ts:97](../frontend/src/api/apply.ts#L97)）

```ts
export async function watchApply(id, onStage, signal): Promise<string> {
  try {
    const status = await streamApply(id, onStage, signal)   // 先试 SSE
    if (status) return status
  } catch (e) {
    if (signal.aborted) throw e                            // 是组件卸载主动断开的：不再继续
  }
  return pollApply(id, onStage, signal)                    // SSE 连不上 / 断了 / 30 秒没数据：每 3 秒轮询
}
```

`streamApply` 里有一个 30 秒的计时器，每收到数据（包括心跳）就重置；30 秒都没动静就调用 `ctrl.abort()` 主动断开，抛出的异常被上面接住，转去轮询。

> **〔语法〕`AbortController`**：`const ctrl = new AbortController()`，把 `ctrl.signal` 传给 `fetch`，之后任何时候调用 `ctrl.abort()`，这个请求就会立刻中断并抛出 `AbortError`。这里有两层：外层的 `signal` 在"组件卸载"时触发，内层的 `ctrl` 在"超时"时触发，外层触发时顺带触发内层。

**③ 进度只进不退**（[components/Pipeline.tsx:25](../frontend/src/components/Pipeline.tsx#L25)）

### 10.4 原文高亮：按字符区间切段

（[components/ResumeSheet.tsx:37](../frontend/src/components/ResumeSheet.tsx#L37)）

**问题**：一段文字可能同时属于好几条标注。比如"参与了数据库设计，对系统性能进行了优化，响应速度明显提升"，整句是"部分满足"的依据（橙），其中"参与了数据库设计"又是一个问题（红），"响应速度明显提升"是另一个问题（红）。简单地"给每条标注包一个 `<span>`"会出现交叉嵌套，HTML 表达不了。

**做法**：把所有标注的起点和终点都当成"切口"，把原文切成很多小段；每一小段看它被哪几条标注覆盖，颜色取最严重的那条：

用上面那句话举例：三条标注的切口把它切成 `[参与了数据库设计][，对系统性能进行了优化，][响应速度明显提升][。]`，每一段各自知道自己属于哪几条（`keys`）。点其中一段，就在这几条里挑一条聚焦（优先当前列表里的，其次按严重程度）。

"两个区间有没有交集"的判断 `a.start < b.end && a.end > b.start` 在前后端都出现了很多次，值得记住：**开区间 [start, end) 的两段相交，当且仅当各自的起点都在对方终点之前。**

### 10.5 流式建议：一条只生成一次，列表和纸面共享

（[store/advice.ts](../frontend/src/store/advice.ts)、[components/AdviceBlock.tsx](../frontend/src/components/AdviceBlock.tsx)）

同一条建议可能同时显示在两个地方：列表里展开着，纸面上也聚焦着它。如果每个组件各自发请求，就会生成两次、付两次钱，两边的进度也不一样。所以把生成进度放进一个全局 store，按 key（如 `finding:128`）存：

```ts
export function ensureAdvice(key: string, path: string, cached?: Advice | null) {
  const current = useAdviceStore.getState().entries[key]
  if (current && current.status !== 'error') return            // 已有结果或正在生成：什么都不做
  if (cached?.text) return put(key, { status: 'done', text: cached.text })   // 接口里已经带回来了（以前生成过）

  put(key, { status: 'loading', text: '' })
  let text = ''
  streamAdvice(path, (delta) => {
    text += delta
    put(key, { status: 'streaming', text })                    // 每来一段就更新一次，订阅它的组件跟着重新渲染
  })
    .then((advice) => put(key, { status: 'done', text: advice.text }))   // 以复检后的全文为准，整段替换
    .catch((err) => put(key, { status: 'error', text, error: …… }))
}
```

组件这边只管订阅和"需要时调用 `ensureAdvice`"：

```tsx
const entry = useAdviceStore((s) => s.entries[source.key])
useEffect(() => { ensureAdvice(source.key, source.path, source.cached) }, [source.key])
```

**什么时候算"需要"？** 组件挂载的时候。所以列表项 `IssueItem` 里，建议块要**等用户第一次点开这一条才挂载**（`{opened && children}`），不然结果页一打开，十几条建议就全部开始生成了。

**边生成边解析段落**：流到一半时，文字末尾可能是半个段标题（比如"【改"），直接显示会闪一下。显示前先用正则 `/【[^】]{0,5}$/` 把末尾没写完的标题去掉。【】占位的高亮用一个小的括号计数器处理嵌套（"【结果，如平均响应【数值】ms】"只包最外层）。

### 10.6 几种动效是怎么做的

（[components/effects.tsx](../frontend/src/components/effects.tsx)）

- **鼠标跟随光晕**：`requestAnimationFrame` 每帧把光晕位置往鼠标位置挪 8%（`gx += (mx - gx) * 0.08`），于是有"缓缓跟过来"的感觉。这种写法叫线性插值（lerp）。
- **磁吸按钮**：鼠标在按钮上移动时，按钮往鼠标方向偏移 22%–30% 的距离，离开时复位；CSS 里 `transition` 用了一条带回弹的缓动曲线，所以复位时会弹一下。
- **卡片倾斜**：鼠标在卡片上的相对位置换算成 ±2.5° 的 `rotateX / rotateY`，外层加 `perspective` 才有立体感。
- **滚动出现**：`IntersectionObserver` 监听元素进入视口（露出 20%），进来时加一个 class，由 CSS 过渡完成动画；只触发一次就停止监听。
- 所有动效都检查了系统的"减少动态效果"设置（`prefers-reduced-motion`），开了就不动。

### 踩过的坑

- **Tailwind 自带的类名冲突**：自定义了一个 `.collapse` 类，结果 Tailwind 也有同名的工具类（`visibility: collapse`），元素直接消失了，后来改名 `.expand`。同理还避开了 `hidden`、`block`、`ring`（Tailwind 的 ring 会加一圈阴影）。
- **和首页演示卡的全局类名冲突**：结果页的批注想用 `.note`，但首页演示卡已经有一个全局的 `.note`（绝对定位、透明度 0），所以改名 `.paper-note`。
- **TypeScript 类型对不上 `TextDecoderStream`**：最后改成手动 `TextDecoder` 解码，效果一样。

### 答辩可能被问

- **前端怎么保证和后端的数据结构一致？** `api/*.ts` 里的类型是照着后端 `schemas.py` 一个字段一个字段写的，注释里写明对应哪个类；改后端结构时要同步改这里（本项目没有做自动生成）。
- **高亮位置为什么不会错位？** 前后端用同一套字符偏移；后端在抽取文本时就把 emoji 等"JS 里算两个长度"的字符替换掉了（第 3.2 节），两边数出来的字数一致。

## 11. 测试怎么写

涉及：[backend/tests/conftest.py](../backend/tests/conftest.py) 和各个 `test_*.py`。运行：在 `backend/` 下 `.\.venv\Scripts\python.exe -m pytest -q`，283 个用例，大约 45 秒，**不联网、不需要 MySQL 和 Redis**。

### 要解决什么

这个项目依赖一堆外部东西：DeepSeek、硅基流动、MySQL、Redis、真实的 PDF。如果测试也依赖它们，就会又慢、又花钱、结果还不稳定（模型每次回答不一样）。

**② SQLite 内存库代替 MySQL**（[conftest.py:61](../backend/tests/conftest.py#L61)）

```python
engine = create_engine("sqlite://", connect_args={"check_same_thread": False}, poolclass=StaticPool)
Base.metadata.create_all(engine)
```

- `sqlite://` 后面什么都不写 = 内存数据库，测试结束就没了，每个测试都是一个干净的库；
- `StaticPool`：所有连接共用同一个连接，否则每开一个新连接就是一个新的空内存库；
- 模型定义里有几处是为 SQLite 准备的，比如主键 `BigInteger().with_variant(Integer(), "sqlite")`——SQLite 只有 `INTEGER` 主键才会自增。

**③ 依赖覆盖：把接口里用到的外部服务换成假的**（[conftest.py:114](../backend/tests/conftest.py#L114)）

```python
app.dependency_overrides[get_db] = override_get_db                         # 数据库 → SQLite
app.dependency_overrides[get_session_factory] = lambda: db_session_factory  # 后台任务也用测试库
app.dependency_overrides[get_llm_client] = lambda: fake_llm                 # 模型 → 假模型
app.dependency_overrides[get_publisher] = lambda: lambda *_: None           # 进度推送 → 直接丢掉
yield TestClient(app)          # 不写 with：不触发启动时的 MySQL / Redis 检查
```

这就是第 1 章"用 `Depends` 取依赖"的回报：FastAPI 提供了 `dependency_overrides`，测试时替换掉，业务代码一行都不用改。
另一个方便之处：`TestClient` 会在响应返回后**同步地**把后台任务跑完，所以测试里 `POST /apply` 一返回，诊断和匹配就已经跑完了，可以直接查结果。

想测"模型编造了引用"，就让假模型回一句简历里没有的话；想测"模型挂了"，就把回复设成一个异常对象——各种坏情况都能精确地造出来，这是调真实模型做不到的。

### 测的是什么（按重要性）

- **坐标契约**：`full_text[b.char_start:b.char_end] == b.text` 对每一块都成立（`test_layout.py`）。
- **反幻觉**：编造的引用被拦下、拦下后带原因重试、重试成功后正确落库、首轮拦截数统计正确（`test_evidence.py`、`test_diagnose_graph.py`）。
- **隐私**：发给模型的文本里没有姓名、电话（`test_pii_masked_text_is_what_the_model_sees` 等）。
- **越权**：别人的简历、投递、问题一律 404（各个 `test_*_api.py` 里的 `test_rejections`）。
- **失败路径**：模型超时、输出不是 JSON、中途断掉，都要落成明确的失败状态，不能卡在"进行中"。

### 答辩可能被问

- **测试不调真模型，怎么知道真模型行不行？** 单元测试管"我们自己的逻辑对不对"；真模型的效果靠 M8 评测（标注集 + 指标），以及开发时连真实后端的端到端试跑。两者分开。

### B. 答辩高频问题速查

| 问题 | 一句话回答 | 章节 |
|---|---|---|
| 系统怎么防止大模型胡编？ | 模型的每条结论都要逐字引用原文，经 `locate_span` 定位，找不到就丢弃并计数；结构化时模型只回块编号；改写里的数字由代码复检 | 3.7、4、9 |
| 幻觉拦截率怎么算？ | 首轮被拦下的条数 ÷ 首轮模型给出的总条数，数据落在 `diagnoses.hallucination_count` | 6 |
| 两栏简历怎么排阅读顺序？ | 滑动窗口找被压住行数最少的竖向空白带，跨栏行横切，递归先左后右 | 3.3 |
| 为什么匹配不用 RAG？ | 简历 + JD 只有两三千字，全文一次判断更快更便宜，也不会因为检索漏掉而误判；有实测对比 | 7 |
| LangGraph 用在哪、起什么作用？ | 诊断里每条经历并行审查（`Send`）、诊断与匹配两个子图并行；结果靠 reducer 合并 | 6、8 |
| 分数怎么算？为什么不让模型打分？ | 各维度从 100 扣分再加权，匹配按要求权重加权；模型打分不稳定、说不清原因 | 6、7 |
| 个人信息怎么保护？ | 姓名电话等本地抽取、永不外发；发给模型的文本做长度不变的掩码 | 3.6 |
| 怎么控制成本？ | 规则先判不花钱；结果缓存 7 天；诊断前做成本预检；建议点开才生成；每次调用都记账 | 5、6、9 |
