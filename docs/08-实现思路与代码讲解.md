## 1. 整体骨架与登录（通用部分，简要）

涉及：[main.py](../backend/app/main.py)、[deps.py](../backend/app/deps.py)、[errors.py](../backend/app/errors.py)、[security.py](../backend/app/security.py)、[api/auth.py](../backend/app/api/auth.py)

这部分是普通 Web 后端的做法，知道个大概就行：

- **分三层**：`api/` 接请求（很薄）→ `services/` 编排流程、读写数据库 → 领域层（`parser/ diagnose/ matching/ graphs/ rewrite/`）只做计算，不碰数据库。领域层不碰数据库，所以能单独测、单独拿去做实验。
- **依赖注入**：接口参数写 `user: User = Depends(get_current_user)`，FastAPI 会在进接口前先认证。依赖可以叠：`get_current_user`（登录了）→ `get_owned_resume`（简历是你的）→ `get_parsed_resume`（且已解析完）。
- **别人的数据一律 404**，而不是 403：403 等于承认"这个 id 存在"，别人就能挨个试 id 探测。
- **统一错误**：业务代码只 `raise ApiError(40401, "…")`；错误码前三位就是 HTTP 状态码，`code // 100` 一行换算。
- **后台任务**：上传、投递都立刻返回，活交给 `BackgroundTasks` 在同一进程里接着跑。后台任务要自己开数据库会话（请求的会话在响应后已关闭）。
- **全用同步写法**（`def` 不是 `async def`）：FastAPI 会把 `def` 接口放进线程池；PyMuPDF、SQLAlchemy、LangGraph 的 `invoke` 都是同步 API；单人毕设不值得引入整套异步驱动。
- **登录**：bcrypt 存密码（带盐、故意慢），登录发 JWT（内容只是 base64，谁都能解开看，所以只放 `user_id`；签名防篡改）。

两个值得讲的细节：

```python
# 用户名不存在时也验一次假哈希（security.py / api/auth.py:46 的 login）
password_ok = verify_password(body.password, user.password_hash if user else dummy_hash())
```

bcrypt 一次约 0.4 秒。如果用户不存在就立刻返回，攻击者看响应快慢就知道用户名存不存在（**时序攻击**）。验一次假哈希，两种情况耗时一样。

```python
# 注册判重靠数据库唯一约束（api/auth.py:34 的 register）
try:
    db.commit()
except IntegrityError:
    raise ApiError(CONFLICT, "用户名或邮箱已被注册")
```

"先查有没有、没有再插"在并发时会两个请求都查到"没有"、都插进去；交给 UNIQUE 约束判，天然没有竞争。

**修改密码**（`api/auth.py` 的 `change_password`，10-09 加的）：先用 `verify_password` 核对当前密码，再存新的哈希。两个小决定：

- **当前密码不对返回 40001，不是 40101**：前端约定"任何接口返回 401 = 登录失效"，会直接退出登录；输错一次旧密码就被踢出去，体验很差。
- **别的设备不会被立刻踢下线**：JWT 是无状态的，发出去就只能等它过期（24 小时）。要立刻作废，得在用户表记"改密码的时间"，校验令牌时拒绝更早签发的——要改表结构，毕设范围内没做，写进 05 5.8 未来工作。

### 踩过的坑

- **必须单进程运行**（`--workers 1`）：启动时会把库里还在排队或进行中（pending / running）的任务标成失败，前提是"启动那一刻没跑完的一定是上次进程留下的死任务"。多进程会误杀别的进程正在跑的任务。
- **表结构不由代码自动建**：`schema.sql` 由 `models.py` 生成、手动执行，测试检查两者一致。建表语句可以直接放进论文附录。

## 2. 解析简历：从 PDF 到"坐标系"

涉及：[parse_service.py](../backend/app/services/parse_service.py)、`parser/` 下的 [extract.py](../backend/app/parser/extract.py) → [layout.py](../backend/app/parser/layout.py) → [section.py](../backend/app/parser/section.py) → [pii.py](../backend/app/parser/pii.py) → [structure.py](../backend/app/parser/structure.py)

### 要解决什么

把 PDF 变成：
1. **`full_text`**：按正确阅读顺序拼成的全文（两栏简历直接从上往下读，左右两栏会交错在一起）；
2. **块**：全文切成的一段段，每段记下在 `full_text` 里的区间 `[char_start, char_end)`；
3. **结构化结果**：教育、经历、项目、技能……每条都记着对应哪段区间。

之后诊断、匹配、高亮全靠这套"第几个字到第几个字"的**坐标系**，所以它定下来就永远不改（系统不变量①②）。

### 流程（[parse_service.py:31](../backend/app/services/parse_service.py#L31) `parse_resume`）

```python
extracted = extract_pdf(path)                 # ① 抽出每一行：文字、坐标、字号、是否加粗
layout = analyze_layout(extracted)            # ② 排阅读顺序、切块、定坐标系
sections = detect_sections(layout)            # ③ 认出章节
basics = extract_basics(layout, sections)     # ④ 本地抽姓名电话（不发给模型）
sections = classify_sections(……, llm, ……).sections   # ⑤ 词典认不出的候选标题交模型归类（2.4）
structured = extract_structure(……, llm, ……)   # ⑥ 让模型把章节拆成一条条
```

每一步是纯函数；任何一步（包括最后写库）抛异常都会被接住，落成 `parse_status='failed'` 并记下原因——后台任务绝不能把异常"抛丢"，否则记录永远停在"解析中"。

### 2.1 按"行"抽取，并保证前后端数的字数一样

（[extract.py:101](../backend/app/parser/extract.py#L101) `clean_text`）

PyMuPDF 自带的"块"太粗、顺序也不可靠，所以只取"行"，顺序和分块自己做。

```python
_NON_BMP = re.compile(r"[\U00010000-\U0010FFFF]")    # emoji 等
s = _NON_BMP.sub(_REPLACEMENT, s)                     # 换成 "�"
```

为什么换掉 emoji：`"😀"` 在 Python 里长度是 1，在 JavaScript 里是 2。后端说"高亮第 10–20 个字"，前端遇到 emoji 就整体错位。换成两边都算 1 的字符，坐标就一致了。

扫描件的判定很简单：能抽出的字符少于 100 个，就是图片型 PDF。

### 2.2 分栏算法（全项目最难的部分）

（[layout.py:181](../backend/app/parser/layout.py#L181) `_best_band`、[layout.py:411](../backend/app/parser/layout.py#L411) `_order`）

**核心直觉**：两栏简历中间有一条从上到下贯穿的空白带，找到它，左边读完再读右边。难点是页顶的姓名、通栏的章节标题会"压"在这条空白带上。

**找空白带：滑动窗口数"压住它的行"**

```python
while a + width <= right_end:                 # 3% 页宽的竖条从左扫到右，每次挪 2pt
    left = [l for l in lines if l.x1 <= a]    # 整行在竖条左边
    right = [l for l in lines if l.x0 >= b]   # 整行在竖条右边
    if 两边都至少 3 行 且 两边字数都 ≥ 12%:
        blocked = {横跨这个竖条的行}
        key = (len(blocked), 两边字数差)      # 压住的行越少越好，其次两边越均衡越好
……
clearness = 1 - len(blocked) / n              # c：空白带有多干净，1 = 完全干净
```

"两边都要像一栏"这个条件很关键：没有它，单栏简历里"项目名 ………… 2023.09–2024.01"这种右对齐的日期，会被当成一个很窄的右栏。

**递归切分（递归 XY 切分的变体）**

```python
if band and band.clearness >= 0.8:              # 确定是分栏
    spanning = band.blocked | 页顶的通栏行
    if spanning:
        return _split_by_spanning_rows(……)       # 有跨栏行：按跨栏行横切成几段，每段再处理
    return _split_columns(……)                   # 没有：左右切开，先左后右
segments = _y_segments(lines)                   # 竖着切不了：在大的水平留白处横切，每段再试一次
……
return _place_rows(lines, ……)                   # 都切不动：叶子，按 y、x 排好
```

跨栏行的处理用图来理解：

```
姓名（跨栏）               → 单独一段
┌ 左栏 A ┐  ┌ 右栏 A ┐     → 递归：先左后右
项目经历（通栏标题）       → 单独一段
┌ 左栏 B ┐  ┌ 右栏 B ┐     → 递归：先左后右
```

整页定性：表格的字占 ≥70% → `table`；说不清（0.3 < c < 0.8）的行占 ≥30% → `unknown`；分栏的行占 ≥30% → 空白带在页面中间为 `double`、偏一边为 `sidebar`；否则 `single`。

**时间轴：一列日期不是一栏**

（[layout.py:224](../backend/app/parser/layout.py#L224) `_is_date_column`）

很多简历把经历的日期单独放在左边一列，和右边的标题在同一行。中间也有一条干净的空白带，算法会当成两栏：先读完所有日期，再读所有经历，日期和经历全对不上——而且自报置信度 1.0。

先想到的是看"左右两边的行对不对齐"，实测不行：正常的两栏行距一样，左右也常常对得很齐（合成集最高 0.94）。真正的特点是**内容**：较少的那一边过半是日期，而且这些日期都和另一边某一行在同一水平线上。

```python
dates = [s for s in small if _is_date_line(s.text)]                 # 这一行主要就是个日期（「2022 年 优秀学生干部」不算）
aligned = [s for s in dates if any(same_row(s, o) for o in other)]  # 和另一边同一行
return len(dates) >= 0.5 * len(small) and len(aligned) >= 0.8 * len(dates)
```

满足就不切，按行读，日期和同一行的标题合成一行。"过半"而不是"全是"，是因为日期列里还夹着「教育背景」这类短标题。

**为什么不做大模型版面兜底**：原触发条件（置信度 < 0.7）实测既漏报又误报，最常见的错（时间轴）是"有把握地读错"、兜底根本触发不了，所以改用上面的规则修（实测见 [05-evaluation-and-plan](05-evaluation-and-plan.md) 5.2 末尾）。

**表格：先缩成一块，排好位置再展开**

（[extract.py:130](../backend/app/parser/extract.py#L130) `_find_tables`、[layout.py:372](../backend/app/parser/layout.py#L372) `_take_tables`、[layout.py:323](../backend/app/parser/layout.py#L323) `_place_table`）

表格的列与列之间也有竖着的空白，上面的算法会把它当成栏间空白，整张表按列读乱（"时间 / 2022… 2019… 2025… / 学校 / 江城大学江城一中…"），页面还被判成 sidebar、置信度 1.0。做法分三步：

1. **找表**：PyMuPDF 的 `page.find_tables()` 按边框线找表，只取**格子的位置**，文字仍用自己抽出的行。原因是它抽文字时按格子边界裁字，文字稍微超出格子，一个日期就被切成 `2022.09-2026.` 和 `06`。
2. **归格子、验真假**：中心落在表里的行，归到和它重叠面积最大的格子。有字的格子不到 4 个或不到一半，就不算表格——"顶部色条 + 侧边栏底色块"会被 `find_tables` 拼成一张 2×2 的假表格，靠这条挡掉。
3. **替身**：整张表缩成一个"替身行"，和普通的行一起走上面的分栏算法，所以表格在右栏里就留在右栏；落位时再展开：

```python
if isinstance(r[0], _TableLine):                  # 叶子里遇到表格替身
    placed.extend(_place_table(r[0].table, col, stats))
```

展开的规则：一行里每格都只有一行字 → **整行一块**（`2022.09-2026.06 江城大学 计算机科学与技术`）；第一格是标签 → **标签单独一块**（表格型简历常把"项目经历"放在左列，不拆开章节识别认不出）；有格子写了多行 → 每格各自按原来的折行、项目符号规则分块。

### 2.3 行 → 块，定下坐标系

（[layout.py:541](../backend/app/parser/layout.py#L541) `_starts_new_block`、[layout.py:579](../backend/app/parser/layout.py#L579) `assign_offsets`）

一句话折成两行要并回一块，新的项目符号要另起一块。判断"另起一块"的条件：换了区域或页、字号粗细变了、遇到项目符号或像标题的行、行间留白明显变大，以及最关键的一条——**上一行没写满到栏的右边**（没写满就换行，说明是作者主动换的）。

块排好后，全系统**唯一**定义坐标系的函数：

```python
def assign_offsets(blocks: list[Block]) -> str:
    cursor = 0
    for i, b in enumerate(blocks):
        b.char_start, b.char_end = cursor, cursor + len(b.text)
        cursor = b.char_end + 1           # 块之间用一个 "\n" 连接
    return "\n".join(b.text for b in blocks)
```

从此恒成立：`full_text[b.char_start:b.char_end] == b.text`，测试专门断言这一条。之后任何地方都不准再改文本（不准 strip、不准全角转半角）。

### 2.4 章节识别：词典 + 版面打分

（[section.py:118](../backend/app/parser/section.py#L118) `lookup`、[section.py:191](../backend/app/parser/section.py#L191) `find_headings`、[section.py:231](../backend/app/parser/section.py#L231) `build_sections`、[section_llm.py:46](../backend/app/parser/section_llm.py#L46) `classify_sections`）

- 标题词典匹配：整行就是别名（"教育背景""EDUCATION"）→ 中英双语（"教育背景 Education"）→ 组合标题拆开（"专业技能与证书"按"与"拆开，每部分都认得，取第一部分）。比较前去掉"一、"这类编号和符号、转小写。
- 光靠词典会误判（正文里恰好一行只有"项目"两个字），所以再按版面打分：词典命中 +3、字号更大 +1、加粗 +1、独占一行且短 +1、上方有留白 +1，**≥3 分才算标题**。

**词典认不出的：先找候选，再一次交给模型**

词典管常见写法，冷门写法（"动手实践""能力清单"）交给模型。但不能把每一行都问一遍，所以先用版面挑候选：**字号明显比正文大**的短行，或者**和词典认出的标题长得一样**（同字号、同粗细）的短行——后一条是给"标题和正文一样大、只是加粗"的简历用的。

全部候选一次发给模型，每个带标题和下面内容的开头（先掩码），模型只回"第几个是哪一类"，还可以说"不是标题"（加粗的项目名也长得像标题）：

```python
kind = decided.get(s.block_start) if s.needs_llm else None
if kind == "none":
    continue                      # 不是标题：并回上一节
if kind:
    headings.append(Heading(s.block_start, kind, s.confidence, "llm"))
elif s.matched_by != "style":     # 模型没给定论：字号更大的仍记为 other，同样式的并回上一节
    headings.append(...)
```

模型只能选编号和类别，改不了切分位置；调用失败就当没问过，解析照常成功。一次约 ¥0.002、1.8 秒，没有候选就不调。

**没有标题的教育**：表格型简历的教育表上面常常没写"教育背景"，它就落进开头的 basics 段，而 basics 不发给模型。所以全文没有教育章节时，把开头段**末尾**连续几块像教育的（有"××大学"或"本科 / 硕士"）切出来当教育章节。只切末尾、不切带电话邮箱或住址的块——切走了，本地就抽不到联系方式，还会被发给模型（"海淀区学院路""大学城"也会被当成学校名，自查时发现的）。

### 2.5 个人信息掩码：必须长度不变

（[pii.py:94](../backend/app/parser/pii.py#L94) `mask_pii`）

```python
masked = _PHONE.sub(_mask_digits, masked)          # 手机号每个数字 → X
masked = _EMAIL.sub(_mask_email, masked)           # 邮箱除 @ . 以外 → *
masked = _LOCATION.sub(_mask_location, masked)     # 「所在地：杭州」→「所在地：某某」，只掩地名
masked = masked.replace(name, "某" * len(name))    # 姓名 → 同样个数的"某"
assert len(masked) == len(text)
```

发给模型的永远是掩码文本：姓名、电话、邮箱、身份证号、所在地 / 籍贯都掩掉。**逐字符替换、长度不变**，模型在掩码文本上说"第 120–135 个字有问题"，这个区间直接拿到原文上用，不用任何换算。换成"[电话]"这种长度不同的占位，后面所有位置都会错开。

> **〔语法〕`re.sub` 的第二个参数可以是函数**：每匹配到一处调用一次，返回值就是替换内容。

### 2.6 结构化抽取：模型只回"块编号"

（[structure.py:127](../backend/app/parser/structure.py#L127) `_SectionBlocks.valid`、[structure.py:163](../backend/app/parser/structure.py#L163) `_build_experience`）

**问题**：让模型"把项目经历拆成一条条、给出描述文字"，模型会悄悄改标点、合并换行，拿它的文字去原文里就找不到了。

**做法**：发给模型的每块前面带编号 `[#12]`，模型**只回"这条由第 12、13 块组成"**，文字由代码按编号从原文切：

```python
highlights.append({"text": sb.text(h_span), **h_span})   # 文字来自原文切片，不来自模型
```

模型编的、不在本章节里的编号直接丢掉。这样模型**根本没有机会改写简历内容**。日期也不让模型抽，用正则本地识别。

教育、经历、项目、技能、获奖互不依赖，用线程池**并行调模型**（一轮全发出去，不排队），解析时间从"几次之和"变成"最慢的一次"：

```python
with ThreadPoolExecutor(max_workers=MAX_PARALLEL_SECTIONS) as pool:
    futures = [pool.submit(contextvars.copy_context().run, run, job) for job in jobs]
```

`copy_context().run` 是为了让"评测批次号"这个 `ContextVar` 在子线程里也读得到——它默认不会传进新线程。

### 2.7 版面合成集：怎么证明读对了

（[gen_layout_set.py](../backend/scripts/gen_layout_set.py)、[eval_layout.py](../backend/scripts/eval_layout.py)）

真实简历样本拿不到多少，所以用脚本**画**简历：20 份虚构内容 × 6 种版式 = 120 份（单栏 / 两栏 / 侧边栏 / 表格型 / 时间轴 / 无边框表格型）。按正确的阅读顺序一段段画上去，**画的顺序就是标准答案**；字号、边距、行距、栏宽随机，随机种子固定，每次生成的都一样。

指标是**相邻行对顺序准确率**：标准答案里相邻的两段，在输出里也必须紧挨着、顺序一样才算对。一开始只看"前一段在前"，PyMuPDF 按行交错读两栏也有 97%——栏内相邻的两行仍然"在前"，几乎不扣分，所以改成了"紧挨着"。

对照三组：PyMuPDF 自带排序、最初的规则（没有表格识别和时间轴日期列）、现在的规则。结论：现在的规则总体 98.2%。PyMuPDF 按坐标从上到下读，逐行的版式（表格、时间轴）天然读对、两栏会左右交错；规则正好相反——表格识别和时间轴日期列补的就是"逐行"这一块。各版式的数字和剩下的错详见 [05-evaluation-and-plan](05-evaluation-and-plan.md) 5.2。

合成的版式很规整，只能说明"设计覆盖到的版式都做对了"；真实简历没测，列为局限（见 05 5.8）。

### 踩过的坑

- **右对齐的日期被当成右栏** → "两边都要像一栏"的条件。
- **"标签：内容"列表**（"缓存与分布式：熟练使用 Redis…"）上一项恰好写满一行时，下一项被当成折行 → 专门加了判断。
- **带边框的表格被按列读乱**，而且被判成 sidebar、置信度 1.0（大模型兜底要 < 0.7 才启动，兜底也救不了）→ 表格识别（2.2 末尾）。
- **时间轴读错却自报 1.0**：左列日期被当成一栏 → 日期列规则（2.2）。第一版要求"较少一边全是日期"，合成集里一半没生效：日期列里还夹着「教育背景」这类短标题 → 改成"过半是日期"。
- **新条目的标题行被并进上一条描述**：上一条描述恰好写到栏宽右边，像"写满换行"，下一行「日期 …… 标题」就被当成折行 → 由相隔较远的几段拼成的行一律另起一块。
- **格子里的多行被拼成一块**：判断"这一行写满了没有"时，原来拿这几行自己最宽的一行当右边界，格子里几行长短差不多，行行都像"写满了"→ 格子的右边界改用**格子的边框**。
- **合并格下面那一行被当成标签**："教育背景"竖着跨两行时，第二行只剩"2023.11 | 校赛一等奖"两格，被"两格、左格短"的规则当成了标签 → 标签必须在表格**最左一列**。
- **表格型简历抽不到姓名**：原来只认"单独一块、长得像人名"的块，而「姓名 | 张三」按行展开后是「姓名 张三 性别 男」→ 加了一条正则认「姓名」后面的名字（[pii.py](../backend/app/parser/pii.py) `_LABELED_NAME`）。名字后面必须是空白、分隔符或行尾，「姓名：张三性别：男」这种分不清边界的宁可不认。顺带的好处：姓名抽到了，发给模型前才能把它掩掉。
- **冷门标题的内容整段丢失或串节**：9-27 实测 15 个常见写法词典只认 1 个；标题字号大时被记成 other（结构化不抽 other），标题和正文一样大时根本认不出，内容并进了上一节 → 补词典 + 组合标题拆开 + 候选交模型归类（2.4）。
- **组合标题拆不开**："一、项目和工作经历"里编号的顿号也被当成了连接词 → 拆之前先去编号。
- **PyMuPDF 会把挨得很近的两段字抽成一行**（间隔小于约 6pt）：两格的字挨在一起时就分不开。正常表格的格子左右各有约 5pt 的内边距，两格文字至少隔 10pt，不会发生；测试里曾因为画得太挤踩到过。
- **说明和实际不一致：所在地没掩**：`pii.py` 原来写着「basics 章节永不发给模型」，但匹配判定和差距建议发的是整份简历的掩码文本，开头的个人信息也在里面；姓名、电话、邮箱、身份证号掩掉了，「所在地：杭州」「籍贯：浙江」却原样发出去（2026-10-08 整理文档时对照代码发现）。→ `mask_pii` 加一条：所在地 / 籍贯冒号后的地名掩成等长的「某」；放在邮箱之后，「邮箱地址：」后面的邮箱已经成了 `*`，不会被当成地名。
- **落库写在 `try … else` 里**：else 分支不受 except 保护，写库一出错，简历就一直停在"解析中"，直到重启才被清理 → 落库挪进 try 的末尾；失败时先 `rollback()` 丢掉写了一半的块，再标 failed。投递流水线踩过同一个坑（第 7 章）。

### 答辩可能被问

- **两栏怎么排顺序？** 滑动窗口找被压住行数最少的竖向空白带，跨栏行横切，递归先左后右。
- **表格怎么处理？** `find_tables` 只取格子位置，文字用自己抽的行；整张表缩成一块参与分栏，排好位置再按行展开；左列的章节名单独成块。
- **怎么证明读对了？** 版面合成集 120 份（6 种版式），画的顺序就是标准答案，相邻行对顺序准确率总体 98.2%；PyMuPDF 自带排序在两栏上只有 35%。
- **怎么保证模型不篡改简历？** 结构化时只回块编号，文字从原文切；之后模型的所有引用都要经 `locate_span` 核实（第 3 章）。

## 3. 防幻觉的核心：`locate_span`

涉及：[diagnose/evidence.py](../backend/app/diagnose/evidence.py)。诊断、JD 解析、匹配、结构化抽取的技能名、面试评分五处共用。

### 要解决什么

模型说"这句有问题：『负责系统的优化工作』"——这句话真的在简历里吗？编的就不能展示。

### 思路

拿引用去原文里找：先精确找 → 找不到再模糊找（相似度 ≥ 90，容忍标点全半角、换行这类格式差异）→ 先在提示范围里找（送审的那条经历），再扩大到全文 → **都找不到 = 编的，丢掉并计数**。论文里的"幻觉拦截率"就是这个计数。

### 关键代码

**长度不变的归一化**（[evidence.py:49](../backend/app/diagnose/evidence.py#L49) `normalize_for_match`）

```python
_CHAR_MAP = {code: code - 0xFEE0 for code in range(0xFF01, 0xFF5F)}   # 全角 → 半角
_CHAR_MAP.update({ord("。"): ord("."), ord("\n"): ord(" "), ……})      # 中文标点 → 英文，换行 → 空格

def normalize_for_match(s: str) -> str:
    out = s.translate(_CHAR_MAP)
    assert len(out) == len(s)
    return out
```

每个字符只换成另一个字符，所以归一化后位置不变，在归一化文本上找到的区间可以直接用在原文上——和"掩码长度不变"是同一个思路。

> **〔语法〕`str.translate(表)`**：`{原字符编码: 新字符编码}` 的字典，一次遍历完成全部替换。全角 `！`（U+FF01）和半角 `!`（U+0021）正好差 `0xFEE0`，一行字典推导式就生成了全部映射。

**查找**（[evidence.py:55](../backend/app/diagnose/evidence.py#L55) `_search`）

```python
at = window.find(quote)
if at >= 0:
    return Span(lo + at, lo + at + len(quote), 1.0, "exact")        # 精确命中
if len(quote) < MIN_FUZZY_LEN:
    return None                                                      # 太短的引用不做模糊匹配
hit = fuzz.partial_ratio_alignment(quote, window)                    # 在 window 里找和 quote 最像的一段
if hit.score >= 90:
    return Span(lo + hit.dest_start, lo + hit.dest_end, ……, "fuzzy")
```

太短（<6 字）的引用在任何文字里都能找到"差不多像"的片段，所以只做精确匹配。

**调用方**（诊断，[llm_review.py:58](../backend/app/diagnose/llm_review.py#L58) `_to_finding`）：还要求定位结果落在送审的那条经历里；通过核实后，**证据文字改用原文切片**而不是模型给的那句，存下来的永远是简历原话。

### 答辩可能被问

- **阈值为什么是 90？** 经验值：格式差异只改个别字符、相似度很高，整句编造的相似度会明显低。没有专门做阈值扫描：M8 降质集上模型的引用（3 次共 979 条）全部逐字命中，模糊匹配这一档没用上（05 5.3），阈值的影响在这批数据上测不出来。

## 4. 调对话模型的唯一出口：`LLMClient`

涉及：[llm/client.py](../backend/app/llm/client.py)、[cache/llm_cache.py](../backend/app/cache/llm_cache.py)、[cache/ratelimit.py](../backend/app/cache/ratelimit.py)、[llm/registry.py](../backend/app/llm/registry.py)

### 思路

十几处要调模型，每处都要缓存、限流、记账。只要各写各的，就一定有地方漏。所以只留一个出口（系统不变量④），固定五步：

```
① 算缓存 key → ② 命中就记一行审计、直接返回 → ③ 限流占位 → ④ 调模型、算成本 → ⑤ 写缓存 + 写审计
```

### 关键代码

**缓存 key 含整段 prompt 的哈希**（[llm_cache.py:18](../backend/app/cache/llm_cache.py#L18) `make_key`）

```python
return f"llm:{scene}:{model}:{prompt_version}:{sha256(rendered)}"
```

prompt 变一个字就不命中；`prompt_version` 也在 key 里，**改了提示词就升版本，旧缓存自动失效**。解析失败、空内容的结果不进缓存——否则一次偶发的坏输出会持续 7 天。

**JSON 解析失败不抛异常，而是带原因重试**（[client.py:62](../backend/app/llm/client.py#L62) `parse_json`、[client.py:229](../backend/app/llm/client.py#L229) `invoke_json`）

`parse_json` 返回 `(对象, None)` 或 `(None, "错误原因")`。错误原因是写给模型看的，放进下一轮消息：

```python
messages = [*messages, ("assistant", result.text[:2000]),                   # 你上一次的回答
            ("user", prompts.JSON_RETRY.format(error=result.parse_error))]   # 错在哪
```

比"失败了原样再问一次"有效得多。这段"最多试两次"原来在结构化抽取、章节归类、JD 解析、匹配里各抄了一份，后来合成了 `invoke_json` 一个函数；
面试出题、评分和诊断重试前还要核对编号 / 证据 / 引用（"引用找不到"也走这条路，第 5 章），逻辑不同，各自写循环，只共用 `JSON_RETRY` 这句话。

> **〔语法〕Pydantic**：`class _JdOut(BaseModel): requirements: list[_Requirement]` 声明期望的形状，`model_validate(字典)` 检查字段类型、取值范围，不合格抛 `ValidationError` 并说明是哪个字段。

**限流：Redis 固定窗口计数**（[ratelimit.py:20](../backend/app/cache/ratelimit.py#L20) `acquire`）

```python
key = f"ratelimit:{provider}:{int(now // 60)}"      # 每分钟一个桶
count = redis_client.incr(key)                       # 原子加 1
if count <= limit_per_minute:
    return                                           # 拿到名额
time.sleep(60 - now % 60 + 0.05)                     # 否则睡到下一分钟
```

诊断时十几条经历同时调模型，很容易超过服务商的每分钟上限。`INCR` 是原子操作，多个线程同时加也不会算错。

**流式版本 `stream()`**（[client.py:141](../backend/app/llm/client.py#L141) `LLMClient.stream`，给具体建议和面试出题用）

```python
for chunk in chat.stream(messages):
    usage = chunk.usage_metadata or usage       # token 用量只在最后一块里
    if chunk.content:
        text += chunk.content
        yield chunk.content                     # 模型吐一段，就往外交一段
```

外加两个异常分支：`except GeneratorExit`（调用方中途不要了，比如浏览器断开）照样记一行账；`except Exception` 记账后抛 `LLMError`。

> **〔语法〕生成器**：函数里有 `yield`，调用时不会立刻执行完，外面每取一次就跑到下一个 `yield` 交出一段再暂停，所以模型每吐几个字调用方就能拿到。`GeneratorExit` 继承自 `BaseException`，`except Exception` 接不住，要单独写。

**依赖从构造函数传入**：`LLMClient(chat_factory=…, cache=…, acquire=…, write_audit=…)` 都有默认值；测试时传入假的，不联网也能测完整五步（第 11 章）。

### 模型服务调不通时：说清楚，并且提前告诉用户

10-09 评测时 DeepSeek 余额用完了，才发现所有失败都说"请稍后重试"——可余额不充值，再试多少次都一样。分两步解决：

**① 认出来**（[client.py](../backend/app/llm/client.py) `unavailable_reason`）：按服务商返回的错误分类，再试也没用的那几种带上原因。

```python
if isinstance(e, openai.APIStatusError):
    if e.status_code == 402: return "余额不足（402）"
    if e.status_code in (401, 403): return f"密钥无效（{e.status_code}）"
    if e.status_code == 429 or e.status_code >= 500: return f"服务繁忙（{e.status_code}）"
if isinstance(e, openai.APIConnectionError): return "连不上模型服务（…）"      # 超时也是它的子类
```

`LLMError` 多了一个 `unavailable` 字段，调用方一句话分开说：`LLM_DOWN if e.unavailable else "……请稍后重试"`。

**② 提前告诉**（[status.py](../backend/app/llm/status.py)）：登录后的页面顶上一条横幅，按 `GET /system/llm` 显示。后端怎么知道能不能用：
问 DeepSeek 的余额接口 `GET /user/balance`（不花钱，余额用完返回 `is_available: false`，密钥不对 401），或者用真正调用时碰上的错误。
结论在 Redis 里存 1 分钟，所以余额接口 1 分钟最多问一次，恢复后横幅最多 1 分钟就消失。

- **为什么不放进 `/health`**：容器健康检查看的是它，任一项异常就返回 503。余额用完不该让后端容器被判成不健康，网站别的部分（看以前的结果、诊断报告）照常能用。
- **余额接口自己出了状况（比如 500）按能用处理**：横幅只是提示，宁可少报，不让它误报。
- **踩过的坑：一次网络抖动就误报一分钟**。充值后开发环境的后端第一次去问正好碰上 `ConnectTimeout`，结论存了 60 秒，横幅说"不可用"，其实直连 0.3 秒就通；余额接口有时也要 3–5 秒才返回，原来的 5 秒超时卡在边上。→ 超时放到 10 秒、连不上再试一次（真正调用模型时 SDK 本来也会重试）。

### 踩过的坑

- **DeepSeek 的 JSON 模式要求 prompt 里出现 "json" 这个词**，否则直接报错 → 每个结构化 prompt 都给 JSON 示例，代码里也检查。
- **本机开着 HTTP 代理时**，调国内模型走代理慢好几倍（实测 1 秒 vs 5 秒）→ `httpx.Client(trust_env=False)` 直连。
- **流式调用要开 `stream_usage=True`**，否则拿不到 token 用量，记账全是 0。
- **每次调用都新建 `httpx.Client`**：新建要重新加载证书，实测约 0.23 秒，连接也不复用；诊断时十几个并行调用，光建客户端就 0.9 秒，而诊断本身才 2.5 秒左右 → `http_client` 加 `@functools.cache`，全进程共用一个（它是线程安全的），之后每次约 4 毫秒。openai SDK 只会关掉它自己建的客户端，外面传进去的不会被关。
- **限流占位写在 try 外面**：Redis 连不上、排队超时，抛出来的不是 `LLMError`，调用方写好的降级（面经向量化失败就整段用、总结失败就留空）全都接不住，直接 500 → 占位失败也转成 `LLMError` 并记一行审计（`_take_slot`）。
- **限流上限定得太低，评测"变慢"**：原来每分钟 60 次，按分钟的固定窗口计数，连续跑评测时每 4–5 份就要等到下一分钟，诊断评测"每份 13 秒"里大部分是在等（调高后的对比见 05 5.3）。DeepSeek 官方不限速率（忙时排队变慢），所以上限调到 300，本地限流只防一次发太多。

### 答辩可能被问

- **缓存会不会让评测失真？** 评测时设置批次号，有批次号就跳过缓存。
- **模型服务挂了网站会怎样？** 页面顶上马上提示（后端问服务商的余额接口，1 分钟一次）；出错的地方说"模型服务暂时不可用"，不说"请稍后重试"；以前的结果照常能看。
- **为什么不用 LangChain 的 `with_structured_output`？** 它也能做，但我们要在同一处做缓存、限流、记账，并把错误原因整理成给模型看的中文提示去重试；自己包一层都在一个文件里，更好控制、也更好讲清楚。

## 5. 诊断：规则 + 模型 + LangGraph 并行

涉及：[diagnose/rules.py](../backend/app/diagnose/rules.py)、[diagnose/llm_review.py](../backend/app/diagnose/llm_review.py)、[diagnose/scorer.py](../backend/app/diagnose/scorer.py)、[graphs/diagnose_graph.py](../backend/app/graphs/diagnose_graph.py)、[graphs/state.py](../backend/app/graphs/state.py)

### 思路：确定的用规则，模糊的交给模型

| 规则判（免费、稳定、零幻觉） | 模型判 |
|---|---|
| 有没有数字、开头是不是"参与"这类弱动词、技能栏写了经历里没用 | 是不是空话、有没有夸大、职责边界清不清楚 |

规则先跑，结论同时告诉模型"这些查过了别重复报"。分数用公式算，**不让模型打分**——不稳定，也说不清为什么是这个分。

### 关键代码

**规则用装饰器注册**（[rules.py:57](../backend/app/diagnose/rules.py#L57) `rule`）

```python
RULES: dict[str, Rule] = {}

def rule(code: str):
    def register(fn):
        RULES[code] = fn
        return fn
    return register

@rule("NO_QUANTIFICATION")
def no_quantification(ctx):
    for u in ctx.experience_units:
        if 说了"提升/降低" and not _has_number(u.text):
            yield _finding(……)
```

新增一条规则 = 新写一个函数、上面加一行 `@rule`，别处不用改。

> **〔语法〕带参数的装饰器**：`@rule("X")` 先执行 `rule("X")` 得到 `register`，再执行 `register(no_quantification)`。模块一被导入，7 条规则就自动登记进字典。

"有没有数字"不能简单找数字（[rules.py:71](../backend/app/diagnose/rules.py#L71) `_has_number`）：`(?<![A-Za-z\d.#+\-])\d+` 排除 Vue3、JDK8、CET-6 里的数字；行首的"1."是列表编号也不算，但"10.5%"要算。

**模型审查：带核实的重试循环**（[llm_review.py:78](../backend/app/diagnose/llm_review.py#L78) `review_unit`）

```python
for attempt in range(1, 4):                          # 首次 + 最多 2 次重试
    result = llm.invoke(……)
    if result.parsed is None:
        feedback = "格式不对：" + result.parse_error
    else:
        for item in result.parsed.findings:
            finding = _to_finding(item, ……)          # 用 locate_span 核实引用
            (review.rejected if finding.verify_result == "failed" else review.verified).append(finding)
```

格式不对、引用找不到，走**同一条重试路径**。被拦下的不展示但存库，用来算拦截率：**首轮**被拦下的条数 ÷ 首轮模型给出的总条数。

**LangGraph：每条经历一个并行分支**（[diagnose_graph.py:50](../backend/app/graphs/diagnose_graph.py#L50) `_dispatch`；建图在 [diagnose_graph.py:96](../backend/app/graphs/diagnose_graph.py#L96) `build_diagnose_graph`）

```
START → rule_scan → plan_review ─(Send × N)→ review_unit ─→ merge_findings → score → END
```

```python
return [Send("review_unit", {"unit": u, ……}) for u in units]     # 一条经历一个分支，同时跑
```

N 个分支同时往 State 里写，靠 reducer 合并（[state.py:18](../backend/app/graphs/state.py#L18) `DiagnoseState`）：

```python
llm_findings: Annotated[list[Finding], add]       # 多个分支同时写 → 用 + 合并
cost: Annotated[float, add]                       # 各分支的花费加起来
```

**没声明 reducer 的字段被多个并行分支同时写，LangGraph 会直接报错**——这是用 LangGraph 做并行最容易踩的坑。

> **〔语法〕`Annotated[类型, 附加信息]`**：给类型挂一个附加信息，Python 不管，LangGraph 读出来当合并函数用。`add` 来自 `operator`，就是 `+` 的函数版本。

三种模式（只规则 / 只模型 / 两者都用）共用这张图，只在两个节点里各有一个 if；做消融实验切换的是参数，不是代码路径。分发前还有一次**成本预检**：按预估单价算最多能审几条，超出的截掉，状态记为 `partial`。

**合并**：规则和模型指向同一处（区间重叠超过一半）、同一维度时，只留规则那条。

**评分**（[scorer.py:28](../backend/app/diagnose/scorer.py#L28) `score`）：各维度从 100 分起扣（严重 25 / 中等 12 / 轻微 5），再加权。两个细节：
- **按经历条数摊薄**：经历写得多被查的地方也多，直接累加会天然吃亏（开发时一份 7 条经历的简历"表达"维度被扣到 0 分）；
- **没人查的维度记 `None`、不记满分**：只开模型通道时，"量化"维度没有任何来源能查，记 100 分就是把"没人查"当成"没问题"。

### 怎么评测：程序化降质

（[gen_eval_set.py](../backend/scripts/gen_eval_set.py)、[run_eval.py](../backend/scripts/run_eval.py)）

不请人标注，而是**造数据时就定好标准答案**：20 份虚构底稿刻意写得"干净"（每条描述都有数字和实打实的动词、技能栏只列用过的技能、两段实习前后衔接），每份再出两个坏版本——规则类降质（删数字、改成「协助」、技能栏多写一个没用过的技能、造 7 个月空窗）和语义类注入（在描述后面接一句夸大 / 前后矛盾 / 职责不清的话）。缺陷在哪、该由哪条规则或哪类问题报出，脚本都记着；"检出"就是有一条问题的证据区间和缺陷那段文字重叠。

三种模式切换的只是参数（`mode`），跑的是同一张图。评测在**评测批次号**下跑：绕过缓存（要测真实行为），每次调用都带批次号记进 `llm_calls`。批次号是个 `ContextVar`，LangGraph 并行分支里也读得到（实测 78 次调用全带上了）。

每种模式跑 3 次。结论：规则类缺陷只用模型时，技能对不上和时间空窗完全抓不到——模型逐条审描述，看不到跨条目的问题；语义类缺陷只用规则也是 0；两者都用，两类都检出。**规则和模型各管一块，合起来两类都抓得到。** 模型的引用全部逐字照抄，引用核对是道保险，这批数据上没有触发（论文里如实写）。3 次之间只有模型部分有一两处波动，结论不变；第 1 次慢是卡在限流（原因见第 4 章）。各项检出率、误报、成本、用时详见 [05-evaluation-and-plan](05-evaluation-and-plan.md) 5.3 (3)(4)。合成底稿规整、缺陷句典型，检出率偏乐观。

### 答辩可能被问

- **LangGraph 起了什么作用？** 两处并行：每条经历并行审查（`Send`）、诊断与匹配两个子图并行（第 7 章）；结果靠 reducer 合并。
- **规则和模型冲突怎么办？** 同一处、同一维度只留规则的。
- **没有人工标注，怎么知道诊断对不对？** 程序化降质：在干净底稿里故意放进已知的缺陷，看能不能在对的位置报出对的类型。规则 + 模型两类缺陷都 100% 检出；只用一种都有一类完全抓不到。

## 6. 匹配：规则先判，其余一次交给模型

涉及：[matching/jd_parser.py](../backend/app/matching/jd_parser.py)、[matching/skill_dict.py](../backend/app/matching/skill_dict.py)、[matching/matcher.py](../backend/app/matching/matcher.py)、[matching/llm_judge.py](../backend/app/matching/llm_judge.py)

### 关键点

**① JD 拆要求：模型拆，代码核实**（[jd_parser.py:57](../backend/app/matching/jd_parser.py#L57) `_verify`）：每条要求必须带 JD 原话，原话在 JD 里找不到、或者声称的技能 JD 里根本没有，就丢掉。权重（必须项 1.0 / 加分项 0.5 / 软素质 0.3）由代码按类型定，不让模型给。

**② 技能词典：一条正则扫全文**（[skill_dict.py:43](../backend/app/matching/skill_dict.py#L43) `_compile`）

```python
ordered = sorted(set(words), key=lambda w: (-len(w), w))     # 长的写法排前面
pattern = "|".join(左右加边界(re.escape(w)) for w in ordered)
```

每个细节对应一个真实会出错的例子：
- **长的排前面**：正则的 `|` 按顺序尝试，"微服务架构"要先于"微服务"，"C++"要先于"C"；
- **英文词两侧加边界**（`(?<![A-Za-z0-9])…(?![A-Za-z0-9])`）：不然"Go"会命中"Google"，"Java"会命中"JavaScript"。不用 `\b` 是因为它对中文不起作用；
- **两个字符以内的英文区分大小写**（C、Go、JS）：不然普通单词"go"也算。

扫出的结果存成 `skill_mentions`（哪个技能、第几个字、哪个章节），是全系统唯一的"文本 → 技能"入口，诊断和匹配都查它。

**③ 规则只判十拿九稳的**（[matcher.py:77](../backend/app/matching/matcher.py#L77) `_is_plain_skill_requirement`）：要求去掉技能名后只剩几个字（"熟悉 Redis"）、且经历里确实用过，才由规则直接判满足；"熟悉 Redis 缓存穿透、击穿、雪崩的解决方案"这种带限定语的，光看到 Redis 字样不能算，交给模型。学历、年限也用规则算（工作 / 实习区间合并求总时长，重叠的只算一次）。

**④ 其余的连同简历全文一次交给模型**（[llm_judge.py:44](../backend/app/matching/llm_judge.py#L44) `judge_with_fulltext`）：模型说满足，就必须给出简历原话，经 `locate_span` 定位；找不到就作废、按缺失处理、记一次幻觉。

**⑤ 模型判完，规则再把一道关**（[matcher.py](../backend/app/matching/matcher.py) `recheck_listed_only`，2026-10-09 加的）：
技能只写在技能栏时，规则会判"部分满足"，但混合模式还是交给模型复核（技能栏里的 Java 可能就是 Spring Boot 项目里在用的）。
评测发现模型常常看到"专业技能中列出了 X"就判满足，和提示词里"只是提到 = 部分满足"正好相反。所以模型判完再查一次：

```python
rule = _match_skill(req, structure, full_text)            # 规则自己的结论
if rule.status == "partial" and not _in_experience(structure, item.char_start, item.char_end):
    return rule                                           # 模型的依据不在任何一段项目 / 工作经历里 → 照规则
```

依据落在经历里的照模型的（模型找到了没写出字面的用法），所以原来"交给模型复核"的好处还在。
只在混合模式里加；"只用模型"是对照组，不加。

**⑥ 算分**：每条要求按状态折算（满足 1 / 部分 0.5 / 缺失 0），再按权重加权平均。

### 为什么匹配不用 RAG

简历加 JD 只有两三千字，放得进 prompt 就不检索：全文一次判断比逐条 RAG 更快、更便宜，也不会因为检索漏掉片段（学历、"技术栈"那一行）而误判（实测对比见 [06-workflows](06-workflows.md) 6.2）。**知道什么时候不该用 RAG，本身就是一个能讲的点。**

### 内置岗位模板：先解析好，再进种子数据

没有具体 JD 时可以选模板（计算机 7 份：Java / Python·Go 后端、前端、算法、大模型应用、测试开发、数据分析；运营 5 份：内容、用户、活动、电商、产品运营）。流程：

```
data/job_templates/<方向>/*.txt     手写的 JD 原文（第一行是岗位名称；目录名是方向，如 cs、ops）
  ↓ scripts/build_job_templates.py  复用 parse_jd（按方向取提示词），每份调一次模型
data/job_templates.json             原文 + 拆好的要求项，提交进仓库
  ↓ scripts/dump_seed.py
backend/sql/seed.sql                和技能词典一起导入 MySQL
```

- **为什么预先解析、不在导入时调模型**：模型每次输出可能不同，导入时现调，同一份模板在不同机器上拆出的要求就不一样，导入还得有 API key。解析一次存成 json，导入是纯 SQL，结果固定；拆得对不对，看 json 就知道。
- **重复导入：按标题更新，不能删了重建**（[dump_seed.py](../backend/scripts/dump_seed.py) 的 `_templates_sql`）：

```sql
UPDATE jobs SET raw_text = @raw, requirements = @reqs, …  WHERE is_template = 1 AND title = '…';
INSERT INTO jobs (…) SELECT NULL, 1, '…', @raw, @reqs, 'success' FROM DUAL
  WHERE NOT EXISTS (SELECT 1 FROM jobs WHERE is_template = 1 AND title = '…');
```

  技能词典可以先 `DELETE` 再插（id 按 CSV 行号固定）；模板不行：`match_reports.job_id` 是 `ON DELETE CASCADE` 的外键，删掉模板会把用户在这个模板上的投递一起删掉，重插后 id 也变了。所以"有就改、没有就插"，清单里去掉的改成软删除。`FROM DUAL` 是 MySQL 的虚拟表，让 `INSERT … SELECT` 可以带 `WHERE`。
- **测试守住三处一致**（`test_seed_sync.py`）：txt 与 json 的原文一致（改了原文忘了重新解析会报错）；json 与 seed.sql 一致；每条要求都满足 `raw_text[char_start:char_end] == quote`，`skill_id` 与当前词典一致。
- **踩过的坑**：「熟练掌握 Python 或 Go 其中一门语言」被模型当成了 Python 这一项技能（提示词要求"或"连接的保持一条、不填技能）。默认的混合模式下影响不大：要求里还有"或 Go"，规则不会直接判，会交给模型读全文。但只用词典的对照模式会把只会 Go 的人判成缺失。改成「任一门语言即可」重新解析就对了。模型拆的结果要人过一遍，这也是预先解析的好处。

### 怎么评测：三种模式比一比

（[run_eval.py](../backend/scripts/run_eval.py) 的 `match_requirements`，`--task match`）

同样不请人标注：用诊断评测那 20 份虚构简历，每份配 8 条岗位要求，**满足与否按简历内容就能确定**——比如简历里没有 Flink，"熟悉 Flink"就是不满足；技能栏多写的那个技能经历里没用过，"熟悉它"就是部分满足。三种模式切换的还是同一张图的参数，每组跑 3 次。结论（各类要求的一致率、花费详见 [05-evaluation-and-plan](05-evaluation-and-plan.md) 5.3 (2)）：

- **只用规则**判不了"用过 A 或 B 等框架""有高并发经验"这类要读懂的要求，一律记不满足，这两类全错。
- **用了模型**的只错在一处：只写在技能栏的技能，模型有 15–18% 判成满足（理由"专业技能中列出了 X"），规则在这一项上全对。混合模式为了稳妥，把规则判成"部分满足"的技能也交给模型复核（技能栏里的 Java 可能就是项目里实际在用的），所以这一项反而不如规则。
  后来运营、财会简历上错得更多（判对的只有 0–50%），就加了上面的 ⑤：这一项在三个方向上都变成 100%，其余各项不变。
- **混合 vs 只用模型**：一致率持平，交给模型的条数少、花费也少。

## 7. 投递流水线与进度推送

涉及：[services/apply_service.py](../backend/app/services/apply_service.py)、[graphs/apply_graph.py](../backend/app/graphs/apply_graph.py)、[cache/pubsub.py](../backend/app/cache/pubsub.py)、[api/task.py](../backend/app/api/task.py)、[nginx/default.conf](../nginx/default.conf)

### 要解决什么

投递要跑十几秒到几十秒。要做到：接口立刻返回；过程中能实时推进度；推送出问题（断线、漏消息）也一定能知道任务结束了。

### 时序

```
POST /apply → 建两条 pending 记录（诊断、匹配），开后台任务，立刻返回 id
GET /tasks/apply/{id}/stream（SSE 长连接）
后台：等简历解析完 → 跑图 A（诊断 ∥ 匹配 → 初筛）→ 每完成一个节点往 Redis 频道发一条进度
SSE：订阅频道转发进度；每秒查一次数据库，任务结束就发 done 并断开
```

### 关键代码

**图 A：两个子图并行**（[apply_graph.py:52](../backend/app/graphs/apply_graph.py#L52) `build_apply_graph`）

```python
graph.add_edge(START, "diagnose")                # 从起点连两条边 → 两个节点并行
graph.add_edge(START, "match")
graph.add_edge(["diagnose", "match"], "gate")    # 两个都完成才到 gate
```

**边跑边推进度**（[apply_service.py:97](../backend/app/services/apply_service.py#L97) `_run_graph`）

```python
for update in graph.stream(state, stream_mode="updates"):    # 每完成一个节点吐一次
    for node, fields in update.items():
        publish(task_id, "progress", {"stage": node, ……})
```

`graph.invoke` 只在最后给结果，`graph.stream` 每过一个节点吐一次，这就是进度的来源。图里不碰数据库，跑完由 service 落库——所以图能单独跑，评测脚本可以直接调子图做消融。

**MySQL"可重复读"的坑**（[apply_service.py:83](../backend/app/services/apply_service.py#L83) `_wait_until_parsed`）

刚上传就点投递时，要等解析完：

```python
while resume.parse_status in ("pending", "parsing"):
    time.sleep(0.5)
    db.commit()           # ← 先结束当前事务
    db.refresh(resume)    # ← 再重读
```

只写 `refresh` 会一直读到 `parsing`（CLAUDE.md 的"踩过的坑"里记着这条）。MySQL 默认隔离级别是**可重复读**：同一个事务里读多少次，看到的都是事务开始那一刻的快照，看不到别的会话后来提交的新状态。先 `commit()` 结束旧事务，下一次读才会开新事务看到最新数据。

**SSE 接口：结束以数据库为准**（[task.py:69](../backend/app/api/task.py#L69) `_events`）

```python
while 没超过 10 分钟:
    status = 查数据库(任务状态)                  # ① 每轮先查库
    if status 已结束:
        yield sse_event("done" 或 "error", ……)
        return
    message = subscription.get(timeout=1)        # ② 最多等 1 秒 Redis 消息
    if message 是 progress:
        yield sse_event("progress", message["data"])
    elif 15 秒没发过东西:
        yield ": keep-alive\n\n"                 # ③ 心跳（SSE 里 : 开头是注释，浏览器会忽略）
```

**为什么结束要看数据库、不信 Redis？** 发布订阅是"发了就忘"：浏览器连上来之前发的、网络抖动时发的消息都会丢。只等 Redis 的 done，错过一次就永远等下去。每秒查一次库，不管什么时候连上来、漏了多少，任务一结束就一定收到 done。Redis 只负责"中间进度"这种丢了也无所谓的信息。

**Nginx 要关缓冲**：Nginx 默认把响应攒一攒再发，SSE 就变成"攒够了一次性到"。`proxy_buffering off`，响应头带 `X-Accel-Buffering: no`，gzip 也不压 `text/event-stream`（压缩同样会缓冲）。

**后台任务：每一步都要在 try 里**（[apply_service.py:48](../backend/app/services/apply_service.py#L48) `run_apply`）：后台任务抛出的异常没人接，前端只能看数据库里的状态。原来图跑完之后的两次落库写在 try 外面，落库一出错，两条记录就一直停在 running，前端要等 SSE 10 分钟超时才知道。现在落库也放进 try，任何一步出错都记成 failed。测试的做法：把 `match_service.save_result` 换成一个直接抛异常的函数，检查两条记录都是 failed。

**"哪里不符合"在读取时组装**（[apply_service.py:162](../backend/app/services/apply_service.py#L162) `gap_items`）：没满足的要求按"权重高的在前、同等重要时缺失在部分满足前"排序。原设计里这是图 A 的一个节点，后来改成读取时组装，每条都带着数据库 id，才能拿去生成建议。

**「我的投递」列表**（[apply_service.py:135](../backend/app/services/apply_service.py#L135) `list_applies`）：投递就是 match_report，表里没有 user_id，
归属跟着简历走（和 `GET /apply/{id}` 一样，简历删了就不列）。先查出这一页的投递，连带岗位、简历（两个 join）；
再用**一条** `IN` 查询把这些投递下面的面试都取出来、按投递分组——不按条去查，否则 20 条投递就要再查 20 次（N+1 问题）。
这一步抽成了 `interviews_of`，结果页的 `GET /apply/{id}` 也用它带上这次投递的面试（成绩单里显示）。
失败原因不直接给 `error_msg`（那是给开发者排查的技术报错）：简历没解析出来的复用解析失败的提示（扫描件、加密……），其余统一一句"分析时出错了，可以再投一次"。

**删除简历、岗位**（[resume.py:78](../backend/app/api/resume.py#L78) `delete_resume`、[job_service.py:74](../backend/app/services/job_service.py#L74) `delete_job`）：都是软删除，只打 `is_deleted` 标记，文件和数据留着。两者的后果不一样：投递的归属跟着简历走，删了简历，它的投递和面试报告在「我的投递」里一起看不到；删岗位只是不能再拿它投递，已有的投递照样能看，面试也照样能开（取岗位用的是 `db.get`，不看删除标记）。所以删简历前要提示「它的 N 次投递也会隐藏」：[`GET /resumes`](../backend/app/api/resume.py#L50) 每条带上 `apply_count`，同样是**一条**分组查询（`GROUP BY resume_id`）算出这一页每份简历投过几次，不按条查。

### 踩过的坑

- **启动清理漏了"排队中"**：原来只把 running 的诊断 / 匹配标成失败。投递在等简历解析时（最长 120 秒）两条记录还是 pending，这时重启服务，它们就永远停在 pending；而建新投递时 pending 也算"进行中"，这份简历从此再也投不了（一直 409）→ 启动清理改成 `status IN ('pending','running')`，并加了测试。

### 答辩可能被问

- **为什么用 SSE 不用 WebSocket？** 进度只需服务端往浏览器推，单向；SSE 就是普通 HTTP 长连接，Nginx 配置简单。
- **进度消息丢了怎么办？** 结束信号以数据库为准，丢的只是中间进度。
- **「我的投递」怎么带出每条投递的面试？** 先查一页投递，再用一条 IN 查询取这些投递的面试、按投递分组，不按条查（避免 N+1）。

## 8. 具体建议：提示词、流式接口、数字复检

涉及：[rewrite/advice.py](../backend/app/rewrite/advice.py)、[services/advice_service.py](../backend/app/services/advice_service.py)、[api/advice.py](../backend/app/api/advice.py)、[llm/prompts.py](../backend/app/llm/prompts.py) 的 `ADVICE_*`；调提示词的完整过程见 [具体建议-提示词草稿](design/具体建议-提示词草稿.md)

### 要解决什么

原来"怎么改"是规则的固定模板，同一种问题下面永远是同一句话（"说的有点太泛了"）。要改成针对**这一句**、**这条要求**的具体建议。

### 思路

1. **点开才生成**，只为真正看的条目付费；生成过的存库复用。
2. **流式返回**，1 秒左右出第一个字。
3. **不让模型编**：原文没有的内容用【】留给用户填；生成完用代码复检数字。

### 提示词是怎么调出来的

拿一次真实投递（虚构简历）的数据直接调 DeepSeek，逐条读输出，把每个问题翻译成一条具体规则写进提示词：

| 版本 | 发现的问题 | 怎么改 |
|---|---|---|
| 第一版 | 偏长（146–257 字）；改写时加了原文没有的做法（"保证回调幂等"）；技能类问题改错地方 | 每段限字数；原文没有的一律用【】留空；技能问题要说"在某段经历里写" |
| 第二版 | 把"参与了数据库设计"改成"负责……"，替用户升级了职责 | 加一条：参与 / 负责 / 主导这类词不替用户改，写成【负责 / 参与，按实际】 |
| 第三版 | 问题类 78–125 字，差距类 139–231 字，首字 0.5–1.1 秒 | 定稿 |

### 关键代码

**上下文：这一句 + 所在整段经历**（[advice.py:49](../backend/app/rewrite/advice.py#L49) `finding_prompt`）：诊断结果记着 `unit_id`（如 `projects[0].highlights[2]`），用正则拆开就能找到这一句和整段经历。只发这一句，模型不知道项目是做什么的，给不出具体建议。技能栏的问题没有所属经历，就把全部经历发过去。发的都是掩码文本。

**数字复检**（[advice.py:92](../backend/app/rewrite/advice.py#L92) `fix_numbers`）

```python
allowed = set(NUMBER.findall(original))       # 原文（这段经历）里出现过的数字；NUMBER 与规则引擎同一口径
parts = _SECTION.split(text)                   # 按【段标题】切开
for 【改成】那一段里、不在【】占位里的每个数字:
    不在 allowed 里 → 换成【数值】，计数 +1
```

> **〔语法〕`re.split` 带括号的正则**：模式里有捕获组时，分隔符本身会保留在结果里。`_SECTION.split("【问题】A【改成】B")` 得到 `['', '问题', 'A', '改成', 'B']`，奇数位是段名、偶数位是内容，还能原样拼回去。

**为什么是事后复检、不是"违规就让模型重写"？** 流式输出已经发出去的字撤不回来。所以边生成边下发原文，生成完复检一次，以**复检后的全文**为准存库，并在结束事件（done）里下发。

**服务层：直接给存好的，或者给一个"待生成任务"**（[advice_service.py:53](../backend/app/services/advice_service.py#L53) `finding_task`）

```python
if saved := _saved(finding.rewrite):
    return saved                                   # 生成过：直接返回
def save(session, result):                         # 闭包：记住了 finding_id
    session.get(Finding, finding_id).rewrite = result
return AdviceTask("rewrite", ……, finding_prompt(……), save)
```

`save` 是个闭包，任务带着它，生成完再调用。这样生成流程 `run()` 不用关心"存到哪张表哪个字段"，问题和差距两种建议共用一个 `run()`。

> **〔语法〕海象运算符 `:=`**：`if saved := f():` 等于先 `saved = f()` 再 `if saved:`。

`run()` 本身是个生成器：边从 `llm.stream()` 取字边 `yield ("delta", …)`；失败 `yield ("error", …)`、什么都不存；成功就复检、开新会话存库、`yield ("done", 结果)`。接口层把这个生成器直接交给 `StreamingResponse`，每产出一段就发给浏览器一段。

**存进 JSON 列的坑**（[advice_service.py:82](../backend/app/services/advice_service.py#L82) `gap_task`）

```python
row.items = [{**i, "advice": result} if i["requirement_id"] == requirement_id else i for i in row.items]
```

差距的建议存在 `match_reports.items` 列表的某一项上。写成 `row.items[k]["advice"] = result`（直接改列表里的字典），**SQLAlchemy 察觉不到，不会写库**——它只看"这个属性有没有被重新赋值"。所以要整体换一个新列表。

### 答辩可能被问

- **建议是模型写的，怎么保证不胡说？** 提示词禁止编造（原文没有的用【】留空、不升级职责、"如果你做过……"的条件写法）；代码复检数字；【】要用户自己按实际填。
- **为什么不在投递时一次全部生成？** 投递要多等 5–10 秒，而且看不看都要付费。

## 9. 模拟面试：图 B，停下来等人回答

涉及：[graphs/interview_graph.py](../backend/app/graphs/interview_graph.py)、[graphs/checkpoint.py](../backend/app/graphs/checkpoint.py)、[interview/](../backend/app/interview/)（materials · planner · asker · rubric · policy · report）、[services/interview_service.py](../backend/app/services/interview_service.py)、[retrieval/context_store.py](../backend/app/retrieval/context_store.py)、[api/interview.py](../backend/app/api/interview.py)

### 要解决什么

前面的图都是一口气跑完的。面试不行：每出一题都要**停下来等用户打字**，可能等几分钟，中间还可能刷新页面、关掉浏览器、第二天再回来。要做到：停得住、接得上、中途出错能从原处继续；题目一个字一个字出来；分数说得清是怎么来的。

只做技术面（HR 面太主观，设计上不做）：5 个话题，每个最多追问 1 次，一场 5–10 问。

### 流程

```
POST /interviews   整理材料 →（面经太长就切段入库）→ plan_interview 定 5 个话题 → 停在 pick_topic 之前
POST /start        pick_topic → retrieve_context → ask_question（流式）→ wait_answer ★ 停
POST /answer       evaluate_answer → decide ─ 追问 → ask_question → wait_answer ★ 停
                                           ├ 下一个话题 → pick_topic → …
                                           └ 话题用完 / 钱花到上限 → final_report → 结束
POST /finish       用户提前结束：不经过图，按已评完分的题出报告
```

### 关键代码

**① 停下来等人：`interrupt()` + 检查点**（[interview_graph.py](../backend/app/graphs/interview_graph.py) 的 `_wait`）

```python
def _wait(state):
    reply = interrupt({"question": state["question"]})     # 图停在这里
    return {"answer": reply["text"], "skipped": reply["skip"]}

# 用户答完（interview_service._advance）：
graph.stream(Command(resume={"text": 回答, "skip": False}), config, stream_mode=["custom", "updates"])
```

检查点（checkpointer）= 每走完一个节点，就把整个 State 存一份，按 `thread_id = "interview:{id}"` 区分会话。`interrupt()` 让图在这个节点停住；带着 `Command(resume=…)` 再调一次时，**这个节点从头重跑**，`interrupt()` 这回直接返回 resume 的值。检查点用 `SqliteSaver`（本地一个 SQLite 文件，零部署）。

创建会话时只想把话题定下来、还不出题，用 `graph.invoke(state, config, interrupt_before=["pick_topic"])`：跑到 pick_topic 之前就停。之后 `graph.stream(None, config)` 从那里接着跑。这样整个面试流程都在一张图里。

**② 流式出题：节点里往外推文字**（`_ask`）

```python
write = get_stream_writer()
write({"asking": {"topic_idx": idx, "depth": depth}})      # 先说是第几个话题、是不是追问
for piece in llm.stream("interview_ask", messages, …, stats=stats):
    write({"delta": piece})
```

service 用 `stream_mode=["custom", "updates"]` 同时收两种东西：`custom` 是节点推出来的文字，原样转成 SSE；`updates` 是每个节点跑完的输出，按节点落库（出完题插一行 turn，评完分写 evaluation，出报告写 report）。**节点本身不碰数据库**（系统不变量④）。`llm.stream` 是生成器、没有返回值，花了多少钱通过传进去的 `stats` 字典带回来（单场成本要封顶）。

**③ 两份状态，MySQL 为准**

MySQL 的 `interview_sessions / interview_turns` 是面试记录的权威来源，页面和报告都读它；话题计划和材料也存在 `sessions.plan` 里。检查点只管"让图能接着跑"。检查点丢了（文件被删）就从 MySQL 重建（`_rebuild`）：

```python
graph.update_state(config, 从 MySQL 拼出来的状态, as_node="ask_question")   # 当作 ask_question 刚跑完
for _ in graph.stream(None, config): pass                                   # 跑到 wait_answer 的 interrupt() 停下
```

`as_node` 的意思是"假装这个节点刚跑完、这是它的输出"，图就知道下一步该去哪。面试结束后删掉这条检查点线程（`checkpointer.delete_thread`），面经切段也一起删。

**④ 出错了从原处继续**

节点抛异常时，检查点停在失败的那个节点之前，`graph.stream(None, config)` 就会从那一步重跑。所以只需要一个"继续"接口：`POST /start` 既是开始也是重试。另外两个保证：
- **回答先落库再恢复图**：评分失败了回答也不会丢；
- **同一题只能答一次**：`UPDATE interview_turns SET answer=… WHERE id=… AND answered_at IS NULL`，影响行数为 0 就是答过了（两个标签页同时提交也一样）。同一场面试同时只允许一个请求推进图（进程内的锁，单进程部署够用）。

**⑤ 评分说得清：依据要逐字引用，分数由代码算**（[rubric.py](../backend/app/interview/rubric.py)）

模型按三项（正确性 / 深度 / 表达，各 0–5）打分，**必须逐字引用候选人回答里的原话作为依据**，经 `locate_span` 核对。一条都对不上 → 带着"哪句找不到"重试一次 → 还不行就三项都给中性 3 分、标 `low_evidence`，聚合时权重减半。和诊断同一套防幻觉思路。

```
题分   = 三项平均 × 20（0–100）；跳过的题记 0 分（不然跳过难题反而拉高平均）
话题分 = 这个话题各题分的加权平均（low_evidence 的权重 0.5）
综合   = 聊到了的话题的平均
结论   练习模式 → 不下结论；没聊完所有话题就结束 → 不下结论（incomplete）；其余 ≥ 60 通过
```

模型只写文字总结（表现好的 / 需要加强 / 和简历问题的关联），不打总分。追问几次也由代码决定（[policy.py](../backend/app/interview/policy.py)）：模型说要追问、这题没跳过、追问次数没用完才追问；钱花到上限就直接出报告。

**⑥ 检索只在面经很长时才用**

和"匹配不用 RAG"同一个判断：放得进 prompt 就不检索。简历和 JD 不检索——每个话题本来就指向具体的某段经历 / 某条要求。用户贴的面经不超过 3000 字就整段给面试官；更长才切段（按段落，约 500 字一段）→ bge-m3 向量化进 Chroma → 按"话题名 + 考察目标"召回 → reranker 精排取 3 段。没贴就跳过。

### 怎么评测：好坏已知的三档回答

（[interview_answers.py](../backend/scripts/interview_answers.py)、[run_eval.py](../backend/scripts/run_eval.py) 的 `--task interview`）

同样不请人打分：从降质集的 6 个虚构项目各出 2 道题，每题写三档回答，**好坏在写的时候就定了**：
- **具体到位**：做法、原因、效果都讲清楚。
- **空泛**：只说做了什么，但没说错。
- **答错**：篇幅、细节和"具体到位"差不多，核心说法是错的，比如"查询和更新在同一个方法里，所以重复回调不会同时进来"。

直接调线上同一个评分函数 `rubric.evaluate`，不走整场面试；36 条回答各打 3 次分。看三件事：**区分度**（每道题"具体"是不是比另两档分高）、**稳定性**（同一回答几次得分差多少）、**依据**（第一次就合格的比例）。

怎么数出"第一次就合格"：不改评分函数，给模型客户端包一层，数它被调了几次。调了 2 次，就说明第一次的输出被打回重试了。

结论：3 次打分中每道题都是"具体到位"比另两档分高，而且具体档的最低分也高于另两档的最高分；空泛和答错的总分差不多，但分项能分开（空泛扣得最多的是深度；答错多半是正确性最低，道理错了也谈不上深度，两项往往一起压低）；依据第一次就全部逐字命中，"给中性分"没有触发。温度设成 0，模型也不是每次输出都一样，不过同一回答 3 次得分大多完全一样。回答是开发者写的、每档特征都很典型，区分度偏乐观，论文里如实写。各档分数、稳定性、成本详见 [05-evaluation-and-plan](05-evaluation-and-plan.md) 5.4（interview-v2 的数；v1 → v2 见下面的坑）。

**运营方向也测了一套**（[interview_answers_ops.py](../backend/scripts/interview_answers_ops.py)，`--task interview --set ops`）：从运营评测集的 6 个虚构项目出 12 题，"答错"档是方法或指标说错，比如完播率拿点赞除以播放算、A/B 测试把新用户和老用户分成两组比、留存率拿相邻两周的活跃人数相除。用运营的领域包打分（三项的定义换成运营的），结论和计算机方向一样，数字同样见 05 5.4。

### 踩过的坑

- **模型把"要求 9"写成 `requirement[8]`**：材料里的编号原来是数字和 `projects[0]`，模型当成了从 0 开始的下标，错一位还看不出来，5 个话题只剩 1 个能用。改成每条材料带一个照抄就行的编号（经历 P1、岗位要求 R9、简历问题 F128），代码按编号核对。
- **"影响行数为 0"的 0 被当成编造的数字**：参考答法复用了具体建议的数字复检，技术细节里的小数字也被换成【数值】。面试这里放过一位数（编造的成果数据很少只有一位），具体建议仍然严格。
- **答一题就提前结束也能"通过"**：综合分只算聊到的话题，答好一题马上结束就过线了。改成没聊完所有话题不下结论。
- **模型一直收到双花括号**（interview-v1）：评分、总结两段系统提示词不经过 `.format()`，示例 JSON 却写成了 `{{ }}`（经过 `.format()` 才会变回单花括号），模型收到的就是双花括号。
  → 改成单花括号、版本升到 interview-v2，重跑评测结论不变；加了测试：发给模型的提示词里不能有双花括号。
- **删检查点线程的时机**：要等图整个跑完再删。在 final_report 那一步的输出里就删的话，图随后还会写最后一个检查点，线程又被写回来。
- **丢掉一个话题就少一个话题**：定话题原来只在一个能用的都不剩时才重试，模型给错一个编号，这场就只有 4 个话题（本机 15 场里有 1 场）。
  → 不够 N 个也带着原因重试一次（"要 5 个，能用的只有 4 个，另外 1 个的 ref 找不到"），两次里取能用的多的那次；材料本来就凑不出 N 条时不为凑数重试（[planner.py](../backend/app/interview/planner.py)）。
- **放弃的面试只在启动时清理**：24 小时没动静就按已答的题出报告、标成放弃，原来只在服务启动时跑一次，长期不重启就一直显示「进行中」。
  → 启动时再挂一个每小时跑一次的后台任务（[main.py](../backend/app/main.py) 的 `sweep_forever`）：

```python
while True:
    await asyncio.sleep(interval)
    try:
        await asyncio.to_thread(sweep_idle_interviews)   # 清理是同步的数据库操作，放线程里跑，不卡住处理请求的事件循环
    except Exception:
        logger.exception(...)                             # 这一轮失败就等下一轮，循环不能停
```

### 答辩可能被问

- **为什么用 LangGraph，不自己写状态机？** `interrupt()` + 检查点本来就是为"跑到一半停下来等人"设计的；追问 / 换话题 / 结束画在图上一目了然，规则是一个纯函数，能单独测。
- **检查点和数据库存了两份，会不会不一致？** 以 MySQL 为准；检查点丢了从 MySQL 重建；面试结束就删检查点。
- **怎么保证评分不是模型随口给的？** 每条依据逐字引用回答、代码核对；对不上就重试、再不行给中性分并减半权重；总分由代码按公式算。
- **评分准不准？** 用好坏已知的三档回答测：具体到位平均 86 分，空泛和答错 38–39 分，3 次打分每道题都排对，同一回答 3 次得分平均只差 1 分。
- **面试里的 RAG 用在哪？** 只用在用户贴的长面经上；简历和 JD 很短，整段给更准。
- **面试做到一半人走了怎么办？** 停在"等回答"本身是正常状态，回来能接着答；24 小时没动静才按已答的题出报告、标成放弃（不调模型），服务启动时和之后每小时各检查一次。

## 10. 求职方向：一套流程，换一套规则

涉及：[domains/](../backend/app/domains/__init__.py)（`cs.py`、`ops.py`）、[llm/prompts.py](../backend/app/llm/prompts.py) 里的 `[[名字]]`、[api/domain.py](../backend/app/api/domain.py)、`jobs.domain`

### 要解决什么

原来整套提示词都按计算机写死（「你是资深技术招聘官」「技术上说得对不对」、示例是 Redis 和缓存）。想支持运营等其他专业，
又不想复制一整套流程。观察下来，**流程和代码都是通用的，变的只是提示词里的几处说法、个别规则和页面文案**。

### 思路

- 用户在工作台第一步选方向，存在岗位上（`jobs.domain`）。诊断、匹配、建议、面试都按岗位的方向取一个「领域包」。
- 提示词里随方向变化的地方换成标记，拼好之后由 `fill()` 换成领域包里的文字：

```python
# llm/prompts.py（片段）
DIAGNOSE_SYSTEM = """你是一位资深[[recruiter]]，正在审阅候选人简历中的**一条**经历描述。…"""

# domains/__init__.py
def fill(text: str, domain: Domain) -> str:
    return _MARK.sub(lambda m: domain.texts[m.group(1)], text)   # 缺片段直接 KeyError

# 调用处：先 .format() 填运行时内容，最后换标记（领域包里的 JSON 示例就不用写 {{ }} 转义）
messages = [("system", fill(prompts.DIAGNOSE_SYSTEM, domain)), ("user", user)]
```

- 简历解析不分方向：上传时还不知道要投哪个岗位。技能词典也不分：不同专业的词不冲突，直接加进一张表。
- 规则也能按方向补一点：判断「写没写结果」的结果词（提升、降低、缩短……）是按技术岗写的，运营写「公众号涨粉明显」会被当成没写结果，
  其实写了、只是没数字。领域包加了 `RESULT_WORDS`（运营 21 个指标名，计算机为空），`RuleContext` 把它拼到通用词表后面：
  计算机方向的规则一点没变，运营方向这句改报「缺少量化」。

### 怎么保证计算机方向一个字都没变

先拍快照，再改造。`tests/prompt_cases.py` 用一个「只记录、不回答」的假模型，按真实调用路径把 10 个场景的提示词都生成一遍存起来；
改造后 `test_domains.py` 逐字比对。`cs.py` 里给提示词的 24 个片段也不是手抄的，是脚本从原文里截出来的（另有一个诊断问题的标题 `risk_depth_title`，不进提示词）。
所以提示词版本号不用升，缓存不失效，M8 的评测结果也还对应现在的代码。同一组测试再用运营方向生成一遍，确认 10 个场景都变了、没有残留标记。

### 领域包有没有用：运营评测集

照计算机那套造了一套运营评测集（10 份虚构底稿 × 3 个版本），同一批简历分别用运营、计算机的领域包跑诊断和匹配。
造数据的代码两个方向共用，只换素材（`scripts/eval_set_ops.py`）：

```python
# gen_eval_set.py：Pool 装一个方向的素材（实习、项目、没用过的工具、注入的句子、专业……），造底稿、降质、画 PDF 的代码不变
OPS = Pool("ops", 10, settings.DATA_DIR / "eval_set_ops", ops.INTERNSHIPS, ops.COMPANIES, ops.PROJECTS, ...)
POOLS = {p.key: p for p in (CS, OPS)}
```

改造计算机那套时怎么保证没变：用新代码重新生成 60 份，和原来的标准答案逐字比、每份 PDF 抽出的文字逐份比，全部一样。

结论（数字详见 [05-evaluation-and-plan](05-evaluation-and-plan.md) 5.3 (7)）：检出率、一致率两种包差不多，
差别在说法：计算机包对运营简历有几条写"看不出技术含量"，运营包没有，还会举运营的例子。
这些缺陷看的是结构，不靠专业知识；领域包管的是"话说得对不对路"，而这些话会直接显示给用户。

### 第三个方向：财会金融

为了验证「加方向 = 加规则和数据」在和互联网差别更大的专业上也成立，又加了财会金融（会计、审计、财务分析、税务、证券研究）。
改动：`domains/finance.py`（25 段说法 + 7 个结果词）、`skills_seed.csv` 35 条、4 份模板、评测素材 `scripts/eval_set_finance.py`；
代码只在 `DOMAINS` 里登记一行，前端的下拉框按接口返回的方向列表画，不用改。
评测（数字见 [05](05-evaluation-and-plan.md) 5.3 (8)）：检出率两种包都是 100%；财会包在干净底稿上多报了几条"描述模糊"
（多是挑"缩短 50%"没交代口径），引用全部逐字命中，是更较真、不是编造。

### 第四个选项：「其他」（通用包）

方向只有三个，别的专业（设计、教育、法律、医药……）也想测。做法是再加一个不带行业的领域包 `domains/general.py`，下拉框里叫「其他」，排在最后：
- **说法写成中性的**：角色就叫"招聘官 / 面试官"，示例用各专业都有的事（办公软件、毕业设计、职业资格证）；证书要求照财会的做法记成 other。
  规则不分专业，照常跑；结果词取运营和财会的并集（不知道是哪一行，写了指标名就算写了结果）。没有岗位模板，用户自己贴 JD。
- **告诉用户可能不够准**：领域包多一个可选的 `NOTE`，只有通用包写了，接口原样给前端，前端有就显示（选方向时、结果页、诊断报告）。
  以后加专门方向不用碰页面。

```python
note: str = ""      # Domain 里：只有通用方向有，专门方向为空、页面不显示
...note=getattr(module, "NOTE", "")   # _load：专门方向的模块不用写这一项
```

- **评测**（数字见 [05](05-evaluation-and-plan.md) 5.3 (9)）：三套评测集换通用包跑，检出率和专门包一样（缺陷看结构）；
  差在挑刺的口径（计算机简历上多报"协同过滤没说是哪一种"这类细节）和匹配略低。所以页面上说"仅供参考"是有依据的。
- **坑**：一致性测试原来要求"每个方向都有模板"，通用包没有模板，改成"每个专门方向都有"。

### 踩过的坑

- **重新解析模板会把老模板也改掉**：模型结果缓存只有 7 天，9 月解析的计算机模板早过期了，再跑一遍可能拆得不一样，已有投递引用的要求项就对不上。
  → 构建脚本改成原文没变的模板直接沿用旧结果，只按新词典重算 `skill_id`（它是代码查词典算的，不是模型给的）。
- **加词条会影响老模板**：数据分析模板里「Excel」「A/B 测试」原来词典里没有（skill_id 为空），加进运营词条后要跟着补上，否则一致性测试报错——正好由上一条的重算处理。
- **老数据没有方向**：`get_domain(None)` 一律按默认方向；面试材料里没记方向的老面试也照常。
- **标准答案也会定错**：运营匹配评测的第一版"二选一"写成"会用 X 或 Y 等工具制作图文或视频素材"，简历只列了工具、没写用途，模型判"部分满足"是对的。
  → 要求里只写简历能证明的东西；模型和标准答案对不上时，先看模型给的理由。
- **结果词只收指标名**：「留存、转化、曝光」单独出现时多半在说做了什么（「负责用户留存分析」），算成结果会报「提到了留存却没有数字」；收「留存率、转化率、曝光量」。
- **证书不能进技能词典**：简历里证书（CPA、ACCA、初级会计……）多半写在「技能证书」一栏，解析时归到技能；要是证书也是词条，「技能栏写了、经历里没用过」这条规则会对每个证书报一次。→ 证书不进词典，领域包的 JD 解析示例把证书要求写成 other，交给模型按全文判断。
- **别名会撞常用缩写**：给「京东」加别名「JD」，简历和招聘信息里的 JD（岗位描述）都会被认成京东，去掉了。加别名先想想它在别处是什么意思。

### 答辩可能被问

- **怎么扩展到其他专业？** 写一个领域包（提示词里 24 个 `[[标记]]` 对应的文字 + 页面文案 + 规则开关），补词条和模板，流程代码不改；测试会检查新方向的片段是否写全。
- **为什么不让模型自己判断方向？** 用户选更可靠，也让 JD 解析在知道方向之后进行；下拉框里方向多了也只是多几行。
- **领域包有没有用？** 同一批运营简历换两种包跑：检出率差不多（缺陷看的是结构），差在说法——计算机包会说"技术含量"，运营包说运营的话。
- **加一个方向要多少工作？** 财会金融就是这么加的：一份领域包、35 个词条、4 份模板、一套评测素材，代码只登记一行，大约一天。
- **方向不够怎么办？** 选「其他」走通用包：问题照样能查出来（检出率和专门包一样），但说法不对行、挑刺口径不稳，页面上明说"可能不够准，仅供参考"。
- **用户选方向和防幻觉是什么关系？** 用户选方向消除的是"用错标准"这一类错误（让模型猜方向，猜错了整条链都用错规则）；
  模型在判断里编东西，靠的仍是"引用必须在原文里逐字找得到"。两者管的是不同的错。

## 11. 测试怎么写

涉及：[tests/conftest.py](../backend/tests/conftest.py)。在 `backend/` 下 `.\.venv\Scripts\python.exe -m pytest -q`，409 个用例，约 20 秒，**不联网、不需要 MySQL 和 Redis**。

思路：把外部依赖全部换成假的。前面反复出现的设计——领域层不碰数据库、`LLMClient` 的依赖从构造函数传入、接口里的数据库 / 模型 / 推送都用 `Depends` 取——很大程度上就是为了能测。

- **测试里把 bcrypt 调到最低强度**：线上一次哈希约 0.37 秒（故意慢），几十个测试都要注册用户，原来全部测试要 54 秒、一半时间花在这上面 → conftest 里一个自动生效的 fixture 把 `security.BCRYPT_ROUNDS` 改成 4，降到约 20 秒。
- **测试用的 PDF 现场生成**：用 PyMuPDF 在指定坐标写字，想测两栏就放两列，想测扫描件就只放一张图。每行文字带编号（L01、R01…），顺序对不对一眼可见。不依赖真实简历，也没有隐私问题。
- **SQLite 内存库代替 MySQL**：`create_engine("sqlite://", poolclass=StaticPool)`，每个测试一个干净的库；`StaticPool` 让所有连接共用同一个内存库。
- **依赖覆盖**：FastAPI 提供 `app.dependency_overrides`，把数据库、模型、进度推送换成假的，业务代码一行不改：

```python
app.dependency_overrides[get_db] = override_get_db             # → SQLite
app.dependency_overrides[get_llm_client] = lambda: fake_llm     # → 假模型
```

- **假模型按"问的是什么"给预设回复**：键可以写成 `"_ReviewOut:某段文字"`，只在 prompt 里出现这段文字时命中。诊断时几条经历同时调模型、先后顺序不确定，按内容匹配，结果就是确定的。想测"模型编造引用"就让它回一句简历里没有的话，想测"模型挂了"就把回复设成异常——各种坏情况都能精确造出来。

**测什么（按重要性）**：坐标契约（每块都满足 `full_text[start:end] == text`）、反幻觉（编造被拦、带原因重试、拦截数统计对）、隐私（发给模型的文本里没有姓名电话）、越权（别人的一律 404）、失败路径（模型超时、输出坏掉、中途断开都要落成明确的失败状态）。

**真模型的效果怎么验证？** 单元测试管"自己的逻辑对不对"；真模型的效果交给 M8 评测（造数据时定好答案，做法见第 5、6、9、10 章，结果见 05）和开发时连真实后端的试跑。

## 12. 部署：本机 Docker

涉及：[docker-compose.yml](../docker-compose.yml)、[backend/Dockerfile](../backend/Dockerfile)、[frontend/Dockerfile](../frontend/Dockerfile)、[nginx/default.conf](../nginx/default.conf)

### 做法

在项目根目录 `docker compose up -d --build`，一条命令起四个容器，浏览器打开 `http://localhost`：

```
nginx    前端打包好的静态文件 + 把 /api 转发给后端（同一个域名，没有跨域）   ← 对外只开 80 端口
backend  FastAPI，单 worker（后台任务、启动清理都依赖单进程）
mysql    首次启动（数据卷为空）时自动执行 schema.sql、seed.sql：建表、导入岗位模板和技能词典
redis    限流计数、进度推送
```

- **前端在 Docker 里打包**（多阶段构建）：先在 Node 镜像里 `npm run build`，再只把 `dist` 拷进 Nginx 镜像，最终镜像 94 MB，不带 Node。
- **MySQL、Redis 不对外开端口**：容器之间用服务名当主机名（`DATABASE_URL` 里写 `mysql:3306`）。本机开发用的 MySQL、Redis 照常跑，互不冲突。
- **后端镜像按 `requirements.lock` 装**，版本和开发机一致；后端数据（上传的简历、面经向量库、面试检查点）放数据卷。
- `restart: unless-stopped`：Docker Desktop 开着，电脑重启后容器自己起来。

### 怎么确认流式没被 Nginx 缓冲

经 Nginx 投递一次，记下每个事件的到达时间：进度的 4 个事件在 2.1 / 3.8 / 4.8 / 4.8 秒陆续到达；具体建议 60 段分 24 次到达，
和在容器里直连后端（98 段分 35 次）节奏一样。被缓冲的话会在最后一下子全到。

### 踩过的坑

- **中文全成了乱码**（「åŽç«¯å¼€å‘…」）：MySQL 镜像首次建库执行 `.sql` 用的客户端字符集不是 utf8mb4，UTF-8 的字节被当成 Latin-1 存了进去。
  本机手动导入时客户端默认就是 utf8mb4，所以一直没发现。→ 两份 SQL 开头加 `SET NAMES utf8mb4;`（改在生成脚本里）。
- **时间差 8 小时**：容器默认 UTC，MySQL 设的是北京时间。创建时间是 MySQL 写的，最后活动、结束时间是 Python 写的，
  「24 小时没动静才收尾」的判断也会错 8 小时。→ 后端容器也设 `TZ: Asia/Shanghai`。
- **健康检查提前报"好了"**：首次建库时 MySQL 先起一个不监听网络的临时实例跑 `.sql`，用 `localhost`（套接字）ping 会通，
  后端连上来发现表还没建好就退出。→ 健康检查改走 TCP（`-h 127.0.0.1`），建完库正式启动后才通。
- **开机自启不按依赖顺序**：重启电脑后 Docker 同时拉起所有容器，后端可能比 MySQL 先起、连不上就退出；有重启策略，会被再拉起来，等十几秒就好。

### 答辩可能被问

- **为什么用 Docker Compose？** 一条命令在任何装了 Docker 的电脑上起来，依赖版本和开发机一致；数据库、缓存不用另外装。
- **前端为什么不单独起一个服务？** 打包后只是静态文件，Nginx 直接托管，同一个域名下转发 `/api`，也就没有跨域问题。

### A. 踩过的坑汇总

按章节排；正文里的坑都在这里有一行。

| 坑 | 现象 | 怎么解决 | 章节 |
|---|---|---|---|
| 多进程部署 | 启动清理误杀正在跑的任务 | `--workers 1` | 1 |
| Python 和 JS 数字符长度不同 | 有 emoji 时高亮整体错位 | 抽取时把非 BMP 字符替换掉 | 2.1 |
| 右对齐的日期 | 单栏简历被判成两栏 | 空白带两侧都要"像一栏" | 2.2 |
| 带边框的表格 | 按列读乱，被判成 sidebar、置信度 1.0 | `find_tables` 取格子位置，整张表缩成一块参与分栏，落位时按行展开 | 2.2 |
| 底色块拼成的假表格 | 侧边栏简历被当成表格 | 有字的格子 ≥ 4 个且 ≥ 一半才算表格 | 2.2 |
| 表格格子里的多行 | 长短差不多的几行被拼成一块 | 格子的右边界用格子的边框 | 2.2 |
| 合并格下面那一行 | 竖着合并的格子下面只剩两格，被当成"标签 + 内容" | 标签必须在表格最左一列 | 2.2 |
| 时间轴（左列日期） | 先读完所有日期再读经历，自报 1.0 | 较少一边过半是日期且和另一边同行 → 按行读 | 2.2 |
| "标签：内容"列表写满一行 | 下一项被当成折行 | 专门加判断 | 2.3 |
| 新条目的标题行 | 上一条描述恰好写满，「日期 …… 标题」被并进上一条 | 由相隔较远的几段拼成的行一律另起一块 | 2.3 |

### B. 答辩高频问题速查

| 问题 | 一句话回答 | 章节 |
|---|---|---|
| 怎么防止大模型胡编？ | 模型的每条结论都要逐字引用原文，经 `locate_span` 定位，找不到就丢弃并计数；结构化时模型只回块编号；改写里的数字由代码复检 | 2.6、3、8、9 |
| 幻觉拦截率怎么算？ | 首轮被拦下的条数 ÷ 首轮模型给出的总条数（`diagnoses.hallucination_count`） | 5 |
| 两栏简历怎么排顺序？ | 滑动窗口找被压住行数最少的竖向空白带，跨栏行横切，递归先左后右 | 2.2 |
| 没有人工标注，评测的标准答案哪来？ | 造数据时就定好：诊断在干净底稿里放已知缺陷；匹配按简历内容就能确定每条要求满不满足；面试评分用好坏已知的三档回答 | 5、6、9 |
| 规则 + 模型比单用好在哪？ | 诊断：规则管数字 / 动词 / 跨条目比对，模型管夸大 / 矛盾，合起来两类都 100%；匹配：一致率与只用模型持平（97.7% vs 98.1%），省 27% 的钱 | 5、6 |
| 表格型简历怎么读？ | `find_tables` 只取格子位置；整张表缩成一块参与分栏，排好位置再按行展开，左列章节名单独成块 | 2.2 |

| 词典里没有的章节标题怎么办？ | 版面挑候选（字号更大，或和已认出的标题同样式），一次交模型归类，模型可判"不是标题"；只回编号和类别，失败就当没问过 | 2.4 |

| 个人信息怎么保护？ | 个人信息本地抽取；发给模型的文本先把姓名、电话、邮箱、身份证号、所在地掩成等长的占位，长度不变所以位置不用换算 | 2.5 |
