## 9.3 一分钟介绍这个项目

> 这是我的毕设，一个给应届生用的求职辅助系统。用户上传简历、贴上想投的岗位，系统做三件事：指出简历本身的问题；对照岗位要求逐条判断满不满足，模拟一次初筛；再按这个岗位做一场模拟面试。
>
> 技术上有三个点。第一，流程用 LangGraph 编排：投递是并行的流水线，面试是能停下来等人的状态机。第二，判断不全交给模型：确定的用规则，模糊的才给模型，模型的每条结论都要逐字引用简历原文，程序核对不上就作废。第三，所有调模型的地方走同一个调用层，缓存、限流、记账只写一遍，还配了一个管理端看花费、换模型。

## 9.4 第一点：LangGraph 流程编排与人机协同

### 先把几个词讲清楚

| 词 | 用自己的话说 | 项目里在哪 |
|---|---|---|
| 状态图 | 把流程画成图：节点是一步（一个函数），边是下一步去哪，状态是一张跟着流程走的工单，每一步读它、往上写 | 两张图：投递、面试 |
| 并行 | 从同一个点连出两条线，两边就同时跑；把两个节点写进一个列表再连到下一步，意思是都到齐了才往下走 | [apply_graph.py](../backend/app/graphs/apply_graph.py)：诊断和匹配 |
| `Send` | 分支有几条要运行时才知道，画图时没法先画好，就在运行时现场发：有几条经历，就返回几个 `Send` | [diagnose_graph.py](../backend/app/graphs/diagnose_graph.py) 的 `_dispatch` |
| reducer | 几个分支同时写工单的同一栏，必须先声明怎么合并，不声明直接报错。我们声明的是「加在一起」 | [state.py](../backend/app/graphs/state.py)：`Annotated[list[Finding], add]` |
| `interrupt` | 让图停在这一步，把题目交出去；用户答完，再带着回答把图叫醒 | [interview_graph.py](../backend/app/graphs/interview_graph.py) 的 `_wait` |
| 检查点 | 每走完一步，把整张工单存到硬盘，像游戏自动存档。`interrupt` 能停住再继续，靠的就是它 | [checkpoint.py](../backend/app/graphs/checkpoint.py)：`SqliteSaver`，一个本地文件 |

### 两张图长什么样

投递：

```
            ┌─► diagnose（诊断）─┐
投递开始 ───┤                    ├─► gate（过初筛线）
            └─► match（匹配） ───┘

诊断里面：rule_scan ─► plan_review ─► review_unit × N（同时跑）─► merge_findings ─► score
匹配里面：rule_match ─► judge_fulltext ─► score_match
```

面试：

```
定话题 ─► 选话题 ─► 查面经 ─► 出题 ─► ★等回答 ─► 评分 ─► 决定下一步
            ▲                  ▲                              │
            └── 换下一个话题 ──┴────────── 追问 ───────────────┤
                                 话题用完 / 花费到上限 ─► 出报告
```

**同时跑的只有两处**：`diagnose` 和 `match` 这两个节点；`diagnose` 里面 `review_unit` 的多份（有几条经历开几份）。
匹配里面是三步直线，模型只调一次；面试那张图一步接一步，没有同时做的。

`Send` 和 `interrupt` 各用在一处：`Send` 在诊断里（分出去一起做），`interrupt` 在面试里（停下来等人）。

### 可能的追问

- **为什么用 LangGraph，不自己写 if / else？**
  面试要「走一步、停下来等人、再走」，刷新页面、重启服务后还要接得上，`interrupt` 加检查点就是为这个设计的。追问、换话题、结束画成图上的边，推进规则是一个单独的函数，能单独测。投递那张图用它，是为了并行和每一步的进度事件。
- **并行为什么不自己开线程池？**
  能开，但结果怎么合并、每一步的进度怎么推给页面，都得自己写。用图的话，合并规则声明一行，每个节点跑完自动有事件，直接转成页面上的进度。
- **并行之后快了多少？**
  有几条经历就同时审几条。评测里一份简历的诊断约 2.3–2.8 秒，和只审一条的时间差不多（05 5.3）。
- **一个分支失败了怎么办？**
  单次调用自带重试。重试完还失败，这次投递整个记成失败，不给半份结果：分支里不单独接错误，由后台任务统一落成失败状态。
- **分支之间互相看不到花了多少钱，预算怎么控制？**
  分出去之前算一次：预算 ÷（每条的预估花费 × 1.5 倍的重试余量）= 最多审几条，超出的不发。发出去的就让它跑完。
- **`interrupt` 停住的时候，状态存在哪？多场面试怎么区分？**
  存在检查点里，按 `thread_id`（`interview:场次 id`）分开，叫醒时带上它。
- **叫醒之后从哪一行接着跑？**
  那个节点从头重跑一遍，`interrupt()` 这次直接返回用户的回答。所以 `interrupt()` 前面不能放重复执行会出问题的代码；我们这个节点里它就是第一行。
- **检查点和 MySQL 存了两份，以谁为准？**
  MySQL。页面和报告都读 MySQL；检查点只管让图能接着跑，丢了能从 MySQL 重建，面试结束就删。
- **等用户回答，为什么不用 WebSocket 一直连着？**
  连接一断，状态就丢了。停在检查点上，等待期间不占任何连接，隔一天回来也能接着答。
- **投递的进度怎么实时到页面？为什么是 SSE？**
  图每跑完一个节点，发一条 Redis 消息，SSE 接口转发给浏览器。这里只需要服务端往浏览器单向推，SSE 就是普通的 HTTP 长连接，比 WebSocket 省事。
- **进度消息丢了怎么办？**
  Redis 的发布订阅是发了就忘，所以「结束了没有」不信它，每秒查一次数据库。丢的只会是中间进度。

实现细节：08 第 5 章（诊断的并行）、第 7 章（投递流水线和进度推送）、第 9 章（面试）。

## 9.5 第二点：规则 + LLM 混合判定与证据溯源

### 诊断和匹配都不是全交给模型

| | 规则做的（不花钱） | 模型做的 |
|---|---|---|
| 诊断 | `rule_scan`：7 条固定规则扫一遍，比如「经历里没写数字结果」「技能栏写了、经历里却没用过」 | `review_unit`：每条经历调一次，挑规则看不出来的毛病，比如描述含糊、看不出本人做了什么 |
| 匹配 | `rule_match`：能确定的要求直接判，比如词典里查得到的技能、学历、年限 | `judge_fulltext`：规则判不了的要求，连同简历全文一次交给模型 |

- **调用次数**：诊断有几条经历就调几次；匹配只调一次，要求全被规则判完时一次都不调。
- **算分不走模型**：诊断的分、匹配的分、过不过初筛线，都是公式算的。同一份结果，分数每次一样。
- **两边重复时留规则的**：规则和模型指出同一处的同一类问题，只保留规则那条。

### 证据溯源是怎么回事

1. 发给模型之前，把姓名、电话、邮箱、所在地换成**同样长度**的占位字符（等长掩码）。
2. 要求模型的每条结论都逐字引用简历里的原话。
3. 程序拿这句引用去原文里找：先一字不差地找；找不到再按相似度找（≥ 90，只容忍标点全半角、换行这类差异）。
4. 找不到就当它是编的：告诉模型哪句找不到，让它重做；还找不到，这条结论作废。

等长的好处：掩码前后每个字的位置不变。模型在掩码文本上指出的那一段，直接就能在原文上高亮，不用换算。

### 那组数字怎么来的

简历和岗位要求是自己造的，造的时候就定好了每条要求满不满足，所以能自动对答案，不用人工标注。同一批数据用三种做法各判一遍：只用规则、只用模型、两者结合。

### 可能的追问

- **为什么不全交给模型？**
  规则不花钱、每次结果一样、说得清为什么。而且模型有固定会错的地方：只写在技能栏、经历里没用过的技能，模型常判成「满足」（评测里 60 次错了 9–11 次），规则在这一项是全对的。
- **那为什么不全用规则？**
  规则判不了要读懂句子的要求，比如「用过 A 或 B 其中之一」「描述里有依据、但没点名技能」。这两类只用规则全错，所以只用规则的一致率是 75%。
- **两边结论不一样，听谁的？**
  规则有把握的听规则。匹配里模型判完，规则再查一遍：模型说满足、给的依据却不在任何一段经历里，就记成部分满足。
- **模型引用的话和原文差一两个标点，算不算编的？**
  不算，相似度那一档就是为这个留的。但少于 6 个字的引用只认一字不差：短句在哪都能找到「差不多像」的。
- **实际拦下过多少编造？**
  评测里模型给的 979 条引用全部逐字命中，一条都没拦到。如实讲：这道核对是保险，在这批数据上没有触发。
- **评测数据是自己造的，可信吗？**
  主动说局限：数据是合成的，没有用真实简历和人工标注验证，故意放进去的毛病比较典型，数字偏乐观。它能说明的是三种做法之间的差别。
- **为什么匹配不用 RAG？**
  实测过。简历加岗位要求才两三千字，全文一次给模型只要一次调用；逐条检索再判断要几十次调用，更贵更慢，还会因为检索漏掉片段而判错。

## 9.6 第三点：LLM 调用层的统一封装与成本控制

### 「统一调用层」是什么

不是把所有请求合成一次对话。意思是：项目里十几处要调模型，它们都只调同一个函数，缓存、限流、记账写在这个函数里。业务代码只说「我要问什么」，不关心用的是哪家模型、怎么限流，这就是解耦。各处各写一份的话，一定有地方漏。

每次调用固定五步（[llm/client.py](../backend/app/llm/client.py)）：

```
① 算出这次输入的「指纹」
② 拿指纹去缓存里查 ── 查到了 → 记一笔、直接返回，不花钱
③ 没查到 → 限流：先占一个名额
④ 调模型
⑤ 把答案存进缓存，记一笔账
```

缓存排在限流前面，所以命中缓存的调用不占名额。

### 缓存：同样的输入不重复付费

和「先查缓存，没有再查数据库，查完写回缓存」是同一个套路，只是把数据库换成了大模型：它又慢又要钱。

- **指纹**：`llm:{场景}:{模型}:{提示词版本}:{整段输入的 SHA-256}`。输入差一个字就不命中；换了模型、改了提示词，旧答案自动不用。
- **存多久**：7 天，Redis 到期自动删。
- **不缓存的**：模型返回空内容或格式不对的（多半是偶然出错，存了会错 7 天）；面试出题（同一个人面两场不能问一样的题）；评测时的调用（要测模型的真实表现）。
- **Redis 坏了**：当作没命中，照常调模型。缓存是省钱用的，它坏了不该让功能用不了。

### 限流：每分钟最多 300 次

诊断的并行分支会同时发出十几个请求，所以发之前先占一个名额，名额用完就等到下一分钟（[cache/ratelimit.py](../backend/app/cache/ratelimit.py)；下面是示意，准确写法看源码）。

```python
key = f"ratelimit:{服务商}:{现在是第几分钟}"   # 每分钟一个计数器
count = redis_client.incr(key)                 # 加 1，并拿到加完后的数
if count <= 300:
    return                                     # 没超，放行
time.sleep(到下一分钟还剩几秒)                  # 超了，睡到下一分钟再试
```

这叫**固定窗口**：把时间按整分钟切成一格一格，每格单独数，换格清零。

| 做法 | 怎么数 | 特点 |
|---|---|---|
| 固定窗口（我们用的） | 按整分钟分格，每格单独数 | 最简单，一个计数器就够；两格交界处会突发 |
| 滑动窗口 | 每次往回看「刚过去的 60 秒」有多少次 | 没有交界问题；要记每次请求的时间 |
| 令牌桶 | 按固定速度往桶里放令牌，拿到才能走 | 最平滑，还能攒一点应付短时高峰；实现最复杂 |

面试时可以自己带出来的一段：

> 限流用的是 Redis 的固定窗口，每分钟一个计数器，`INCR` 加一，超了就等到下一分钟。固定窗口在两个窗口交界处会有突发，我知道，但服务商本身不限速率，这里只是防并行分支一下子发太多，所以没上滑动窗口。上限一开始定的 60，批量跑评测时发现大部分时间都在等限流，才调到了 300。

### 记账和管理端

每调一次模型，往 `llm_calls` 表写一行：哪个场景、挂在哪个对象上、哪家的哪个模型、用了多少 token、估算花费、耗时、有没有命中缓存、成没成功、失败原因。

管理端的统计就是查这张表。它没有记「是哪个用户的」，所以分两步：先按（天、场景、对象）汇总，再去查这些对象是谁的，每种对象一条 `IN` 查询。失败的调用按报错里的状态码归成一句人话（余额不足、密钥无效、超时……），原始报错点开才看。

### 在线换模型

- **怎么做到不重启**：进程里留一份「现在用哪家」。只在两个时候读数据库：服务启动时、管理端改了以后。平时调模型直接看这一份。
- **切换前先试**：保存、换 Key、切换之前都真调一次，调不通就什么都不改。填错一个字符，全站的诊断和面试都会停，不能先存了再说。
- **Key 怎么存**：加密后才进数据库（Fernet 对称加密，钥匙从 `JWT_SECRET` 派生）。接口只返回开头 3 位和后 4 位。

### 可能的追问

- **缓存和数据不一致的问题，这里有吗？**
  基本没有。缓存的是「这段输入 → 这个答案」，输入不变答案就能用，没有「数据被改了缓存没跟上」的情况。提示词改了就升版本号，旧缓存自动失效。
- **为什么限流用 Redis，不在程序里放一个变量？**
  `INCR` 是原子的，十几个分支同时加 1 一个都不会少算；评测脚本和网站同时跑，算的也是同一个上限。
- **固定窗口有什么问题？**
  第 59 秒来 300 次、下一分钟第 0 秒又来 300 次，两秒里放过了 600 次。为什么没换见上面那段话。
- **`INCR` 和 `EXPIRE` 是两条命令，中间挂了怎么办？**
  key 里带着分钟数，过了这一分钟就没人再用它，最坏是留下一个没过期的小 key，不会算错。要严格就用 Lua 脚本合成一步。
- **和 Sentinel 的限流有什么不同？**
  Sentinel 限的是别人调我，保护自己的服务；这里限的是我调别人，免得被服务商拒绝。
- **实际会被卡住吗？**
  平时不会，一次投递也就十来次调用。真被卡住是上限还是 60 的时候跑评测：60 份里 13 份要等到下一分钟，一份 13 秒，调到 300 后约 2.5 秒。
- **花费准吗？**
  是估算：单价 × token 数，不是服务商的账单。页面上也标了「估算」。
- **部署多个实例，「现在用哪家」怎么同步？**
  现在不支持，项目是单进程跑的。要多实例，得把这份配置放到 Redis，或者改了以后发通知让每个实例重读。
- **`JWT_SECRET` 换了，库里的 Key 怎么办？**
  解不开了。启动时发现解不开，就退回 `.env` 里的那一家并记日志，页面上那一条标「要重新填」。
- **为什么不接 Langfuse 这类现成的平台？**
  数据本来就在自己的表里，缺的只是统计和页面。现成的平台要多起五六个容器，每次调用还要再往它那边写一份。

实现细节：08 第 4 章（调用层）、第 13 章（管理端）。

## 9.7 专业技能里的三行

### FastAPI 那一行，每个词指项目里的什么

| 词 | 项目里的例子 |
|---|---|
| 依赖注入 | 接口参数写 `Depends(...)`，进接口前先查「登录了没有 → 这份简历是不是你的 → 解析完了没有」，一层叠一层；管理端接口挂 `require_admin`。测试时把数据库、模型换成假的，业务代码不用改 |
| Pydantic 校验 | 请求体、响应体的形状（[schemas.py](../backend/app/schemas.py)）；模型返回的 JSON 也用它检查字段齐不齐、类型对不对 |
| SSE 流式接口 | 三个：投递进度、修改建议一个字一个字出、面试出题（[api/sse.py](../backend/app/api/sse.py)） |
| pytest 测试 | 500 个用例，约 35 秒，不联网：假模型、内存数据库、假时钟 |
| Docker 部署 | `docker compose up -d --build` 起四个容器：Nginx、后端、MySQL、Redis |

和 Spring Boot 的对应关系见 [07](07-代码导读.md) 第 1 节：`api/` 是 Controller，`services/` 是 Service，`schemas.py` 是 DTO。面试官是 Java 背景时，用这张对照表讲最快。

### LangGraph / LangChain 那一行

括号里的三个词见 9.4。后半句「结构化输出与校验重试」：

- **结构化输出**：不让模型回一段话，而是回固定格式的 JSON，程序才能直接取用。
- **校验重试**：交上来的东西不合格，就把错在哪告诉它，让它重做。两类不合格走同一套办法：格式不对（缺字段、类型错）；内容不对（引用的原文找不到）。
- **为什么不用 LangChain 自带的 `with_structured_output`**：它也能做。但我们要在同一处做缓存、限流、记账，还要把错误原因整理成给模型看的话去重试，自己包一层更好控制。

### RAG 那一行

| 词 | 用自己的话说 |
|---|---|
| RAG | 资料太长时不整份塞给模型，先查出最相关的几段，再连同问题一起给它 |
| 向量召回 | 粗筛。把每段文字变成一串数字，意思相近的文字数字也相近；提问时找出最接近的 20 段 |
| 重排 | 精筛。把「问题 + 每一段」放在一起逐个打分，只留最相关的 3 段 |
| Chroma、bge | Chroma 是存向量、找最接近的几个的数据库；bge 是把文字变成向量的模型和重排模型 |

**项目里只有一处用到**：模拟面试时，用户贴的面经超过 3000 字。

| 情况 | 怎么处理 |
|---|---|
| 没贴 | 不检索 |
| 贴了，不超过 3000 字 | 整段直接给模型，不检索 |
| 贴了，超过 3000 字 | 切成约 500 字一段存进向量库；每个话题先找出 20 段，重排后留 3 段 |

贴岗位 JD 不会触发它：JD 是让模型拆成一条条要求存进数据库，匹配时直接拿来用。

被问「你的项目哪里用了 RAG」：

> 只有一处，面试时用户贴的长面经。匹配没用，因为我实测过：简历加岗位要求才两三千字，全文一次给模型只要一次调用；逐条检索再判断要几十次调用，更贵更慢，还会因为检索漏掉片段而判错。

## 9.8 不分哪一点的问题

### 「印象最深的问题」可以讲这几个

挑一个讲透，按「现象 → 原因 → 怎么改 → 学到什么」说。

| 问题 | 一句话 | 细节在 |
|---|---|---|
| 刷新页面，整个服务卡几秒 | 流式接口用的同步生成器，是在事件循环的线程里被回收的，回收时要等模型的流读完，这几秒所有请求都没人理。改成放到线程里取和收尾。改完又带出新问题：原来靠「卡着」顺带保证的先后顺序没了，要补一个等待 | 08 第 7 章 |
| 轮询一直读到旧状态 | 后台任务等简历解析完，只 `refresh` 一直读到「解析中」。MySQL 默认是可重复读，同一个事务里看到的都是开始那一刻的快照。先 `commit` 结束事务再读 | 08 第 7 章 |
| 评测「变慢」其实是在等限流 | 每份 13 秒，以为是模型慢；查下来大部分时间在等下一分钟。上限 60 → 300 后约 2.5 秒 | 08 第 4 章 |
| 进度推送偶尔收不到「结束」 | Redis 发布订阅发了就忘，错过一次就永远等。结束信号改成以数据库为准 | 08 第 7 章 |
| 换了向量模型，新向量存不进去 | Chroma 的集合维度在第一次写入时就定死，只删记录不够，要把集合删掉重建 | 08 第 13 章 |

面试官是 Java 后端背景时，第二个最容易聊开：事务隔离级别是共同话题。

### 「这个项目有什么不足，重做会怎么改」

- **只能单进程运行。** 启动时清理没跑完的任务、同一场面试的锁、「现在用哪家模型」，都放在进程里。要多实例，得把锁和配置挪到 Redis。
- **评测数据全是合成的**，没有真实简历和人工标注。
- **限流是固定窗口**，交界处会突发。
- **`llm_calls` 没记用户**，统计时要多查几次。当初没加，是因为要把「当前用户是谁」一路传到调模型的地方，改动大。
- **改密码后别的设备不会立刻下线**：JWT 发出去只能等它过期。
- **只在本机用 Docker 部署过**，没上公网，没做过压测。

### 「测试怎么做的」

500 个用例，约 35 秒，不联网、不需要 MySQL 和 Redis。外部依赖全换成假的：模型是按「问的是什么」给预设回复的假模型，数据库是内存里的 SQLite，要等的逻辑用假时钟。想测「模型编造引用」「模型挂了」「连接中途断开」，都能精确造出来。真模型的效果不靠单元测试，靠评测。细节见 08 第 11 章。

### 「这个项目是用 AI 写的吗」

仓库是公开的，里面有 `CLAUDE.md`，点进来就能看到这是和 AI 编程助手一起做的，所以如实讲。重点放在哪些是自己定的：

- 评测全部自动化、不做人工标注，标准答案在造数据时定好。
- 版面解析不做大模型兜底，改用规则修。
- 面试只检索用户贴的面经，简历和岗位要求不检索。
- 只做一轮专业面，不做 HR 面：太主观。
- 让用户先选求职方向，不让模型去猜：少一类「用错标准」的错误。
- 管理端自己做，不接现成的平台。

然后挑 9.4–9.6 里的一个设计，把为什么这么做讲清楚。
