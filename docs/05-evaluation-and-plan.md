# 八、评估方案

## 8.1 评测集构成与局限

```
程序化降质（规则类，GT 自动）：删量化数字 / 强动词降级 / 技能栏多写一个经历里没用过的技能 / 造时间空窗
程序化降质（语义类，只有 LLM 通道能检，注入在 bullet 正文）：夸大注入 / 逻辑矛盾注入 / 职责混合注入；判分为位置命中，risk_type 另报类型准确率
局限：降质只覆盖预设缺陷；语义类边界模糊；评测数据全为合成、没有真实简历与人工标注；第三方 API 静默升级（以 model_version 记录）
```

**评测全部自动化，不做人工标注**（2026-10-06 用户定的）：系统定位是给求职者用的自动化平台（企业也多用 AI 初筛），流程里没有人工审核；
评测用"造数据时就定好标准答案"代替人工标注——诊断用程序化降质，匹配用"按构造就知道满足与否"的简历 + 岗位要求，面试评分用质量分档已知的回答；
残留幻觉以"引用核对拦截率"代替。论文里如实写明：评测数据是合成的，没有用真实简历和人工标注验证。

实现（2026-10-06）：`scripts/gen_eval_set.py` 用 20 份虚构底稿各出 3 个版本——干净 / 规则类降质 4 处 / 语义类注入 3 处，共 60 份单页 PDF（`data/eval_set/`，不进仓库）。
底稿刻意"干净"：技能栏只列项目技术栈里的技能、两段实习只隔 1 个月、每条描述都以实打实的动词开头并带数字和结果词，这样每处缺陷有没有被检出可以干净地判断；
同一份里的几处缺陷落在不同的描述上，互不干扰。"删技能提及"改成"技能栏多写一个没用过的技能"（触发的是同一条规则，造起来更干净）；
"套表格模板"这轮不做：ATS 规则只看图片，表格本来就不计入。`scripts/run_eval.py` 按 rule_only / llm_only / hybrid 跑诊断：解析走缓存（不是被测对象），
诊断在评测批次号下绕过缓存。

## 8.2 版面解析评测

合成集：20 份虚构内容 × 6 种版式 = 120 份单页 PDF，`scripts/gen_layout_set.py` 生成到 `data/layout_set/`（固定随机种子，不进仓库）。
版式：单栏 / 两栏 / 侧边栏 / 表格型（带边框）/ 时间轴（经历的日期单独成左列）/ 无边框表格型（表格型去掉边框，只靠对齐）。
PyMuPDF 按阅读顺序逐段绘制，GT = 绘制顺序；字号、边距、行距、栏宽、项目符号、标题下划线随机，一半侧边栏带底色块。真实集 20 份可砍。
指标（`scripts/eval_layout.py`）：相邻行对顺序准确率（GT 里相邻的两段，在输出里也**紧挨着且顺序一致**才算对——只看"前一段在前"时，
两栏按行交错着读几乎不扣分）、文档级全对率、版面类型判对率（时间轴应判 single，无边框表格型不算）。
对照：PyMuPDF sort=True / 最初的规则（去掉表格识别和时间轴日期列）/ 现在的规则。原计划的"启发式 + LLM 兜底"不做，理由见 04-design 5.1 末尾。

2026-10-06 结果（相邻行对顺序准确率，括号里是全对的文档数 / 20）：

| | 单栏 | 两栏 | 侧边栏 | 表格型 | 时间轴 | 无边框表格型 | 总体 |
|---|---|---|---|---|---|---|---|
| PyMuPDF sort=True | 100%（20） | 34.9%（0） | 41.8%（0） | 100%（20） | 100%（20） | 100%（20） | 77.7% |
| 最初的规则 | 100%（20） | 100%（20） | 100%（20） | 77.4%（0） | 83.0%（10） | 77.5%（0） | 89.8% |
| 现在的规则 | 100%（20） | 100%（20） | 100%（20） | 100%（20） | 100%（20） | 89.3%（0） | 98.2% |

- PyMuPDF 按坐标从上到下读，逐行的版式（表格、时间轴）天然读对，两栏会左右交错；规则正好相反，表格识别和时间轴日期列补的就是这一块。
- 无边框表格型的剩余错误：顶部「姓名 / 电话 | 求职意向 / 邮箱」2×2 信息格被按列读（不影响抽取）；左列章节名和右边第一行拼成一块，章节会认不出（已知局限）。
- 版面判对 96/100：两份侧边栏（宽 180pt）的空白带中心落在页宽 41.5%，被判成 double；两份时间轴被判成 sidebar 0.8（外层先按跨栏行切过一刀、记成了分栏，里层才认出日期列；阅读顺序是对的，类型只作记录）。
- 合成版式规整，这组数只说明"设计覆盖的版式都做对了"，真实简历要另测。

## 8.4 模拟面试评测

```
评分区分度   质量分档已知的回答（具体到位 / 空泛 / 答错），看系统分是否按档排序（代替"人工打分 vs 系统分"）
评分稳定性   同一回答 --repeat 3 的标准差
evidence 有效率  面试评分 evidence 经 locate_span 通过的比例（与诊断拦截率同口径）
```

「薄弱点覆盖率」不测：定话题的提示词规定简历问题最多 2 个，"前 5 条被覆盖"最多 40%，测的是提示词里的规则。

**结果**（2026-10-06，`scripts/run_eval.py --task interview --repeat 3`；`data/eval_runs/interview-20261006-173359.json`）

`scripts/interview_answers.py`：从降质集的 6 个虚构项目各出 2 道题，共 12 题；每题写三档回答，档位在写的时候就定了——
具体到位（做法、原因、效果都讲清，结果数字和简历一致）/ 空泛（只说做了什么，没有说错）/ 答错（篇幅、细节和"具体"相近，核心技术说法是错的）。
直接调线上同一个评分函数 `rubric.evaluate`（不走整场面试），36 条回答各打 3 次分，共 108 次调用。

| 档位 | 总分（0–100） | 正确性 | 深度 | 表达（0–5） |
|---|---|---|---|---|
| 具体到位 | 86.4 | 4.64 | 3.36 | 4.97 |
| 空泛 | 37.7 | 2.03 | 1.00 | 2.64 |
| 答错 | 36.1 | 1.17 | 1.00 | 3.28 |

- 区分度：3 次里"具体 > 空泛""具体 > 答错"都是 12 / 12（100%）；具体档最低 67 分，另两档最高 47 分，没有交叉。
- 分项：空泛档扣得最多的 100% 是深度；答错档 83.3% 是正确性最低，另外 2 题模型把深度（1）打得比正确性（2）还低。
  空泛和答错的总分差不多（36 次比较里空泛高 14 次、相等 15 次、低 7 次），分项上能分开：答错的正确性更低、表达更高。
- 稳定性：评分温度为 0，同一回答 3 次得分完全一样的占 75%；不一样的 9 条里 8 条只是某一项差 1 分（总分差 7 分），最大一次差 13 分；平均标准差 1.06 分。
- evidence：第一次输出就合格 100%，引用全部逐字命中，"没有依据、给中性分"没有触发。
- 成本：每条回答 ¥0.0047、3.1 秒。
- 局限：回答是开发者写的，不是真人回答；每档特征都很典型，区分度偏乐观。只测评分，没测出题和定话题。

# 九、验证方式

1. **坐标契约**：`test_layout.py`、`test_resume_upload.py` 断言 `full_text[b.char_start:b.char_end] == b.text`
2. **解析**：`scripts/eval_layout.py` 输出 8.2 指标表
3. **溯源**：`findings.verify_result='failed'` 首轮占比；面试 evidence 通过率（`run_eval.py --task interview`）
4. **诊断**：`scripts/run_eval.py` 在降质集上跑三种模式，输出 8.3 (3)(4) 的指标表
5. **匹配**：`run_eval.py --task match`，与造数据时定好的标准答案比一致率（8.3 (2)）
6. **面试推进与评分**：`test_interview.py` 覆盖 追问上限 / 跳过 / 成本到顶提前结束 / 分数聚合与结论 / 话题编号核对 / 续答与检查点重建 / 24h 清理
7. **端到端**：`docker compose up -d` 后：贴 JD（或选模板）→ 上传简历 → 投递 → 初筛结果 → 具体建议 → 技术面 → 报告
8. **中断**：面试中 kill 进程后重启，会话可续答；24h 清理生效
