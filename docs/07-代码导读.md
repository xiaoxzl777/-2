# 七、后端代码导读

> 每个文件夹是干什么的、为什么需要、哪些要吃透、哪些当黑盒就行。
> 后端 `app/` 约 8000 行、80 多个文件，需要细读的只有第 5 节列的几个文件。

## 1. 先建立对应关系：它就是一个分层的 Web 后端

和 Spring Boot 的分层是一一对应的：

| 这个项目 | Spring Boot 里叫 | 干什么 |
|---|---|---|
| `app/api/` | Controller | 接请求、校验参数、返回 JSON。每个文件约 20–110 行，很薄 |
| `app/services/` | Service | 编排流程、读写数据库、开后台任务 |
| `app/models.py` | Entity | 11 张表 |
| `app/schemas.py` | DTO / VO | 请求体、响应体长什么样（Pydantic） |
| `app/deps.py` | 拦截器 + 参数解析器 | "当前登录用户是谁""这份简历 / 这次投递是不是你的""解析完了没有" |
| `app/config.py`、`app/database.py` | application.yml、DataSource | 读 `.env`、数据库连接 |
| `app/errors.py`、`app/security.py` | 全局异常处理、JWT 工具类 | 统一响应 `{code, message, data}`、密码哈希与令牌 |
| `app/main.py` | 启动类 | 启动时检查 MySQL / Redis、清理上次没跑完的任务、挂路由；服务开着时每小时扫一次很久没动静的面试，按已答的题出报告、标成放弃（`sweep_forever`） |

**以上是普通 Web 后端，扫一眼即可。** 真正新的东西在下面几个包里。它们有一个共同约定：
**只做计算，不碰数据库**（输入是普通数据，输出也是普通数据），算完交给 Service 去存。好处是能单独测试、单独做实验。

| 包 | 约多少行 | 一句话 |
|---|---|---|
| `app/parser/` | 1630 | PDF → 一段全文 + 每块文字的位置 + 结构化信息 |
| `app/diagnose/` | 530 | 找出简历写得不好的地方（7 条规则 + 大模型） |
| `app/matching/` | 430 | 把 JD 拆成要求，逐条判断简历满不满足 |
| `app/rewrite/` | 120 | 具体建议：拼 prompt、数字复检 |
| `app/interview/` | 470 | 模拟面试：材料编号、定话题、出题、评分、推进规则、报告 |
| `app/graphs/` | 570 | 用 LangGraph 把上面的步骤编排成流程图（并行、分支、停下来等人） |
| `app/llm/` + `app/retrieval/` + `app/cache/` | 1020 | 调大模型、调向量模型、查向量库、用 Redis |
| `app/domains/` | 190 | 求职方向（计算机 / 运营）：每个方向一份提示词片段、规则开关和页面文案，见第 4 节和 [04](04-design.md) 4.16 |

## 2. 整个系统只有三个核心想法

所有看起来复杂的代码，都是这三件事的不同写法。答辩和面试讲清这三条就够了。

### ① 坐标系

解析完简历后拼出一个 `full_text`（所有文字按阅读顺序用换行连起来），**之后永远不改**。
系统里任何东西——一个块、一条经历、一个问题的证据、一条匹配依据——都用 `char_start / char_end` 表示
"它是 full_text 的第几个字到第几个字"。

- 前端高亮只需要按区间涂色；
- 代码和测试里到处是 `full_text[start:end] == 这段文字`，检查的就是坐标没有错位；
- 定义坐标系的只有一个函数：`parser/layout.py` 里的 `assign_offsets`。

### ② 模型说的话，必须能在原文里找到（反幻觉）

模型说"这句话有问题"，就拿它引用的那句话去原文里找——先精确找，找不到再模糊找（相似度 ≥ 90）。
**找不到 = 它编的，丢掉并计数。** 这个函数是 `diagnose/evidence.py` 的 `locate_span`，五个地方共用：

| 哪里 | 模型引用的是 | 找不到怎么办 |
|---|---|---|
| 诊断 | 简历里有问题的那句话 | 带着原因让模型重试，最多 2 次；还不行就丢弃 |
| JD 解析 | JD 里提出这条要求的原话 | 这条要求丢弃 |
| 匹配（全文模式） | 简历里能证明满足要求的那句话 | 这条按"未满足"处理 |
| 结构化抽取 | 技能栏里的技能名（必须真在它所在的块里） | 这个技能丢弃 |
| 面试评分 | 候选人回答里的原话 | 重试一次；还不行给中性分、权重减半 |

规则引擎的证据本来就是从原文切出来的，不用核对。

被丢弃的数量都落库了（`hallucination_count`），论文里的"幻觉拦截率"就是从这里算的。

### ③ 确定的用规则，模糊的交给模型

| 用代码判（免费、结果稳定） | 问模型 |
|---|---|
| 这条描述里有没有数字 | 这句话是不是空话、有没有夸大 |
| 学历够不够、工作年限够不够 | "有高并发项目经验"算不算满足 |
| 要求的技能词在简历经历里出现过没有 | 简历写的是 MyBatis-Plus，JD 要 MyBatis，算不算 |

规则先跑，规则判不了的才花钱问模型。诊断、匹配的分数用公式算，**不让模型打分**（模型打分不稳定，也说不清为什么是这个分）。
面试评分离不开模型的判断：模型按 0–5 给正确性、深度、表达三项，依据必须逐字引用回答；题分、话题分、综合分和结论由公式算。

## 3. 一次"投递"从头到尾经过哪些文件

用户点"投递"（`POST /apply`，带上简历 id 和岗位 id）之后：

1. `api/apply.py` 校验：简历是你的吗、岗位看得见吗 → 建两条"待处理"记录（一条诊断、一条匹配）→ 把活丢给后台任务，立刻返回。
2. `services/apply_service.py` 的 `run_apply`（后台）：如果简历还在解析就等它 → 准备好数据 → 跑图 A → 每完成一步往 Redis 发一条进度。
3. `graphs/apply_graph.py`（图 A）：**诊断和匹配同时跑**，两条都完成后看匹配度到没到初筛线（`SCREEN_THRESHOLD`，60 分）。
   - 诊断那条线 `graphs/diagnose_graph.py`：7 条规则扫一遍 → 每条经历**并行**发给模型审 → 去重合并 → 算分。
   - 匹配那条线 `graphs/match_graph.py`：规则先判 → 规则判不了的要求，连同简历全文**一次**交给模型判断 → 算分。
4. 回到 `apply_service`：调 `diagnose_service.save_result` 和 `match_service.save_result` 把结果写进数据库。
5. 前端通过 `api/task.py`（SSE）实时看到进度；结束后请求 `GET /apply/{id}`，拿到"过没过 + 哪里不符合"。

LangGraph 在这里的价值就两个字：**并行**（每条经历同时审、诊断与匹配同时跑）。除此之外它只是把步骤连起来。

## 4. 各板块说明

### parser/ —— 解析（按执行顺序）

| 文件 | 干什么 | 要不要细读 |
|---|---|---|
| `extract.py` | 用 PyMuPDF 读出每一行的文字、坐标、字号、是否加粗，以及带边框表格的格子位置；扫描件 / 加密文件在这里被拦下 | 扫一眼 |
| `layout.py` | **全项目最难的文件。** 解决"两栏简历从上往下读会左右串行"：找页面中间贯穿上下的空白带，有就分左右栏分别读（但一边是一列日期的"时间轴"按行读）；表格先缩成一整块参与分栏，排好位置再按行展开；再把折行的句子合并成"块"；最后 `assign_offsets` 定下坐标系 | 懂思路即可，不必逐行 |
| `section.py` | 认章节标题（"项目经历""专业技能"）：标题词典 + 字号 / 加粗 / 是否独占一行 打分；词典认不出、但像标题的行记为候选；没有标题的教育从开头段切出来 | 扫一眼 |
| `section_llm.py` | 把候选标题一次交给模型归类（或判"不是标题"并回上一节），失败就当没问过 | 扫一眼 |
| `pii.py` | 姓名、电话、邮箱在本地用正则抽出来；发给模型之前把它们换成**等长**的 `X`（等长是为了不破坏坐标系） | 读，很短 |
| `structure.py` | 让模型把"项目经历"拆成一条条。关键设计：**模型只回块编号，不回文字**，文字由代码按编号去原文切——模型没有机会改写简历内容 | 读 `_extract_section` 这一个函数 |
| `normalize.py` | 把"2023.9 – 至今"这类日期统一成 `2023-09` | 不用读 |

### diagnose/ —— 诊断

| 文件 | 干什么 |
|---|---|
| `rules.py` | 7 条规则，每条一个小函数：成果没数字、只说做了什么没说结果、弱动词开头、技能列了却没在经历里用到、时间线有空窗或重叠、不利于机器解析、篇幅异常 |
| `llm_review.py` | 把每条经历单独发给模型审；引用在原文里找不到 → 带着原因让它重试，最多 2 次 |
| `evidence.py` | 核心想法②：`locate_span` |
| `scorer.py` | 五个维度各从 100 分往下扣（严重 25 / 中等 12 / 轻微 5），再加权 |
| `types.py` | 两个数据类：`ReviewUnit`（一条送审的经历）、`Finding`（一个被发现的问题） |

### matching/ —— 匹配

| 文件 | 干什么 |
|---|---|
| `jd_parser.py` | 调一次模型把 JD 拆成要求项（必须 / 加分 / 软素质 × 技能 / 学历 / 经验 / 其他），每条必须带 JD 原话 |
| `skill_dict.py` | 技能同义词词典（191 个技能：计算机 155 + 运营 36，词典不分方向）：认出 "SpringBoot" 和 "Spring Boot" 是同一个；解析简历时顺手把全文里出现的技能都标出来（`skill_mentions`）。词典存在 `skills` 表里，由 `services/skill_service.py` 读出 |
| `matcher.py` | 规则能判的先判（技能词、学历、年限）+ 加权算总分。规则只判十拿九稳的：要求就是技能名本身、且经历里确实用过；带限定语的（"熟悉 Redis 缓存穿透…"）交给模型 |
| `llm_judge.py` | 规则判不了的要求，连同简历全文一次交给模型；模型说"满足"就必须逐字引用简历里的依据，引用找不到就作废 |

匹配有三种模式，是给论文的对比实验用的，线上只用 `hybrid`：

| mode | 做法 | 用途 |
|---|---|---|
| `dict_only` | 只用规则，不调模型 | 基线 |
| `llm_fulltext` | 不用规则，全文 + 全部要求一次问模型 | 对照：只用模型 |
| `hybrid` | 规则先判，剩下的一次问模型 | 线上默认 |

**为什么匹配不用 RAG**：简历加 JD 一共两三千字，放得进 prompt 就不检索；实测对比见 [06](06-workflows.md) 6.2。

### rewrite/ —— 具体建议

结果页上点开一条问题或差距时，现场让模型针对这一句 / 这条要求写建议（规则的固定模板"说得太泛"）。
`advice.py` 只做两件纯计算：拼 prompt 要的上下文（这一句、所属经历、JD 原话，一律用掩码文本），以及生成后的**数字复检**——
改写里出现原文没有的数字就换成【数值】。调模型、存库在 `services/advice_service.py`，接口在 `api/advice.py`（流式）。

### interview/ —— 模拟面试（只有专业面：计算机叫技术面，运营叫运营面；不做 HR 面）

| 文件 | 干什么 |
|---|---|
| `materials.py` | 整理一场面试的材料：岗位要求 + 初筛判定、经历（掩码文本）、简历问题、面经；每条带一个编号（P1、R9、F128），话题用它指回材料 |
| `planner.py` | 一次模型调用定一场的话题（默认 5 个，配置项 `INTERVIEW_TOPICS`），代码核对每个话题的编号是否真实存在；能用的不够数就带着原因重试一次，取能用的多的那次 |
| `asker.py` | 拼出题的 prompt（主问题和追问共用，追问时带上本话题的问答和上一答的不足）；第一题前的开场白由代码拼 |
| `rubric.py` | 评分：模型按 0–5 给三项分，依据必须逐字引用回答，由代码核对；题分、话题分、综合分、结论全是公式 |
| `policy.py` | 答完一题之后追问、换话题还是结束（纯函数） |
| `report.py` | 面试报告：分数聚合 + 模型写文字总结（表现好的 / 需要加强 / 和简历问题的关联） |

图在 `graphs/interview_graph.py`（图 B），落库和推进（面试的状态机）在 `services/interview_service.py`，接口在 `api/interview.py`（流式）。

### llm/ 与 retrieval/ —— 模型调用和检索

| 文件 | 干什么 |
|---|---|
| `retrieval/context_store.py` | **标准的两阶段检索**，用在模拟面试：用户贴的面经超过 3000 字时切段、向量化后存进 Chroma；每个话题先用向量相似度**召回**若干段，再用 reranker **精排**出最相关的 3 段；面试结束就删 |
| `retrieval/chroma_client.py` | 打开嵌入式向量库（数据在 `data/chroma`，不需要单独起服务） |
| `llm/client.py` | 全项目调 DeepSeek **只走这一个函数**，固定五步：查缓存 → 限流 → 调用 → 记账（写 `llm_calls` 表）→ 写缓存。模型输出不是合法 JSON 时不抛异常，而是把错误原因返回，由调用方带着原因重试。`stream()` 是流式版本（具体建议、面试出题用），同样五步 |
| `llm/embedding.py` | 调硅基流动的向量接口（bge-m3）和重排接口（bge-reranker） |
| `llm/prompts.py` | 所有提示词集中在这里，每组带版本号；改了提示词就升版本，旧缓存自动失效。随求职方向变化的地方写成 `[[标记]]`（见下面 domains/） |
| `llm/registry.py`、`llm/audit.py` | 模型名 → 模型对象与单价；写审计表 |

### graphs/ —— LangGraph

图 A `apply_graph` 与它的两个子图 `diagnose_graph`、`match_graph`（见第 3 节），以及模拟面试的图 B `interview_graph`。`state.py` 定义图里流动的数据长什么样；带 `Annotated[..., add]` 的字段表示
"多个并行分支会同时往里写，用加法合并"——这是 LangGraph 并行的固定写法。
图 B 会在 `wait_answer` 停下来等用户回答（`interrupt()`），状态存在检查点里（`checkpoint.py`，本地 SQLite 文件 `data/checkpoints.sqlite`），用户答完再从原地接着跑。

### cache/ —— Redis 的三个用途，一个文件一个

`llm_cache.py` 模型结果缓存（同样的输入不重复付费）、`ratelimit.py` 限流（每分钟最多多少次调用）、
`pubsub.py` 后台任务的进度推送。`redis_client.py` 是连接。

### domains/ —— 求职方向（领域包）

同一套流程，按岗位的方向换提示词里的角色、示例和评分说明，开关个别规则。

| 文件 | 干什么 |
|---|---|
| `__init__.py` | `Domain`（一个方向的全部差异：提示词片段、`disabled_rules` 要关掉的诊断规则、`result_words` 规则额外认的结果词、页面文案、示例 JD）；`get_domain(key)` 按方向取包，没有方向的老数据按计算机处理；`fill()` 把提示词里的 `[[标记]]` 换成包里的文字，包里缺了就直接报错 |
| `cs.py`、`ops.py` | 计算机、运营各一份：`TEXTS`（每个 `[[标记]]` 对应的文字）、`DISABLED_RULES`（目前两个方向都没关规则）、`RESULT_WORDS`（运营的「涨粉、阅读量」等，计算机为空）、下拉框和页面上的文案 |

`llm/prompts.py` 里有 24 个 `[[标记]]`，在 `.format()` 填完运行时内容之后才由 `fill()` 替换，所以包里的示例 JSON 不用给花括号转义。
方向存在岗位上（`jobs.domain`），诊断、匹配、JD 解析、具体建议、面试都按它取包；`api/domain.py` 把方向列表给工作台第一步的下拉框。
**简历解析不分方向**：上传时还不知道投哪个岗位，章节词典、技能词典都用全集。加一个方向 = 加一个包 + 技能词条 + 岗位模板，流程代码不用改。

### services/ 与 api/

一个业务一对文件：`resume`、`job`、`apply`、`interview`、`diagnose`、`match`、`advice`（具体建议）各有 `api/xxx.py` 和 `services/xxx_service.py`。只有一边的：

- `api/auth.py`（注册、登录、当前用户）、`api/system.py`（健康检查）、`api/domain.py`（求职方向列表）、`api/task.py`（后台任务的进度流）、`api/sse.py`（SSE 拼装，进度流、具体建议、面试三处共用）；
- `services/parse_service.py`（解析简历的后台任务）、`services/skill_service.py`（从 `skills` 表读技能词典）。

后台任务只有两种：**解析**（上传时触发，入口 `parse_service.parse_resume`）和**投递**（诊断 + 匹配 + 初筛，入口 `apply_service.run_apply`），
直接用 FastAPI 的 `BackgroundTasks`，在接收请求的进程里跑，所以服务必须单进程；解析不在图里。诊断与匹配不单独触发，只提供查询接口。
具体建议和模拟面试不是后台任务，是请求里直接流式返回（POST + text/event-stream）。

### tests/、scripts/、sql/、部署文件

- `tests/`（约 4500 行、约 370 个用例）：**不用读。** 它的作用是保证改代码时不会把以前的功能改坏；里面的模型、向量库、Redis、检查点全是假的，不联网。
- `sql/schema.sql`、`sql/seed.sql`：建表，以及技能词典 + 岗位模板，手动在 MySQL 里执行（Docker 部署时首次启动自动执行）。它们由 `scripts/dump_schema.py` / `dump_seed.py` 从 `models.py`、`data/skills_seed.csv`、`data/job_templates.json` 生成；json 由 `scripts/build_job_templates.py` 解析 `data/job_templates/<方向>/*.txt`（`cs/`、`ops/`）得到，原文没改过的模板沿用 json 里的结果、不重新调模型。改表后重新生成即可（没有线上数据，不需要迁移脚本）。
- `scripts/gen_layout_set.py` → `scripts/eval_layout.py`：生成 120 份虚构的版面合成集到 `data/layout_set/`（单栏 / 两栏 / 侧边栏 / 表格型 / 时间轴 / 无边框表格型，带标准阅读顺序），再给解析的阅读顺序打分，和 PyMuPDF 自带的排序、最初的规则对比（结果见 [05](05-evaluation-and-plan.md) 5.2）。
- `scripts/gen_eval_set.py` → `scripts/run_eval.py`：评测诊断、匹配、面试评分，结果见 05 的 5.3、5.4。
  - 评测集：`gen_eval_set.py` 生成计算机 20 份虚构底稿 × 3 个版本（干净 / 规则类降质 / 语义类注入），在 `data/eval_set/`；`--domain ops` 用 `scripts/eval_set_ops.py` 的素材生成运营 10 份底稿 × 3 个版本，在 `data/eval_set_ops/`。
  - `run_eval.py` 默认按 rule_only / llm_only / hybrid 跑诊断，算检出率、拦截率、花费（溯源与架构消融）；`--task match` 用规则类降质版配上按内容就能定答案的岗位要求，比较 dict_only / llm_fulltext / hybrid 三种匹配模式；`--task interview` 拿 12 题 × 三档回答（具体 / 空泛 / 答错；计算机在 `scripts/interview_answers.py`，运营在 `scripts/interview_answers_ops.py`）调面试评分函数，看分数是否按档排序、几次打分是否一致。
  - `--set` 选评测集（计算机 / 运营），`--domain` 选用哪个方向的领域包（默认同 `--set`）：同一批运营简历换两种包跑，就能看出领域包有没有用。结果 JSON 写到 `data/eval_runs/`。
- `data/`（`config.DATA_DIR`）：进仓库的只有 `skills_seed.csv`、`job_templates/`、`job_templates.json`。其余都不进仓库：运行时产生的上传 PDF（`uploads/`）、面经向量库（`chroma/`）、图 B 的检查点（`checkpoints.sqlite`）；脚本生成的 `layout_set/`、`eval_set/`、`eval_set_ops/`、`eval_runs/`；`resumes/` 放真实简历样本（含个人信息）。
- 部署文件：`docker-compose.yml` 起 mysql、redis、backend、nginx 四个容器；`backend/Dockerfile` 用 Python 3.13 装 `requirements.lock`、单进程跑 uvicorn；`frontend/Dockerfile` 先用 Node 打包前端，再放进 Nginx；`nginx/default.conf` 托管前端页面、把 `/api` 转发给后端（流式接口关掉缓冲）；`backend/.dockerignore`、`frontend/.dockerignore` 列出不发给 Docker 构建的文件。步骤见 [README](../README.md)「部署」，思路和坑见 [08](08-实现思路与代码讲解.md) 第 12 章。
